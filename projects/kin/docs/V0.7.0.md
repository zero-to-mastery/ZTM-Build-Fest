# v0.7.0 — Routines

**Status:** Frozen v0.7.0 capability contract. Daily/Weekly Routines are implemented through Rust replay, protocol v7, atomic IndexedDB writes and native Web Components. The user authorized v0.7.0 validation/tagging followed by v0.7.1 correctness. Earlier frozen contracts remain authoritative for their supported versions.

## Pre-implementation baseline and architectural trace

Kin is a local-first household coordination application using dependency-free Rust, a manual Wasm ABI, native Web Components and IndexedDB. At the start of v0.7 work, Today/Needs, Handoff, Talk, Pulse and Since You Last Looked existed. Routines had no implemented event codes or payload layouts; the old `ROUTINE_COMPLETED` catalogue entry was conceptual, not a frozen wire contract. Codes 1–13 were occupied. There is no separate TODO file in the project; release contracts, ROADMAP and TESTING carry the work and gates.

The current flow is:

1. A native control dispatches a bubbling, composed `kin:*` intent event.
2. `kin-app` freezes the command, manages busy/focus/retry state, and calls `EventStore.append`.
3. One IndexedDB read/write transaction reads ordered event rows and local context. The browser encodes a candidate with random event identity and the transaction's next logical time.
4. Before insertion, the synchronous JS bridge allocates/copies the candidate stream into Wasm and calls `kin_apply_events`. Rust parses, validates, deduplicates and replays in supplied order. Explicit `as_of` controls Pulse; the stable cursor controls summary selection.
5. Rust returns complete canonical state and the exact summary boundary. JS copies result bytes from the current memory buffer, strictly decodes them, and frees its input exactly once.
6. If Rust accepts, storage appends bytes and advances the counter atomically. Only transaction completion resolves the returned projection. Abort exposes no successful state.
7. `kin-app` updates component properties from that projection and broadcasts content-free invalidation. Peer/focus/visibility/timer refresh reads a consistent saved snapshot and replays it; it does not append events.

Relevant code: `rust/src/{event,state,protocol,abi}.rs`, `web/wasm/kin-engine.js`, `web/storage/event-store.js`, `web/components/kin-app.js`. Tests use native Rust, Node built-ins with real Wasm, and a dependency-free Chromium regression runner. Independent legacy byte fixtures must remain independent of new encoders.

Initial baseline: 82 Rust tests and 31 Node/real-Wasm tests pass. The checkout already contains documentation and bridge-test edits; preserve them. The local `kin-v0.6.3` annotated tag exists. No claim is made here about remote branch/merge state.

## Decisions not fixed by earlier contracts

These product/protocol choices were not fixed by v0.6.3. The following recommendations were adopted for v0.7.0:

| Decision                                | Recommendation and consequence                                                                                                                                                                                                              |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Week boundary                           | Monday through Sunday; fixed, without locale preference or ISO week numbers.                                                                                                                                                                |
| Civil-time authority                    | Browser-local Gregorian date, explicitly passed to Rust. No household time-zone setting yet. Different device zones can project different current periods; keys remain portable. A shared zone policy belongs to a later explicit contract. |
| Civil-date encoding/range               | Little-endian `u32` containing `year * 10000 + month * 100 + day`, years 1–9999. Zero is not a date. This is a calendar label, never Unix milliseconds.                                                                                     |
| First occurrence                        | Available immediately on the creation civil date, including a partial first week. Persist that date because envelope UTC time alone cannot reconstruct a historical local date.                                                             |
| Stale action across boundary            | Reject the stale intent after fresh Rust projection inside the write transaction; refresh and ask the user to act on the displayed current occurrence. Never retarget a completion/reopen or its retry.                                     |
| Replay versus current-action validation | Historical occurrence events remain valid independently of projection date. Current-only UI commands compare their frozen key to Rust's fresh canonical key before appending.                                                               |
| Editing                                 | Archive and create another Routine. No in-place text/cadence editing or unarchive in this line.                                                                                                                                             |
| Duplicate human actions in summary      | Follow v6: exact duplicate delivery appears once; distinct valid no-op actions are still facts and each may appear. No new summary coalescing policy.                                                                                       |

These choices are now part of the shipped contract. Future changes require explicit compatibility design; no unresolved decision expands this release line.

## Product semantics and terminology

A **Routine** is something the household wants to accomplish once during a recurring civil period. A **cadence** is Daily or Weekly. An **occurrence key** identifies a period; an **occurrence** is derived for a Routine and that key. **Completed** describes an occurrence, never permanent completion of the Routine. **Archived** is a terminal Routine tombstone.

Examples: feed the starter daily; take the trash out weekly; clean the kitchen weekly. Open means available to complete, without an overdue or failure implication. Advancing time creates no household fact, reset, missed count, or backlog.

Create, complete current occurrence, reopen current occurrence, archive. Definitions retain immutable text, cadence, creation civil date, creator and envelope creation timestamp. Archive hides the Routine from ordinary lists but retains its definition and source history. A separately identified replacement Routine starts fresh.

## Civil recurrence and identity

Use the proleptic Gregorian calendar, years 1–9999 inclusive. Gregorian leap years are divisible by four except centuries not divisible by 400. Reject invalid dates; do not normalize February 30 or month 13. `0001-01-01` is a Monday. Rust owns validation and weekday/week-start calculation.

- Daily key: the supplied civil date.
- Weekly key: the Monday on or before that date. The period includes that Monday through Sunday. The key can fall in the preceding month or year; no week number or week-year is encoded.
- Identity: `(routine_id[16], occurrence_key:u32)`. No random occurrence ID and no automatically generated event.
- No active occurrence when projection date is before `created_on`. On/after creation, project exactly the containing period. Weekly first key may precede `created_on` by up to six days.
- Prior-period completion never completes a new period. Reprojection after many periods immediately selects the containing period, without enumerating skipped periods.
- Clock rollback or zone change can select an earlier recorded period again. Its own completion state is replayed; history is not rewritten. Archive remains terminal regardless of projection date.

Midnight means a change in the browser's local civil date, not an elapsed 86,400,000ms. The browser obtains year/month/day from the same `Date` instance used for `as_of`. It must not use UTC `toISOString()` for the local date. Rust does not derive local dates from UTC timestamps or read the wall clock. No time-zone offset, zone database, exact time, or configurable week start is needed for this release.

## Explicit projection context

Protocol v7 requires `as_of:i64` (unchanged browser timestamp bounds) and `civil_date:u32` (valid date above), plus the existing optional summary cursor. Same ordered bytes + same context + same cursor produce identical output. Dates outside the supported range fail closed, even for empty v7 histories; old protocols retain their former ranges and behavior.

`as_of` controls Pulse only. `civil_date` controls Routine occurrence selection only. Rust validates both but does not claim they correspond to a particular zone. It cannot verify that correspondence without an additional zone contract. Projection time never filters or reorders source events.

## Event kinds and binary payloads

New schema-1 kinds, available only in protocol v7:

| Code | Name                           | Exact payload                                                                                   |
| ---- | ------------------------------ | ----------------------------------------------------------------------------------------------- |
| 14   | `ROUTINE_CREATED`              | `routine_id[16]`, `cadence:u8`, `reserved[3]=0`, `created_on:u32`, `text_length:u32`, `text[N]` |
| 15   | `ROUTINE_OCCURRENCE_COMPLETED` | `routine_id[16]`, `occurrence_key:u32` (20 bytes)                                               |
| 16   | `ROUTINE_OCCURRENCE_REOPENED`  | `routine_id[16]`, `occurrence_key:u32` (20 bytes)                                               |
| 17   | `ROUTINE_ARCHIVED`             | `routine_id[16]` (16 bytes)                                                                     |

Creation offsets: ID 0–15, cadence 16, reserved 17–19, creation date 20–23, text length 24–27, text from 28. Cadence: `0 = Daily`, `1 = Weekly`. Text: strict UTF-8, 1–4096 bytes, nonblank under existing Rust trim semantics; preserve exact text bytes, including BOM. All integers little-endian. Existing 88-byte envelope offsets and kinds 1–13 are unchanged; creation actor/timestamp come from the envelope.

All Routine envelope timestamps must satisfy the existing browser timestamp range; existing event timestamp contracts are unchanged. Occurrence events intentionally do not carry a second action date: the key records the explicitly targeted period, not an unverifiable claim about the sender's wall clock.

## Validation, replay and duplicate behavior

Replay continues in supplied IndexedDB order. Distinct events require strictly increasing positive logical time; UTC timestamp does not order events. Household must be consistent. IDs use the existing opaque 16-byte rules (no new nonzero restriction); Routine entity identity has its own namespace.

Exact same event ID and canonical bytes: ignore repeated delivery before order/transition checks. Conflicting bytes for the same event ID: category 4, no partial state. A distinct create for an existing Routine ID is invalid. Unknown Routine references, actions before creation in replay order, and any distinct action after archive (including repeat archive) are invalid. Identical delivery of an archive is still deduplicated.

Completion/reopen key must be a valid date. Daily key must be on/after the creation date. Weekly key must be Monday and on/after the Monday containing the creation date. A key before the first period or a non-Monday weekly key is invalid. Replay accepts valid recorded keys later than projection context: changing the clock must not make saved history invalid. Browser current-action rules below prevent future or stale-period writes through normal interaction.

Replay maintains completion state by `(RoutineId, key)` in transient Rust memory. Missing entry means open. Complete sets completed; reopen sets open. Distinct repeat completion and reopening an open period are valid state no-ops. Complete/reopen/complete ends completed. Multiple periods remain independent. Only the current period is returned; no history UI or persisted projection cache is introduced. Retain historical period facts through full replay so clock rollback is deterministic.

Malformed structure, date, enum, reserved bytes, UTF-8 or timestamp: category 2. Unknown protocol/kind/schema: category 3. Invalid references, lifecycle, blank text, period alignment/range relative to creation, cursor or identity/order: category 4. Resource bounds: category 5. Preserve existing ABI categories 1 and 6, and v1 KERR format. Validation failure yields no partial result or persistence.

## Protocol v7 request and ABI rationale

The exports do not change. The versioned buffer layout must change because v6 has no civil date or Routine projection and cannot express these fields in its reserved bytes. Keep v1–v6 byte-for-byte; never repurpose their reserved fields.

The v7 KINE header is 44 bytes:

| Offset | Size | Field                           |
| ------ | ---- | ------------------------------- |
| 0      | 4    | `KINE`                          |
| 4      | 2    | version = 7                     |
| 6      | 2    | reserved = 0                    |
| 8      | 4    | event_count <= 10,000           |
| 12     | 8    | as_of:i64                       |
| 20     | 1    | cursor_present, 0 or 1          |
| 21     | 3    | reserved = 0                    |
| 24     | 16   | cursor ID; all zero when absent |
| 40     | 4    | civil_date:u32                  |

Follow with unchanged envelopes and exact kind-specific payloads. A present cursor must match the supplied stream. Requests/results remain bounded to 64 MiB. No extra ABI command for recurrence, hidden module time, or retained household state.

Browser bridge: `applyEvents(records, asOf, cursorEventId, civilDate)` with explicit required civil date for the v7 writer. No default clock reads in the bridge. Strict result decoding continues supporting v1–v7. Legacy fixture callers construct their original requests independently.

Allocation/free rules are unchanged: JS owns one input allocation, frees once on success/failure; Rust borrows input and owns output. Reacquire `memory.buffer` after operations that can grow it; copy output before another apply call. Never retain Wasm typed-array views or free Rust result pointers.

## Result and state representation

KINS v7 header is 56 bytes. Offsets 0–51 have the v6 fields and meanings, with version 7. Offset 52 is `routine_count:u32`. Record order: Items, Handoffs, Talks, Pulses, Routines, then summary entries. Old entity record layouts and collection order do not change.

Routine records are in creation-event order, including tombstones. Fixed header is 56 bytes followed by text:

| Offset | Size | Field                                                  |
| ------ | ---- | ------------------------------------------------------ |
| 0      | 16   | routine_id                                             |
| 16     | 16   | created_by                                             |
| 32     | 8    | created_at:i64                                         |
| 40     | 4    | created_on:u32                                         |
| 44     | 4    | occurrence_key:u32, zero when unavailable              |
| 48     | 1    | cadence, 0 Daily / 1 Weekly                            |
| 49     | 1    | lifecycle, 0 active / 1 archived                       |
| 50     | 1    | occurrence state, 0 unavailable / 1 open / 2 completed |
| 51     | 1    | reserved = 0                                           |
| 52     | 4    | text_length:u32                                        |
| 56     | N    | strict UTF-8 text                                      |

Archived records always have unavailable occurrence/zero key. Active records projected before creation also use unavailable/zero. Otherwise require open/completed and a nonzero valid key, aligned with cadence and first period. Bridge validates structural combinations; Rust determines whether the supplied context makes a period current. JS decoded records use `routineId`, `createdBy`, `createdAt`, `createdOn`, `cadence`, `status`, `occurrenceKey` (null when unavailable), `occurrenceStatus`. No mutable JS completion map.

Combined Item/Handoff/Talk/Pulse/Routine count <= 10,000, plus at most eight summary records. Empty v7 result is 56 bytes. Unknown enum values, inconsistent zero keys/status, duplicate Routine IDs, invalid dates/text, overflowing counts/lengths, truncation and trailing bytes fail closed.

## Persistence, stale tabs and retries

IndexedDB stays schema 1, with the same stores/indexes/context. Extend metadata kind validation to 14–17 and preserve exact canonical bytes. No Routine table, migration, stored occurrence list, reset event, or time-zone metadata.

Create captures browser local date from the transaction's time sample. Complete/reopen commands freeze the occurrence key returned to the displayed component. In the serialized append transaction, read the current stream and context, capture fresh `as_of`/civil date once, and synchronously project the existing stream through Rust. Compare the command's key with that Routine's canonical current key, and require it still be active and available. This is an identity comparison against canonical state, not a JS recurrence calculation. A mismatch aborts with recoverable stale-action feedback and schedules refresh; never replace the command's key with the new key.

Then encode the candidate and replay the candidate stream with the same context before writing. This extra preflight is needed only for occurrence commands. Identical-period actions from two tabs serialize safely; distinct repeated completion is a valid no-op. An archived Routine fails without append. Rust remains responsible for all persisted lifecycle and period validation. No asynchronous work inside the transaction.

Failed writes preserve events, counter, cursor, draft and prior visible state. Retry freezes text/cadence for create and ID/key for occurrence actions. Failed create has no accepted creation date; a later retry obtains its date when it can commit. A committed operation is never retried as a second write because a subsequent projection fails: broadcast the committed invalidation and offer refresh-only retry. Repeated refresh failures preserve any pending command retry. Successful recovery never automatically appends. New intent supersedes an older retry.

After boundary change, clear an obsolete occurrence retry after canonical reprojection, explain “That period changed. Review the current routine.” Keep stored historical events intact. Broadcast only existing `events-changed` / `view-state-changed` markers, without content or dates/keys.

## Components and browser lifecycle

Add one `<kin-routines>` following existing list/capture conventions. No separate `<kin-routine>` is needed; no component framework or new runtime. Use a semantic section, h2, native labeled text input, labeled Daily/Weekly select (Daily default), Add button, and unordered list. Each row shows text, cadence, textual occurrence state, Complete/Reopen and Archive. Unavailable active records show “Not available for the current date” and no occurrence action. Hide archived rows.

Properties: `routines` receives decoded canonical records; `disabled` controls native controls. Events always bubble and are composed:

| Event                             | Detail                         |
| --------------------------------- | ------------------------------ |
| `kin:create-routine`              | `{ text, cadence }`            |
| `kin:complete-routine-occurrence` | `{ routineId, occurrenceKey }` |
| `kin:reopen-routine-occurrence`   | `{ routineId, occurrenceKey }` |
| `kin:archive-routine`             | `{ routineId }`                |

Components never write storage, calculate weeks, mark completion optimistically, or treat dispatch as success. KinApp owns orchestration/busy/error/retry and assigns only committed Rust state. Preserve independent best-effort tab draft `kin.routine.draft` containing text/cadence, cleared only on matching successful submission; denial of session storage must not block use.

Extend existing time refresh scheduling to run when Routine state needs it, even without Pulse. Sample fresh context on startup, refresh, focus, visibility return and advisory timer. Schedule near next local date boundary via browser calendar operations, capped at 60 seconds for clock/zone changes, alongside Pulse expiry. Never add fixed day milliseconds or mutate occurrence status in JS. Timers are advisory; visibility/focus replay handles missed days. A hidden callback may defer; reconnect queues replay while retaining busy protection. Disconnect cancels timers/listeners. Refresh failure preserves displayed canonical state and offers retry without a tight failure loop.

## Compatibility and non-goals

Preserve parsing/replay/encoding of all previously supported v1–v6 requests, result bytes, schemas and rejection behavior. Old protocols reject Routine events/state, including archived-only state, as unsupported rather than omitting them. Old households project unchanged existing entities and summaries under v7, with zero Routines. Old clients encountering new events fail closed and preserve bytes. No renumbering, source rewrite, reserved-byte reinterpretation or database migration.

Excluded: reminders, alarms, notifications, exact times, calendars, overdue labels, missed counts, streaks, percentages, scoring, assignments, custom weekdays, every-N recurrence, monthly recurrence, RRULEs, generated Items, history UI, analytics, backend/sync implementation, recurrence/text editing and background-generated facts. `.1`–`.3` add no capability.
