Evidence is separated by kind. Automated profiles and virtual authenticators
are not physical devices or human comparisons.

- 419 Node server/web tests across 42 files: 419 passed, 0 failed.
- Rust tests: 173 passed, 0 failed; doc tests: 0.
- Rust format, warnings-denied Clippy, version consistency, Kin diff whitespace,

  `1ea16fb68e1a1e3dcea34d06ad7f100cb6fc5fa2f1835b380f339b6f5662e9ce`.
  There is no committed expected WASM artifact, so repository-artifact parity
  is not applicable.

### 2. Service integration tests — PASS

The 419 Node tests include server, durable-store, HTTP, pairing, sync, archive,
member lifecycle, rotation recovery, and restart integration coverage. This is
the existing suite; it was not rewritten or weakened for this audit.

### 3. Independent browser-profile tests — PASS (with one transient first-run failure)

`npm run verify:browser` was run with Edge and temporary isolated profiles.
The final full run exited 0: browser regression PASS, encrypted storage PASS,
security UI PASS (143 assertions), virtual passkey PASS (32 assertions), and
household authority PASS (103 assertions). The authority drill exercised
Adult and Limited admission, direct-HTTP denial for Limited trust operations,
history entitlement, member removal, Temporary expiry, device revocation,
committed-epoch/B-002 recovery, KARC export/clean-profile restore/reapproval,
and two-client offline event reconciliation without duplicates.

The first full browser run exited 1 after the household authority script failed
at its rendered-fingerprint equality assertion during Limited admission
(profile C), after Adult admission passed. A separate rerun of that drill passed
all 103 assertions, and a second complete `npm run verify:browser` also passed
all 103. The first failure was not reproduced; no product defect was confirmed.
Keep the initial failure visible as a transient test observation rather than
counting the first run as a pass.

The drill's offline control is browser-level automation against the local relay;
it is not OS-level or physical-network disconnection. Its fingerprint check
compares rendered strings across profiles; it does not count as human
fingerprint verification.

### 4. Installed-PWA tests — NOT RUN

No installed-PWA lifecycle was exercised. Browser tabs and the browser
regression runner do not count as installation. Cache upgrade consistency,
offline installed launch, interrupted update recovery, and update while local
data exists remain manual gates.

### 5. Physical-device tests — NOT RUN

No independent physical devices or human participants were used. Do not infer
physical-device, mobile-browser, or hardware-passkey validation from these
results.

### 6. Cross-network tests — NOT RUN

All service/browser exercises used a local relay on one host. Separate LANs,
internet paths, and real network loss/reconnect were not exercised.

### 7. Human fingerprint-verification tests — NOT RUN

The browser drill verifies that separately rendered fingerprints match and
that product actions enforce confirmation state. No person compared values
between devices or completed a real passkey ceremony in this audit. The passkey
suite used a Chromium virtual authenticator.

## Defects and disposition

### No newly confirmed release-blocking defect

The initial Limited-admission fingerprint assertion failure did not reproduce
in the dedicated drill or the full browser-gate rerun. No fix was made and no
regression test was added for an unconfirmed product failure.

### P-005 — approval button visual state (known, nonblocking)

The browser drill again reported that “Approve with passkey” was not visually
disabled before fingerprint confirmation for several invitation profiles.
The application handler refuses approval without confirmation and the drill
asserted that refusal before proceeding. This is a visual/usability defect,
not an authorization bypass; it remains open and was not changed in this
evidence-focused patch. The existing record and behavior are described in
[`LIVE_HOUSEHOLD_VERIFICATION.md`](LIVE_HOUSEHOLD_VERIFICATION.md).

### Accepted threat-model limitation

Preserve R-3 from the prior audit: recovery relies on an honest relay for
revocation/session enforcement and committed-epoch recovery markers. This
milestone did not redesign signed commit records and makes no claim against a
compromised relay.
