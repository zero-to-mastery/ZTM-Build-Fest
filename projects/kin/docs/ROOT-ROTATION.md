# Local root rotation contract v1

Frozen for the v0.10.2 implementation before code changes. This contract changes
local protection only; canonical events, transport keys, sync epochs and KARC v1
framing retain their published meanings.

An explicitly confirmed replacement recovery key and an independent CSPRNG
256-bit root establish root version N+1 for the same vault. The recovery secret
is never persisted or transmitted. The candidate wrapper is unwrapped and its
verifier authenticated before staging. Existing PRF wrappers are retired; users
must re-add passkey unlock with a fresh verified PRF ceremony afterward.

New roots use manifest format 2 and authenticated root-version context. Legacy
format 1/root 1 remains readable with its unchanged cryptographic encoding.
Every normal storage open, transaction and manifest mutation compares the live
vault identity, root version, configuration revision where applicable, and durable
lock epoch. A copied older manifest cannot replace a newer manifest through Kin.
Complete hostile rollback of all site data remains outside this guarantee without
an independent monotonic witness.

The existing `security_state` key/value stores accommodate explicitly versioned
per-record staging; event DB 3 and key DB 4 need no structural upgrade. One Web
Lock (`kin-security-migration`) serializes migration/rotation operations. A CAS
changes the event singleton from `encrypted` to `root-rotating`, increments its
lock epoch, and records journal version 1, random rotation ID, vault identity,
source/target root versions and source/candidate manifests. Peer tabs lock. Normal
event and key transactions reject a rotating marker. Key staging first fences
the key database in a transaction serialized after prior key writes.

Only the candidate root encrypts a transitional copy of the source root, bound
to the rotation ID. The source root never wraps the candidate. Thus restart can
unlock the same candidate using the newly saved recovery key and resume without
generating another candidate; the old corpus remains intact before publication.
Staging encrypts complete records from every event and key store. It decrypts and
compares every value, including exact canonical bytes, restores device private
serializations and epoch keys, checks trust pins, and performs complete Rust replay.
No household epoch or transport key is regenerated by this operation.

Journal progress distinguishes preparing/staging, staged, verified, commit pending
and cleanup. Every batch and committing transaction checks operation ownership and
the durable lock epoch. Failure before event publication preserves the source.
After verification, a single event-database transaction replaces the event corpus
and manifest with the candidate, marked `root-cleanup`. Old wrappers and the source
root bridge are removed from the authoritative manifest. An idempotent key commit
then replaces protected key rows atomically. Finally staging is removed and the
event manifest becomes `encrypted`. Until both databases agree, ordinary household
access remains unavailable; unlock resumes cleanup with the candidate recovery key.
This is journalled cross-database publication, not one IndexedDB transaction.

The new root cannot be recovered from an old copied recovery wrapper and its
secret. After successful cleanup, those old capabilities cannot decrypt newly
protected data. Rotation cannot erase plaintext, keys, old archives, or transitional
source-root material already copied by an attacker; a compromised unlocked browser
can still access its authorized plaintext and keys.

Archive recovery is intentionally local-only (Option A). It recovers household
history, creates fresh anonymous local identities, and grants no membership,
trusted-device authority or sync reattachment. A future rejoin would require a
separately authorized workflow. The planned v0.13 recovery line must settle the
long-term archive authority policy; until then the implemented boundary remains
local-only. The v0.14 UX line must reflect the resulting policy.
