## Objective and scope

Capture “This matters. We can come back to it at a better time.” Add a dedicated short Talk topic, open/resolved lists, resolve, reopen, and terminal archive. Preserve Today/Needs, Handoff, and all canonical event bytes. Resolved is only workflow state: it asserts no agreement, objective solution, correctness, responsibility, partner confirmation, or end to conflict.

## Non-goals

No chat, comments, replies, threads, transcripts, history browser, editing, restore, notifications, reminders, scheduling, due dates, recipients, assignment, voting, reactions, decisions, compromise/boundary forms, emotion labels, sentiment, advice, counseling, AI, scores, blame, analytics, response metrics, named verified identity, pairing, auth, sync, backend, encryption, Pulse, summaries, or routines. No runtime framework/dependency.

## Domain and lifecycle

`TalkId` is a distinct typed ID. `TalkState` contains only talk_id, exact text, created_by and created_at from the add envelope, and `TalkStatus` (Open, Resolved, Archived). Resolution provenance remains in immutable envelopes. `HouseholdState` has separate ordered items, handoffs, and talks; each retains original add-event order. UI shows newest additions first within each Talk group.

| Current          | Intent                 | Result                                      |
| ---------------- | ---------------------- | ------------------------------------------- |
| absent           | add                    | open                                        |
| open or resolved | resolve                | resolved; repeated resolve is a valid no-op |
| resolved or open | reopen                 | open; repeated reopen is a valid no-op      |
| open or resolved | archive                | archived tombstone                          |
| absent           | resolve/reopen/archive | domain error                                |
| archived         | any ordinary mutation  | domain error                                |
| existing ID      | distinct add           | domain error                                |

Exact duplicate event delivery is idempotent; conflicting event-ID reuse is an integrity/domain error. Invalid replay returns no partial projection. Archive retains every source event and hides the topic from normal lists.

## Events and schemas

Codes 1–7 and their schemas remain unchanged. All Talk events use schema 1:

| Code | Kind          | Exact payload                            |
| ---- | ------------- | ---------------------------------------- |
| 8    | TALK_ADDED    | talk_id[16], text_length:u32, UTF-8 text |
| 9    | TALK_RESOLVED | talk_id[16]                              |
| 10   | TALK_REOPENED | talk_id[16]                              |
| 11   | TALK_ARCHIVED | talk_id[16]                              |

Text is strict UTF-8, 1–4096 bytes, not whitespace-only. Preserve Unicode and whitespace exactly. No envelope metadata is duplicated in payloads. Existing household consistency, logical ordering, identity and immutable-byte rules apply.

## Protocol compatibility and Rust projection

Protocol v4 requests use the unchanged 12-byte KINE header and 88-byte event envelope, with explicit version 4. All integers are little-endian. Limits remain 10,000 events/entities and 64 MiB request/result. Exact lengths, zero reserved bytes and strict UTF-8 are required.

KINS v4 header (20 bytes): magic[4], version:u16=4, reserved:u16=0, item_count:u32, handoff_count:u32, talk_count:u32. Serialize all v2-layout Items, then v3-layout Handoffs, then Talks. Combined entity count is at most 10,000.

Talk record (48 fixed bytes plus text): talk_id[16], created_by[16], created_at:i64, status:u8 (0 open, 1 resolved, 2 archived), reserved[3]=0, text_length:u32, text[N]. Empty v4 result is 20 bytes. KERR remains v1 with unchanged error categories.

Protocols v1/v2/v3 retain their exact published layouts and event support. They reject Talk events or any Talk state, including tombstones, with unsupported-version category 3; never return a lossy partial view. Browser calls use v4. Rust alone owns decoding, text/lifecycle validation, duplicate/reference handling, mixed replay, ordering and serialization.

## Browser, storage and draft ownership

`kin-talk-list` owns one labeled input, semantic Open/Resolved lists and native action buttons. Commands bubble and are composed: `kin:add-talk { text }`, `kin:resolve-talk { talkId }`, `kin:reopen-talk { talkId }`, `kin:archive-talk { talkId }`. KinApp orchestrates canonical storage, Rust replay, busy states, feedback, focus and retry. JavaScript does not decide transition validity.

IndexedDB remains schema 1: no structural change or migration. Candidate replay occurs within the existing atomic event/counter write transaction. Invalid candidates append nothing. BroadcastChannel remains exactly `{ type: "events-changed" }`; peers reload canonical events and replay in Rust.

Best-effort tab draft `kin.talk.draft` is independent of compose and Handoff drafts. Successful completion clears only the submitted draft snapshot if it still matches. A failed add retries the original text; newer text survives retry/delayed completion. Reconnect cannot unlock or restart an in-flight save. SessionStorage denial cannot block capture.

## Retry and recovery

Reuse existing failed-command and suspended-retry infrastructure. Transaction abort/quota failure retains prior state and retry. Refresh failures, including repeated failures, suspend the original command until canonical reload/replay succeeds. Recovery never automatically appends. New commands supersede suspended retries. Stale actions are validated against canonical events in Rust inside the write transaction, including when invalidation was missed; invalid actions append nothing and trigger refresh. Missing/archived projections clear unavailable retries.
