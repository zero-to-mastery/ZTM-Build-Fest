# v0.2.0 — Today + Needs

**Status:** Current through v0.7.4 Routine Stale-Action Correctness; frozen capability contract for the v0.2.x release line. v0.2.0 implements the behavior below; stabilization work is tracked separately in v0.2.1–v0.2.3. The preceding v0.1.x contract remains historical and its persisted events remain readable.

## Objective

Answer “What matters today, and what does our household need?” with two lightweight views and a short capture path. Kin remains a local household coordination tool, not a general task manager.

## Scope

- Today and Needs views, each showing active and completed items of its classification.
- Capture short text with a native classification control. New items default to Needs; choosing Today takes one additional control action.
- Complete, reopen, and archive items through immutable events.
- Rebuild all item state deterministically in Rust from the canonical IndexedDB event stream.
- Preserve v0.1.x event bytes and make every compatibility normalization explicit.
- Keep capture drafts resilient to delayed, failed, retried, and older operations.
- Keep the existing native Web Components, browser APIs, manual WASM boundary, and dependency policy.

## Non-goals

No Handoff, acknowledgement, Talk, Pulse, Since You Last Looked, routines, recurrence, due dates, calendar, reminders, priorities, arbitrary tags, projects, subtasks, assignees, scoring, editing history, activity surveillance, accounts, real member identity, authentication, passkeys, pairing, remote storage, backend, sync, encryption, cloud APIs, analytics, household-content telemetry, AI runtime, framework, or new runtime dependency. Archive is a tombstone; a full archive-management or restore product is not included. `v0.3.0 — Handoff` remains future work.

## Classification

The complete classification set is `Today` and `Need` (shown in the UI as **Needs**). It is a fixed domain enum, not user-managed categories, labels, or tags. New capture defaults to `Need`. The native control offers the one-step choice of `Today` without a wizard or separate page.

An `ITEM_ADDED` event with legacy event schema v1 has no classification. Its normalized current classification is `Today`, matching the single visible Today list in v0.1.x and preventing an existing item from disappearing or unexpectedly moving after upgrade. Its original bytes are not changed. New instances write schema v2 `ITEM_ADDED` events with an explicit classification.

## Event and transition contract

Event envelope fields, ordering, identity, idempotency, and immutable-byte rules remain as defined in [EVENTS](EVENTS.md). Event kinds retain these numeric protocol codes: `ITEM_ADDED = 1`, `ITEM_COMPLETED = 2`, `ITEM_REOPENED = 3`, and `ITEM_ARCHIVED = 4`.

| Kind             | Readable event schema | New writer | Payload/behavior                                                                                                                                        |
| ---------------- | --------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ITEM_ADDED`     | v1 and v2             | v2         | v1: item ID + text length + UTF-8 text; normalize to `Today`. v2: item ID + classification byte + three zero reserved bytes + text length + UTF-8 text. |
| `ITEM_COMPLETED` | v1                    | v1         | Item ID; active becomes completed, completed is a valid no-op.                                                                                          |
| `ITEM_REOPENED`  | v1                    | v1         | Item ID; completed becomes active, active is a valid no-op.                                                                                             |
| `ITEM_ARCHIVED`  | v1                    | v1         | Item ID; active or completed becomes archived.                                                                                                          |

Classification payload values are `0 = Today` and `1 = Need`; other values and nonzero reserved bytes are malformed. Text remains strict UTF-8, 1–4096 bytes, and is never rewritten in storage. New instances use protocol v2 for all engine calls, write schema v2 only for `ITEM_ADDED`, and write schema v1 for the other three event kinds. Unsupported event versions and kinds fail closed.

The complete item transition matrix is:

| Current state       | Event                        | Result                                               |
| ------------------- | ---------------------------- | ---------------------------------------------------- |
| absent              | add                          | active item with event classification                |
| active              | complete                     | completed                                            |
| completed           | complete                     | completed; valid no-op for a distinct event identity |
| completed           | reopen                       | active                                               |
| active              | reopen                       | active; valid no-op                                  |
| active or completed | archive                      | archived tombstone                                   |
| absent              | complete, reopen, or archive | deterministic domain error                           |
| archived            | complete, reopen, or archive | deterministic domain error                           |

An exact duplicate event delivery is deduplicated by event identity and identical canonical bytes. Reusing an event ID with different bytes is an integrity/domain error. Invalid replay produces no partial state and storage appends nothing. Archived items remain in the Rust projection to enforce terminal state, but are omitted from Today, Needs, and completed UI lists. Archive never deletes or edits source events.

## ABI and protocol versions

Application, event, ABI/protocol, and IndexedDB versions are independent. Protocol v1 remains byte-for-byte unchanged: its reserved bytes remain zero, it accepts the original v1 event kinds/schemas, and it emits the original active/completed result representation. It does not reinterpret v1 reserved bytes as classification or a new status.

Protocol v2 uses the same `KINE`/`KINS` signatures, 12-byte outer headers, 88-byte event envelope, and 48-byte item record size, but has its own explicitly versioned payload/result interpretation:

- Requests accept event schemas/kinds in the table above. The event envelope layout remains the existing 88-byte layout.
- A v2 `ITEM_ADDED` payload is `item_id[16] | classification:u8 | reserved[3]=0 | text_length:u32 | text[text_length]`.
- A v2 result item is `item_id[16] | created_by[16] | created_at:i64 | classification:u8 | status:u8 | reserved[2]=0 | text_length:u32 | text[text_length]`.
- Result classification values are `0 = Today`, `1 = Need`; status values are `0 = active`, `1 = completed`, `2 = archived`.
- Protocol v2 retains little-endian integers, strict UTF-8, the 10,000-event and 64 MiB request/result limits, exact-length parsing, and fail-closed behavior.

The engine reads protocol versions 1 and 2. New browser instances write protocol v2 only. Protocol v1 output remains the historical shape; protocol v2 is required whenever the caller needs classification or archived state. Error categories remain stable and diagnostic text must not contain household content. Every protocol-v1 reserved byte continues to be validated as zero.

## Rust state shape

Rust remains authoritative for decoding, version normalization, validation, transitions, deterministic replay, and projection. The projection is equivalent to:

```text
HouseholdState
├── household_id
└── items: ordered by original ITEM_ADDED event
    ├── item_id
    ├── text
    ├── created_by
    ├── created_at
    ├── classification: Today | Need
    └── status: Active | Completed | Archived
```

Use Rust enums for classification and status. Replay depends only on the ordered event bytes; it does not depend on wall-clock reads, random values, the DOM, network, or unordered-container iteration.

## Browser commands and components

JavaScript owns DOM, native controls, command/event construction, IndexedDB, sessionStorage, BroadcastChannel invalidation, WASM loading, rendering, focus, and busy/error presentation. It does not implement a second reducer or decide transition validity. Browser intents remain minimal:

```text
kin:add-item       { text, classification: "today" | "need" }
kin:complete-item  { itemId }
kin:reopen-item    { itemId }
kin:archive-item   { itemId }
```

The submitted add command captures text and classification together. Draft persistence keeps the existing text key readable; classification may use a separate tab-scoped key, with missing/unknown values defaulting to `need`. Completion of an older operation may clear only the exact text-and-classification snapshot it submitted. Retries reuse that original command and must not overwrite or clear a newer draft.

Reuse `<kin-app>`, `<kin-compose>`, `<kin-item>`, and the Today presentation where responsibilities remain coherent. Add a Needs view only where it clarifies presentation. Item components dispatch intent and do not own authoritative transitions. Use native labeled controls and semantic buttons; archived items do not appear in ordinary lists.

## Storage compatibility

IndexedDB schema remains version 1: no object-store, key, index, or structural record change is required. Persisted event bytes are immutable. The storage adapter validates row metadata against exact canonical bytes, accepts supported event schemas/kinds, and gives Rust the ordered canonical bytes for replay. Unknown newer or malformed events fail closed and remain stored. Do not clear, rewrite, skip, or silently migrate source events. `local_sequence` and the event/context counter continue committing atomically in one transaction. BroadcastChannel continues to carry only a content-free `events-changed` invalidation; peers reload canonical IndexedDB data and ask Rust to rebuild.

## Accessibility and interaction requirements

- Preserve the short `focus, type, submit` path; classification is one native, labeled control with Needs selected by default.
- Today and Needs have clear semantic headings and keyboard-operable navigation/actions. State is not conveyed by color alone.
- Complete, reopen, and archive controls have visible, understandable labels and usable touch targets; archive is not a tiny icon-only action.
- Maintain labels, logical focus order/restoration, visible focus, polite success/busy announcements, assertive error feedback, and no false success on failure.
- Preserve draft intent through failure/retry and same-tab reload where storage permits. A blocked `sessionStorage` must not block capture.
- Support reduced motion, forced colors, increased text spacing, zoom, and narrow reflow including 320 CSS pixels without horizontal page overflow.
- Render household text with safe text APIs. Screen-reader support is tested only where the environment is actually available; do not claim certification without testing.

## Acceptance tests

The v0.2.0 release gate covers at least:

- Replay of realistic v0.1.x history with exact source-byte preservation; schema-v1 items normalize to Today and mixed supported versions replay deterministically.
- Protocol-v1 compatibility and reserved-zero behavior; protocol-v2 classification/status encode/decode and unsupported-version failure.
- Needs default capture, Today capture, classification persistence/reload, keyboard submission, and fast one-control classification selection.
- Completion in either view; reopening; archive from active and completed; archived items hidden after reload while history remains in IndexedDB.
- The full lifecycle matrix, unknown references, invalid transitions with no append/partial state, duplicate delivery, collision behavior, logical ordering, Unicode, and deterministic repeated replay.
- Draft restoration/clearing and the v0.1.5 ownership invariant extended to text plus classification across delayed save, failed add, edit, retry, reconnect, and peer refresh.
- Two-tab convergence by canonical IndexedDB reload; BroadcastChannel message contains only the invalidation marker.
- Safe rendering of script-like text, CSP, same-origin-only requests, no framework/runtime dependency, and privacy-safe errors.
- Keyboard/focus/busy/error behavior, 320px reflow, target sizing, forced colors, increased text spacing, reduced motion, and 200% zoom where available.

The release line must also continue the v0.1.x Rust, bridge, browser, persistence, malformed-row, storage-abort, and network regressions; new coverage extends rather than replaces old cases.
