# v0.1.0 — Household Heartbeat

**Status:** Current through v0.7.4 Routine Stale-Action Correctness; implemented as the first functional Kin release. Specification Freeze A was recorded at v0.0.9; v0.0.10 through v0.0.12 added documentation only. This document remains the v0.1.0 implementation and acceptance contract.

## Objective and user story

Prove the smallest complete local event-driven household loop. A user can open Kin, add one household need, see it, complete it, reload the browser, and see the same state reconstructed from stored events.

```text
open Kin -> load WASM and IndexedDB -> Rust replays events -> render items

add item -> ITEM_ADDED -> Rust validates/reconstructs -> persist event
complete item -> ITEM_COMPLETED -> Rust validates/reconstructs -> persist event
reload page -> Rust replays persisted events -> same state rendered
```

Only render a changed state after the candidate event has been accepted by Rust and its event record has committed to IndexedDB. On storage failure, preserve the prior view and report failure; do not claim the action was saved.

## Scope

### In scope

- Rust compiled for `wasm32-unknown-unknown` with deterministic validation and replay.
- One native `<kin-app>` custom element, with only focused child elements where they clarify responsibility.
- A manual, versioned JS/WASM ABI with documented memory ownership.
- Versioned event protocol using stable event, household, actor, device, and item identities; all household/member/device values are local placeholders.
- Exactly two domain events: `ITEM_ADDED` and `ITEM_COMPLETED`.
- IndexedDB event persistence; Rust derives state from the ordered event log.
- Add and complete a short-text item, refresh, and reconstruct.
- Local-only operation with no household-content network requests.
- Rust domain tests, ABI tests, and browser-level validation per [TESTING](TESTING.md).
- Semantic, keyboard-operable, narrow-screen UI meeting [ACCESSIBILITY](ACCESSIBILITY.md).

### Out of scope

- Handoff, Talk, Pulse, routines, Agreements, Today/Needs classification beyond the simple item view, and Since You Last Looked.
- Reopen, archive, delete, due dates, assignment, priority, labels, projects, and recurrence.
- Accounts, real household/member identity, partner login, passkeys, WebAuthn, pairing, QR codes, device trust, and revocation.
- Content encryption, household keys, Web Crypto for content cryptography, backend, sync, remote networking, conflict resolution, and notifications. The browser's `crypto.getRandomValues` may be used only to generate collision-resistant local event IDs; it does not provide encryption or authentication.
- AI runtime, household-content AI processing, analytics, tracking, relationship features, or a general calendar/task manager.
- Frameworks, external runtime libraries, or convenience WASM bindings without an explicit later architecture decision.

## Responsibilities

### Rust/WASM

Rust owns the event envelope parser, event validation, `ITEM_ADDED` / `ITEM_COMPLETED` semantics, deterministic reconstruction, and encoded state/error result. It receives the complete ordered event stream for each call and keeps no authoritative hidden state between calls. Rust must not access the DOM, IndexedDB, browser lifecycle, WebAuthn, Web Crypto, or networking.

### JavaScript/browser

JavaScript owns WASM loading/bridge, IndexedDB schema and transactions, temporary local IDs and event creation, UI commands, browser-native custom events, rendering, accessibility interactions, and error/loading presentation. It must not duplicate Rust's authoritative reducer.

### Components

`<kin-app>` orchestrates module/storage initialization and the validate-then-persist command flow. `<kin-today>` displays the Rust projection, `<kin-compose>` dispatches an add intent, and `<kin-item>` dispatches completion intent. Child components do not validate business rules or access storage. See [COMPONENTS](COMPONENTS.md).

## Event and replay contract

The only event kinds are `ITEM_ADDED` and `ITEM_COMPLETED`. Event names, payloads, identity fields, local append ordering, idempotency, and invalid-event outcomes follow [EVENTS](EVENTS.md). Local `local_sequence` order controls replay; timestamps are descriptive and never sort the v0.1.0 event log. The same valid ordered events must always yield the same state. Duplicate exact delivery is idempotent; conflicting ID reuse or an unknown item completion fails deterministically.

## Protocol and storage

Use the bounded, versioned binary request/result format and explicit buffer ownership in [ABI](ABI.md). Unsupported versions and malformed input fail closed without partial output. IndexedDB schema, append/read transaction behavior, local placeholder identities, and migration boundary are in [STORAGE](STORAGE.md). IndexedDB stores events; Rust reconstructs state. There is no second authoritative mutable state store.

## Technical requirements

- Rust target: `wasm32-unknown-unknown`.
- Use native Web Components, vanilla JavaScript, HTML/CSS, and browser APIs.
- No `wasm-bindgen`, `web-sys`, `js-sys`, `serde`, `serde_json`, framework runtime, backend, or network dependency.
- Target the latest two stable major releases of desktop/mobile Chrome, Firefox, and Safari at implementation start; require modern WebAssembly, ES modules, Custom Elements, IndexedDB, and secure-context browser APIs as detailed in [IMPLEMENTATION](IMPLEMENTATION.md).
- Keep user-provided item text as data and render with safe text APIs, never executable HTML.
- Do not transmit household content; v0.1.0 has no backend, analytics, or third-party network requests. Local static assets may be served from the same origin.
- Follow [IMPLEMENTATION](IMPLEMENTATION.md), [ABI](ABI.md), and [STORAGE](STORAGE.md).

## Test and accessibility requirements

All Rust, ABI, replay, browser persistence, safe-rendering, network, console, keyboard, status-announcement, focus, zoom, and mobile checks in [TESTING](TESTING.md) and [ACCESSIBILITY](ACCESSIBILITY.md) are release requirements. No external test framework is required merely for convenience.

## Release gate

Do not tag v0.1.0 until every item is verified:

- [x] Rust unit tests pass, including add, multiple items, completion, unknown completion, duplicate delivery, deterministic replay, and protocol boundary cases (23 tests).
- [x] `wasm32-unknown-unknown` release build succeeds and the manual ABI matches [ABI](ABI.md).
- [x] Memory ownership, bounds, malformed input, unsupported versions, zero-length input, stale frees, output reset, and repeated-call behavior pass Rust and runtime smoke checks.
- [x] No external runtime library or framework has been introduced; Cargo has no dependencies and there is no npm dependency tree.
- [x] IndexedDB append/read survives refresh and stores events rather than authoritative derived state.
- [x] Rust reconstructs state from the persisted event log; add and complete work end to end.
- [x] Repeated reload/replay yields the same state without duplicate events, and invalid streams fail safely.
- [x] User-entered script-like text renders literally without injected markup; browser console and page-error logs were clean.
- [x] Requests were limited to the local application origin; no backend, analytics, third-party request, or household-content transmission exists.
- [x] Keyboard submission and completion, visible focus, native labels/status announcements, 48px completion controls, and 320px/360px/640px reflow were exercised.
- [x] README describes implemented behavior and identifies future features and local-storage limitations.
- [x] All changes remain under `projects/kin/`; the v0.1.0 release commit and annotated tag identify the validated state.

The implementation follows this contract. Browser validation was performed on Windows 10 x64 using the integrated VS Code browser (Code 1.139.1, Electron 43.6.0, Chromium 150.0.7871.250). Firefox, Safari, standalone Chrome, and assistive-technology testing were not performed; the browser support target is not a certification claim. Release verification and known gaps are recorded in [CHANGELOG](../CHANGELOG.md).
