# v0.11.0 — Durable Identity & Relay Foundation

**Status:** v0.11.7 implementation candidate; awaiting human review under
`kin-v0.11.7`. Earlier review tags through `kin-v0.11.6` remain unchanged.
These are not published product releases; the last published baseline remains v0.10.3.

## Prerequisites and boundary

- v0.10.x remains the compatibility/security baseline. Keep the minimum-
  knowledge service boundary, WebAuthn/member checks, device-key validation,
  canonical event bytes and encrypted-envelope protocol.
- The service coordinates identity, authorization, opaque relay delivery,
  provisioning and key-epoch state. It is not a household source of truth:
  clients alone retain plaintext semantics, content keys and canonical replay.
- The service must not decrypt, parse, project, index or score household event
  content. Server schema changes do not change event, WASM, IndexedDB, envelope
  or archive versions.
- Keep the built-in HTTP listener on loopback. External access requires a
  configured HTTPS origin and a trusted TLS-terminating reverse proxy.
  Forwarded headers are untrusted unless a separately reviewed allowlist is
  introduced.

## Persistence responsibilities

Persist only information needed to authorize, route, deduplicate, sequence,
coordinate or recover accepted opaque service state:

- household identity/version and historical membership, including removed
  members;
- credential IDs, member ownership, public verification key, algorithm,
  signature counter and required WebAuthn metadata;
- trusted-device identity, member/household relation, public sync keys,
  fingerprint/key-transition history, history entitlement, provisioned epoch
  metadata, trusted/revoked timestamps and the device-token verifier;
- encrypted event canonical bytes, event identity, household/device identity,
  device sequence, persistent relay sequence, key epoch and required cursor
  high-water state;
- encrypted identity-binding envelopes and their idempotency identity;
- current key epoch, rotation-required state, accepted proposal identity and
  the coordination metadata required to reject stale/conflicting proposals;
- unexpired provisioning grants and request-idempotency records needed to
  recover an accepted request whose response was lost;
- bounded, security-focused audit records when they are committed with an
  authorization change.

Retain inactive members and revoked devices as historical authorization state.
Enforce unique IDs, foreign-key relationships, one credential owner, household
membership consistency, the two-active-adult limit, trusted-device limit,
event-ID uniqueness and per-device sequencing in service logic and storage
constraints where practical.

### Explicitly non-persistent or restart-discarded state

| State | Restart behavior | Reason |
| --- | --- | --- |
| Authenticated sessions | Expire on restart; persist no raw session token | Reauthentication with a passkey is a smaller security surface. |
| WebAuthn challenge/ceremony flows | Discard; require a fresh ceremony | One-time unauthenticated state must not become durable authority. |
| Unclaimed pairing codes, claim capabilities and partial claims | Discard | Restart safely cancels enrollment rather than reviving an incomplete authorization. |
| Request-local parsing/validation state and caches | Discard | Recomputed on a fresh request. |
| Process-local rate-limit windows | Reset on restart and remain bounded | A short reset may affect abuse throttling, never authorization; document the limitation. |
| Expired pairing/grant/session data | Reject by absolute server expiry; clean up boundedly | Process uptime must not extend a grant or ceremony. |
| Raw session/device/pairing/claim tokens and private keys | Never persist | Persist only required token verifiers and public key material. |

Active household/device trust is durable; an interrupted login or enrollment
ceremony is not. Pairing restart requires a newly authenticated invitation and
claim flow. Do not store raw WebAuthn challenge state, household plaintext,
content keys, device private keys, recovery secrets, PRF output or raw
authentication capabilities.

## Repository and backend selection

Domain services use a narrow repository/store boundary; SQL must not be
scattered through HTTP routes or authorization rules. Repository operations
must expose explicit transactions and bounded queries, and tests must exercise
the real selected store.

**Selection:** SQLite through `better-sqlite3` 12.4.1, with Node.js 22 or newer.
The v0.10 server already uses synchronous service methods and the API can commit
short local SQLite transactions before responding. SQLite supplies transactional
uniqueness/foreign keys, crash recovery, indexed bounded reads, schema migration
support and an online backup API without adding a network service. The package
metadata declares Node `>=22`. The checked-in Node 22.12 runtime exposes its own
SQLite binding only with an experimental flag; Kin therefore uses the maintained
SQLite driver rather than making the persistent contract depend on that
experimental API.

The tradeoff is one native Node addon (about 27 MB unpacked including its
distribution/build content) and platform-specific prebuilt/fallback compilation
requirements. Install via the project lockfile; verify supported Windows,
macOS and Linux runtime/architecture combinations in CI before claiming them.
No other server framework/ORM or distributed component is justified by Kin's
single-process self-hosted workload. SQLite uses foreign keys, WAL, a bounded
busy timeout and `synchronous=FULL`; backup uses SQLite's online backup API,
not a live-file copy.

The production listener takes an exclusive service lock beside the database,
so another Kin process cannot authorize from stale in-memory identity state.
Graceful shutdown releases the lock. If a process exits uncleanly, startup and
restore fail closed on the stale lock. Follow the explicit PID/process and
manual-removal procedure in [DEVELOPMENT](DEVELOPMENT.md#development-data);
never remove a lock while any service, backup or restore operation is active.

The active database, backup destinations and restore sources/destinations must
all remain outside the static `web/` root. Service startup and admin commands
share canonical path validation, including symlinked ancestors and directories
not yet created. Static serving also refuses symlinks escaping that root.

`npm run backup -- <destination>` uses SQLite's online backup API and verifies
the copied schema and records. `npm run restore -- <backup-file>` requires the
service to be stopped, validates the source, takes the service lock and
atomically replaces the configured database. A replaced database and any WAL
sidecars are preserved with a `.pre-restore-...` suffix. Backups and preserved
copies are sensitive. On platforms without POSIX permission support, access
control depends on operating-system and filesystem permissions.

Repository boundary: `PairingService` persists identity/credential/device
mutations through the identity repository, while `EncryptedSyncService`
persists sync coordination and opaque records through the sync repository.
HTTP handlers coordinate a shared SQLite transaction for cross-service
operations. SQL identifiers are static and every value is bound as a parameter.

## Server schema v1

The first implementation owns `PRAGMA user_version = 1`, independent of all
other version axes. Its normalized storage separates households, members,
credential ownership, trusted devices, sync household state, per-device
sequences, encrypted relay records, identity bindings, provisioning grants and
bounded security audit entries. Relationships and uniqueness are enforced by
SQLite constraints as well as the existing service validations. Ciphertext and
canonical-envelope strings are opaque values; no event payload decoding is
added.

Schema migrations run synchronously during store construction before the
listener is opened. A version newer than 1 or inconsistent migration metadata
prevents startup. Migration 0→1 is one SQLite transaction. The schema is not
silently reset or downgraded.

## Server persistent-schema contract

The server owns an independent integer schema version, initially `1`. It is
distinct from the Kin product version and every client/event/WASM/IndexedDB/
envelope/archive version. The concrete migration set, backend and version are
recorded here and in [VERSIONING](VERSIONING.md) before the persistent store is
used by the service.

Migrations run before listening for application traffic, are ordered and
transactional where supported, and preserve opaque event/binding bytes exactly.
They must preserve authorization meaning, reject malformed/unknown state and
refuse a database with a newer unsupported schema. They never silently discard
ciphertext or reinterpret unknown records. Interrupted migrations must either
roll back atomically or leave a verifiably recoverable state that can be safely
reopened. A failed migration prevents reads/writes through the service; it
does not fall back to empty in-memory state.

## Atomic mutation boundaries

One committed transaction must cover every durable effect of each logical
operation:

- household bootstrap: household, initial member, credential, trusted device,
  token verifier and audit event;
- pairing approval/member activation: membership, credential, device,
  confirmation state and audit event, if confirmation state is retained;
- same-member device approval: device/key certificate and related membership
  references;
- device revocation: revoked timestamp, session invalidation where applicable,
  rotation-required state, affected live grant invalidation and audit event;
- member removal/self-leave: inactive historical member, target device
  revocations, rotation-required state, affected grants and audit event;
- device-key transition: accepted transition/history and current public key;
- encrypted event push: event row and unique identity, relay sequence,
  per-device sequence and household high-water state;
- identity binding: opaque binding bytes and uniqueness/conflict state;
- epoch compare-and-advance: expected/current epoch check, exactly one accepted
  proposal, epoch update, recipient grant records and rotation-pending update;
- provisioning request, package submission and acknowledgement: grant state,
  stable request identity, opaque package/idempotency representation and
  device provisioned-epoch metadata;
- a security audit record tied to any authorization mutation above.

A failure before commit leaves none of that operation's durable effects. A
failure after commit but before the HTTP response is handled by the existing
idempotency/conflict contract. Do not report successful acceptance before the
commit returns.

Expected optimistic-concurrency failures (`sync_cursor_conflict` and
`sync_device_sequence_conflict`) roll back and return HTTP 409. They do not
indicate corruption or poison the store; refresh the cursor/device state and
retry. The sync service discards stale cached relay state after these conflicts.
SQLite failures and unexpected durable invariant failures retain fail-closed
behavior and HTTP 503; readiness remains unavailable until recovery.

## Acknowledgement and restart semantics

`DurableStore.validate()` is the shared startup, readiness, backup and restore
gate. It checks schema/migration metadata, SQLite integrity and foreign keys,
then validates all households in one read transaction. Startup runs this before
the listener can accept traffic. `/readiness` repeats it and returns only
`{"ready":false}` with HTTP 503 on failure; `/health` remains process liveness.
Semantic failure poisons durable authorization until explicit recovery/restart;
ordinary optimistic conflicts remain retryable HTTP 409 responses.

Validation cross-checks provisioning routing/expiry columns against grant JSON,
binding and relay routing columns against canonical opaque envelopes, device
ownership/token/revocation columns against device JSON, and both directions of
credential/member ownership. It checks credential/key metadata, retained key
succession, at most two active adults, the shared trusted-device limit, epoch
and rotation metadata, grant packages/fingerprints, relay/device sequences,
counts/tails/high-water values, and bounded audit metadata. Inactive members,
revoked-device history and expired but consistent grants remain valid. Relay
history is scanned in indexed pages of at most 20 rows, within the existing
100,000-event household limit.

Backup validates both its source and copied database before publishing the
backup; restore validates the source read-only before replacing its target.
Neither silently repairs or skips inconsistent records. These checks detect
inconsistent persisted state; they do not cryptographically authenticate the
whole database against a privileged attacker or inspect household plaintext.

An acknowledged encrypted event is **durably committed** only after the
configured store's transaction commits under its documented local-storage
durability settings. It is not a claim of recipient delivery/read, backup,
replication, semantic validity or protection from storage hardware/filesystem
failure. The service may return durable success only after commit.

Relay sequence is monotonically increasing and never renumbered on restart.
Identical `(household, event ID, canonical envelope)` retries remain idempotent;
same ID with different bytes is a conflict. Device sequence gap checks,
membership/removal, credential ownership, device revocation, key history,
rotation and provisioning decisions are reloaded from persistent authority
before authorizing requests.

Provisioning state that has been durably accepted and remains unexpired
survives restart with its stable request identity and exact opaque package
representation. Expiry is an absolute server timestamp; restart never renews
it. Challenges, sessions, unclaimed pairing/claim state and uncommitted request
state do not survive.

## Backup, restore and rollback limits

The chosen store must provide a supported transactionally consistent backup
mechanism; copying a live database file is not an acceptable backup procedure
when it can omit committed journal/WAL state. Backup/restore covers all durable
identity, authorization, relay and coordination state and preserves schema
version and ciphertext bytes. Backups are sensitive because they contain
identity/routing metadata and opaque encrypted envelopes. They contain no
household plaintext or content keys.

Restore requires a stopped service or the store's supported online mechanism,
validates schema/integrity before serving, and fails closed on corruption or a
newer schema. A stale backup can roll back revocation, membership, cursor or
epoch state unless a trusted client-observed high-water mark detects it. The
service must not claim general rollback protection or v0.12 retention/deletion
semantics.

## Deployment and operational contract

- Validate origin, loopback binding, data path, schema/store availability and
  security-sensitive configuration before listening.
- Never expose the database, journals or backups under the static web root.
  Use restrictive owner-only permissions where the platform supports them and
  document platform limitations; fail on an invalid/unusable path.
- Keep secrets out of source, logs and responses. Forwarded headers are not a
  source of trusted origin/client identity by default.
- Provide minimal liveness and readiness responses; readiness requires a
  structurally and semantically valid store. Responses disclose no path, SQL, secrets or stored
  data.
- Shutdown stops new work, lets bounded active transactions finish where
  possible, closes the store and exits deterministically. An interrupted
  request must not be represented as a committed success.
- Define backup/restore commands, data location, permissions, resource bounds
  and reverse-proxy/TLS expectations in operator documentation.
- Structured logs use bounded outcome codes and optional correlation IDs only.
  Never log request bodies, cookies, authorization capabilities, pairing codes,
  session/device tokens, private keys or encrypted envelopes by default.

## Resource and privacy boundaries

Keep request, batch, event, per-household, credential, device, grant,
binding, audit and rate-bucket limits bounded. Persistent cleanup is idempotent,
expiry-based, bounded per pass and cannot delete live authorization or accepted
relay state. Cleanup is operational garbage collection only; household-data
retention/deletion policy is deferred to v0.12.

The service can observe identity, membership/device relationships, event IDs,
epochs, timing, counts, cursors, network metadata and ciphertext sizes. It
cannot decrypt household event content or derive household semantic event kinds
from accepted encrypted envelopes. No plaintext event projection, search,
analytics, ranking, activity scoring, AI processing or content-key escrow is
introduced.

## Failure behavior and non-goals

Unavailable, full, corrupt or unsupported storage; migration failure; invalid
origin/path/configuration; failed transactions; backup/restore errors; and
shutdown during writes are explicit failures. Never fall back to volatile
success, silently reset the database, leak raw database errors, or discard
unknown ciphertext. Authorization must fail closed when durable state cannot
be read or committed.

This contract does not claim independent security audit, production
certification, zero knowledge, guaranteed availability, physical erasure,
global anti-rollback/transparency, cloud/distributed operation or deployment
support. It does not add household deletion/retention policy, all-device
recovery, UX redesign, new member roles or household-domain capability.

## v0.11.5 semantic-integrity evidence (2026-10-03)

SQLite structural checks previously allowed internally inconsistent Kin state
to reach service startup. The shared validator now enforces the persistence
invariants above before readiness, backup publication or restore replacement.
Mutation regressions retain SQLite integrity while contradicting normalized
grant/device/credential/envelope fields, membership/device limits, rotation
metadata, relay/device sequences or audit shape. They prove fail-closed startup,
coarse readiness HTTP 503 before household access, preserved liveness and valid
backup/restore. Live request/proposal/package grant IDs are also checked before
mutation, preventing malformed input from creating state the durable validator
would reject. Existing certificate encodings and historical authorization
records remain compatible. Server schema v1, sync envelope v1, client/domain
formats and the database backup format are unchanged.

The complete gate passed on Windows x64 / Node 22.12.0 / Edge 154.0.4258.53:
281 Node/real-WASM tests, including all 207 server tests and 100 new regressions;
118 Rust tests with Rust 1.93.0, formatting, warnings-denied Clippy and release
WASM; the complete product browser suite (13 named core scenarios and 25
reported scenario groups, no assertion total); 313 security-storage, 97
security-UI and 18 virtual-WebAuthn/PRF assertions. `npm ci` and `npm audit`
reported zero vulnerabilities. Version consistency and whitespace/Kin-only
checks passed. PowerShell and WSL Ubuntu 22.04 POSIX build/launcher checks
returned HTTP 200 for liveness, readiness, the page and exact WASM bytes.
WSL native Rust also passed 118 tests; the POSIX launcher used Windows Node,
so native Linux Node/addon and macOS deployments remain unverified. The existing
npm native install-script policy warning remains; the installed binding passed.

On Windows x64 / Node 22.12, three full validation samples on a synthetic
file-backed household with 32-byte opaque ciphertext measured 107/100/97 ms at
10,000 events and 1,169/1,137/1,175 ms at the 100,000-event limit. Reopening and
validating the latter took 1,193 ms. Events were populated through normal
service APIs; validation used indexed pages of 20 rows. These are local samples,
not a latency guarantee or worst-case payload benchmark. Readiness runs this
synchronous scan, so large databases can delay other work during validation.

The v0.11.5 candidate stops at durable semantic integrity. It adds no lifecycle
or deletion policy, recovery redesign, UX/UI capability, household role,
protocol, event-format or database-schema change. Validation detects internal
inconsistency, not coordinated database tampering by a privileged attacker.
