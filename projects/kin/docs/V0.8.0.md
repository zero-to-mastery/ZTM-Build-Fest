# Kin v0.8.0 — Household Pairing Contract (Planning Checkpoint)

**Status:** Implemented in v0.8.0; this document is the living record for the v0.8.x incubation line.

## Product boundary

v0.8.0 will make one local-first Kin household usable by two adult members on explicitly trusted devices. Pairing establishes identity and authorization; it does not add chat, roles, assignments, analytics, notifications, or a server-side household state. Existing Item, Handoff, Talk, Pulse, Routine, and summary semantics remain unchanged until a reviewed sync contract exists.

The first capability slice is: create a household, invite one member with a short-lived one-time pairing session, accept on a second device, register a passkey for the joining member, authorize that device, inspect trusted devices, and revoke a device. Member removal, recovery after losing every authorized device, encrypted event relay, and historical re-encryption remain separate decisions.

## Identity terminology

- **Household:** stable opaque identifier for one coordination space.
- **Member:** an adult identity in the household; membership is explicit and never inferred from event activity.
- **Device:** one browser/application installation authorized for one member; replacement creates a new device.
- **Credential:** a passkey/WebAuthn credential that authenticates a member; it is not a device key or household encryption key.
- **Pairing session:** short-lived, single-use enrollment state binding inviter, invitee device, household, and transcript.

These identities must not be collapsed into one ID or represented by display names as authority.

## Required flows

1. An authenticated existing member creates a household or starts an invitation.
2. The inviter displays a high-entropy, short-lived QR/code containing only session material.
3. The recipient scans or enters it; both devices bind the same session and verify a transcript fingerprint.
4. The recipient explicitly accepts, creates or selects a passkey, and names the device locally.
5. The authorized device receives only the access needed for the household protocol.
6. Either party can cancel; expiry, cancellation, failed confirmation, replay, and wrong-device entry grant no membership or content access.
7. An existing member can list and revoke a specific trusted device. Revocation blocks future authorization; it cannot erase copied plaintext.

Adding a device for an existing member is a separate flow and must not create a second member.

## Security and recovery gates

Pairing requires a reviewed cryptographic protocol using platform Web Crypto/WebAuthn primitives or a narrowly justified audited dependency. Kin must not invent a cryptographic primitive, derive household keys from passkey assertions, put a household key in a QR code, or claim end-to-end encryption before implementation and review.

Before code is released, decide and document: session expiry and entropy, server versus local rendezvous, transcript binding and human verification, rate limiting, credential replacement/revocation, lost-device recovery, last-device recovery, device-key storage, household-key provisioning, revocation key rotation, and what history a newly authorized device may receive. A pairing code is never recovery by itself.

## Architecture boundary

Browser JavaScript owns WebAuthn, Web Crypto, QR/code presentation, session lifecycle, network transport, IndexedDB integration, focus/visibility, and secret lifetime. Rust owns validation and deterministic replay of any approved identity/membership events; it never calls browser APIs or handles DOM/network state. A relay, if approved, carries authenticated opaque protocol data and never becomes the household domain reducer.

No existing event kind is renumbered or reinterpreted. The reserved conceptual kinds in `docs/EVENTS.md` (`HOUSEHOLD_CREATED`, `MEMBER_INVITED`, `MEMBER_JOINED`, `MEMBER_REMOVED`, `DEVICE_AUTHORIZED`, `DEVICE_REVOKED`) require frozen payload layouts, authorization rules, protocol version, malformed-input behavior, duplicate/conflict handling, and migration compatibility before implementation. Do not add them speculatively to v7 histories.

## Local-first and privacy requirements

Local household actions remain useful offline. Pairing metadata is minimized, secrets are never logged, and UI errors do not disclose whether a household or member exists. The relay may observe routing metadata and timing if one is introduced; encrypted payloads do not provide anonymity. Existing local-only releases must continue to open without an account or network.

## Acceptance before tagging v0.8.0

- Frozen identity, event, ABI, storage, authorization, and recovery contracts reviewed together.
- Threat-model and cryptographic review completed; no unsupported security claim.
- Browser/Rust responsibilities and secret ownership are explicit.
- Pairing-session expiry, cancellation, replay, wrong-device, duplicate, stale, revoked-device, offline, and retry matrices are tested.
- Existing protocol v1–v7 fixtures and local households remain valid.
- Accessibility covers keyboard operation, focus, status announcements, QR/code alternatives, timeout messaging, forced colors, narrow layouts, and no secret disclosure through accessible names.

## v0.8.0 implementation record

The implementation uses a small same-origin Node service because cross-device expiry, bounded attempts, authorization and atomic membership cannot honestly be enforced by a static page. The service keeps identity state in memory during this incubation release; restart is destructive to server identity state and is an explicit limitation, not a recovery mechanism. It never receives household event content.

- Codes use 40 bits from Node's cryptographic RNG, omit ambiguous letters, expire after ten minutes, are single-use, and are stored only as HMAC-SHA-256 verifiers.
- The state machine is `Pending -> Claimed -> Confirmed`, with `Pending|Claimed -> Expired|Revoked`; terminal transitions fail and confirmation is idempotent.
- WebAuthn verifies origin, RP ID hash, user-presence/user-verification flags, challenge freshness, credential ID, and ES256/RS256 signatures. A nonzero monotonic signature counter is an additional replay or cloning signal for authenticators that support it, not a universal guarantee for synced passkeys.
- An HttpOnly, SameSite=Strict opaque session binds member and trusted device. IDs are references, never authority by themselves.
- Claim creates only pending credential/device material. An authenticated existing adult must approve with a fresh passkey assertion before the member and device are inserted atomically.
- The household maximum is exactly two active adults. Pairing never discloses the inviter, member list, household content, or household identifier to an unapproved claimant.
- Trusted-device inspection and revocation are implemented. Revocation invalidates future service authorization but cannot erase local plaintext.
- Existing household events remain local. No content-key provisioning, encrypted sync, QR, backup, or last-device recovery is claimed.

Validation begins with `node server/pairing-service.test.mjs` and the existing Rust/Wasm/browser regression gates. Subsequent v0.8.x sections record hardening findings and evidence.

## v0.8.1 hardening record

Approval is atomic and idempotent, but no longer hands a session to the claimant. The claimant polls only privacy-safe state and, after confirmation, must complete a fresh WebAuthn assertion before activation. If the passkey is lost immediately after membership creation, the membership remains but the device receives no usable session; another trusted adult may remove that member in a later explicitly authorized flow, while self-service recovery is unavailable. Approval/revocation is serialized by the service state/version check, expiry always uses server time, a new invitation revokes an older live one, duplicate approval returns the confirmed result, and logout invalidates only the opaque session rather than device trust.

## v0.8.2 authorization and trusted-device record

The authorization primitive is an unexpired opaque session bound to an active member and a currently trusted device. A pairing code never authorizes an operation. Pairing approval and joining-device activation additionally require fresh WebAuthn assertions. Client visibility and UI state are never accepted as authorization.

| Operation             | Existing adult                                | Joining adult before approval            | Household adult after approval          |
| --------------------- | --------------------------------------------- | ---------------------------------------- | --------------------------------------- |
| Create pairing        | Active session on trusted device              | No                                       | Yes, only while household has one adult |
| Claim pairing         | Not applicable                                | Valid code plus new passkey registration | Not applicable                          |
| Approve pairing       | Active session, trusted device, fresh passkey | No                                       | Not applicable once household is full   |
| Revoke pairing        | Active session on trusted device              | No                                       | Yes for a live household pairing        |
| View trusted devices  | Yes                                           | No                                       | Yes after passkey activation            |
| Revoke trusted device | Yes; not the current device                   | No                                       | Yes; not the current device             |
| Leave household       | Only if another active adult remains          | No                                       | Yes; own devices/sessions revoked       |
| Remove other adult    | Yes; target must be the other active adult    | No                                       | Yes; target devices/sessions revoked    |

Credential removal is not exposed in v0.8.x because each member has exactly one enrolled credential and silent removal would strand identity. Logout deletes only the current session and does not change trust. Device revocation blocks future service authorization but does not remove membership or erase copied data. Membership removal revokes all known target devices and sessions. If every trusted device/passkey is lost, recovery is unavailable; pairing codes cannot recover access. Household deletion, credential replacement, key rotation and encrypted content provisioning remain out of scope.

## v0.8.3 pre-feedback record

### Final user journey

The initiating adult sets up a passkey-backed household, chooses **Pair another adult**, and receives a selectable eight-character code with a server-time expiry, Copy, Share, and Revoke controls. The joining adult opens `/pair` or an invitation URL, enters or confirms the code, names the device, and creates a passkey. The invitation then says that approval is pending without revealing household identity or content. The initiator sees the claimed device label and approves with a fresh passkey assertion. The joiner must finally prove the enrolled passkey to activate the trusted device. A lost response can be retried against server-authoritative state; a replay cannot create another member.

### Concurrency and failure behavior

One household has at most one live invitation and exactly two active-member slots. Service operations are synchronous atomic mutations; state and version checks serialize approve/revoke and stale approval. Confirmation inserts member, credential and device as one operation before marking the session Confirmed. Expiry is evaluated by the service at every transition. Duplicate approval is an idempotent Confirmed read, duplicate claim fails, and a code verifier is removed at confirmation/revocation. Audit events contain IDs and outcomes, never the code, credential private material, household content, or browser text.

### Accessibility and progressive enhancement

Manual entry is the baseline. URL prefill, Clipboard, and Web Share are enhancements with textual fallbacks; QR is unnecessary. Forms use native labels/inputs/buttons, logical DOM focus, visible existing focus styles, 48-pixel-class controls, text status in addition to color, assertive error and polite status regions, and a selectable monospace code. The countdown is visible but not a live region, avoiding per-second announcements; expiry becomes actionable text. The pairing surface adds no motion and retains forced-colors/reduced-motion behavior. The `/pair` route hides the household coordination surface before authorization. Automated reflow/forced-color/keyboard regressions pass, but NVDA, VoiceOver, Safari, Firefox, and native zoom remain manual validation gaps; no certification is claimed.

### Security assumptions and known limitations

The service is a local incubation server with in-memory identity state. Restart loses identities, sessions and audit history; it is not production durability. Use behind a single trusted origin and TLS outside localhost. There is no encrypted event sync, content-key delivery, database, backup, credential replacement, last-device recovery, household deletion, remote deployment hardening, attestation policy, key rotation, retroactive erasure, or QR. Pairing adds identity/authorization only; existing household events remain local to each browser and are not synchronized. A compromised authorized browser can read local content. WebAuthn verification is implemented, but independent security review and physical authenticator coverage remain required before production use.

### Regression boundary

Protocols v1–v7, event schemas, canonical event bytes, IndexedDB schema 1, Rust replay, and all v0.7.x features remain unchanged. The static browser regression harness returns an unauthenticated status response so legacy single-user behavior remains testable without inventing an account migration. The product intentionally permits existing local-only use at `/`; `/pair` is the protected enrollment route.

## v0.8.4 creation-response correction

The pairing creation endpoint now returns `state: "Pending"` with the code, identifier, expiry and version. The initiating UI previously assumed this documented state was present and called `toLowerCase()` on an absent value. An exact service regression covers the response contract, and the UI now renders a safe recovery message rather than throwing if a future response is malformed.

Button-specific colors and alert styling remain unchanged; authentication behavior and the v0.8.x product scope are unchanged.

## v0.8.6 Pairing Feedback-Gate Corrections

- Pairing codes use cryptographically secure rejection sampling over the 31-character ambiguity-reduced alphabet. Out-of-range 5-bit values are rejected, preserving uniform selection and the existing eight-character entropy (about 39.6 bits); a 512-code regression checks length, alphabet membership, and uniqueness.
- A `Pending` invitation expires after ten minutes. When claimed, the server resets its authoritative expiry to a separate 15-minute approval window. The joining and approving views use the current state deadline.
- Claim registration options validate the invitation before returning WebAuthn creation options. Validation reveals no household data, is rate-limited, and does not claim or consume the code; registration finish revalidates the code.
- Expired and revoked claims stop polling, clear their claim cookie/token after returning terminal status, and return the join UI to editable code entry. Reload follows the same recovery path. `/pair?code=...` captures the code and removes the query before status requests or WebAuthn work.
- Bootstrap and claim activation issue a separate opaque trusted-device cookie; only its hash is kept on the device record. Logout clears the session but retains device trust. Passkey reauthentication is restricted to the credential and active member associated with that trusted device, rotates the device token, and does not trust a new or revoked device.
- Removing another adult requires a fresh WebAuthn assertion. The two-minute, one-use flow binds actor, trusted device, and target member; the server checks credential ownership and atomically deactivates the target, revokes its devices, and removes its sessions. The session-only removal route fails closed.
- Auth cookies are `Secure` only when the configured `KIN_ORIGIN` uses HTTPS; localhost HTTP remains usable. TLS deployments must configure the externally visible HTTPS origin. Forwarded-protocol headers are not trusted to select cookie security.
- Registration/authentication flows and WebAuthn challenges expire after two minutes and are each capped at 512 active entries. Per-client rate buckets expire after one minute and are capped at 4096. Expired entries are pruned on access; active entries are retained and new work is rejected at capacity.

The service remains in-memory and same-origin. No QR, new household size, account recovery, content encryption, or cross-device household-data synchronization is added.

## v0.8.7 Pairing Security and State Hygiene

- Approval finish loads the asserted credential server-side and requires it to belong to the authenticated approving adult before WebAuthn verification or membership authorization. Unknown and another member's credentials share the same non-enumerating structured failure.
- Revoking a trusted device immediately removes every session bound to it. Repeating the revocation is safe and does not duplicate its audit event.
- Authenticated sessions are lazily pruned at their server-authoritative expiry. Confirmation resets a 15-minute activation deadline; expired claim capabilities and retained terminal pairing records are lazily collected.
- Malformed CBOR, COSE keys, authenticator data, client data and signatures produce controlled passkey verification errors rather than low-level runtime exceptions. Empty RSA key material is rejected explicitly.
- A nonzero monotonic signature counter remains an additional replay/cloning signal where supported, not a universal guarantee for synced passkeys. Successful login and activation continue to issue fresh session identifiers.

No pairing UX, household role, recovery architecture, QR, encryption, or synchronization scope is added. The patch is ready for human product feedback.

## v0.8.8 Active-Member Slot Correctness

Household capacity now counts active memberships rather than retained historical member records. After an adult leaves or is removed, the remaining adult may pair a replacement while Kin continues to preserve the inactive historical member record. Pairing creation and final approval both enforce the two-active-adult limit; a full-household approval fails before member, device, credential, session, household-version, or confirmation mutation.
