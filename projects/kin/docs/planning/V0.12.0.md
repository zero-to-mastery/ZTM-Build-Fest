## Lifecycle and authorization

```text
active
  |
  | active adult + fresh WebAuthn assertion
  v
deletion_pending  -- active adult + fresh WebAuthn assertion --> active
  |
  | 30-day deadline expires
  v
deleted (terminal)
```

- Either active adult may request deletion. The requester must authenticate
  again with that member's passkey. Both adults do not have to approve.
- The pending transition is committed to SQLite. Sessions are invalidated,
  pending pairing/claim flows are discarded, and all authenticated writes,
  sync, enrollment and membership changes are rejected immediately.
- Either active adult may cancel during the 30-day grace period from a trusted
  device using a fresh passkey assertion. Cancellation is a conditional
  transaction; it fails at or after the deadline.
- The service finalizes expired requests at startup, during API requests and
  on a one-minute maintenance timer. After finalization there is no recovery or
  cancellation.
- The household row remains as a minimal deletion tombstone (opaque ID,
  version, terminal state and deletion time). This is retained indefinitely:
  removing it would allow a restored older backup to erase the only local
  anti-resurrection record. Members, credentials, trusted devices, sessions,
  pairing state, key epochs, relay ciphertext, bindings, grants, cursors and
  household audit rows are removed at finalization.

This is a one-adult destructive authority model, matching existing fresh-passkey
authorization for sensitive membership changes. It does not claim both-adult
consent or erase copies already learned by either adult.

## Retention schedule

| Data class | Rule and reason |
| --- | --- |
| Active household, members, credentials, devices and sync state | Retained while active for authentication, routing and relay; membership/device revocation remains distinct from household deletion. |
| Pending deletion | Retain household authorization and encrypted relay records for at most 30 days so an adult can cancel; block all use immediately. Sessions and in-memory flows are invalidated at request time. |
| Finalized household | Purge member, credential, device, event, binding, grant, sequence/cursor, epoch and household audit rows at finalization. Retain one minimal household tombstone indefinitely to prevent local stale-backup resurrection. |
| Sessions and WebAuthn flows | Sessions are process-local, expire within 12 hours and are invalidated by deletion request; one-time flows expire within 2 minutes and deletion clears household flows. Restart discards both. |
| Pairing and provisioning state | Pairing capabilities are process-local and expire; deletion discards them. Provisioning grants expire after 10 minutes and are pruned during sync operations. Finalization removes all household grants. |
| Security audit | At most 10,000 rows globally; oldest rows are removed as new records arrive. Finalization removes records for that household. This is count-bounded, not a fixed time window. |
| Service backups | No Kin-managed inventory, age limit or automatic deletion. The operator controls backup locations and expiration. Backups can contain relay ciphertext and routing/authorization metadata. |
| Local IndexedDB and device keys | Not remotely erased by household deletion. Each reachable user must separately clear local Kin data; offline and inaccessible devices may retain plaintext, ciphertext and keys. |
| User-created encrypted archives and external copies | Outside Kin's control. They remain until their holder deletes them and may be recoverable with separately held secrets. |
| Temporary request/rate-limit state | Bounded process-local flows and buckets; expires or resets at restart. No household content is written to request logs. |

## Backup and restore

The restore command requires the explicit
`--acknowledge-deletion-history` option. When restoring over an existing
database, Kin refuses restore if any target household is `deletion_pending`.
The operator must cancel deletion using current valid household authority or
allow it to finalize first. This avoids restoring stale membership, device or
credential authority during the grace period; historical authority is not
merged. Active targets remain restorable. Existing finalized deletion
tombstones override stale active or pending backup states: a restored deleted
household stays deleted, and its old rows are purged and remain non-authoritative.

If the target database and its later deletion history are both missing, Kin
cannot infer deletions that happened after the selected backup. The explicit
operator acknowledgement warns about this limit; do not claim restore is
rollback-proof. Preserve the current database/deletion ledger when performing
recovery. A backup contains only the lifecycle state current when it was made;
it does not expire automatically. Kin cannot erase separately copied backups.

## Stale devices and local recovery

Pending/deleted writes fail server authorization, including uploads made with
old sessions, device cookies, cursors, keys or retry envelopes. The
`/api/household/lifecycle` endpoint lets a client with the opaque household ID
distinguish active, pending and deleted states without returning household
content. A sync client that detects pending/deleted state enters a terminal
non-retrying state and announces that the household can no longer sync.

Finalization invalidates membership and device records server-side, but cannot
remove data or keys from an offline browser. A pending deletion can be
cancelled; final deletion cannot. Restoring a local encrypted archive does not
restore server identity, membership or sync authority.

## Event growth and migration

Canonical encrypted relay history and identity bindings are preserved in full
until final household deletion. There is no compaction/checkpoint scheme.
Per-household event and binding limits remain hard rejection bounds, not
retention policies; once the event limit is reached, writes fail rather than
discard history. Service schema migration 1→2 adds explicit household
lifecycle metadata and insert guards. Event, sync-envelope, local IndexedDB and
portable archive formats are unchanged.

## Verification and limitations

Tests cover lifecycle transitions, fresh-auth HTTP flows, session/write
invalidation, grace cancellation/expiry, restart finalization, data purging,
schema migration, stale backup restore and lifecycle status responses.
Lifecycle behavior is not a legal-compliance certification, physical media
sanitization, cryptographic erasure of client keys, or proof that external
backups/devices have been deleted. See [RETENTION](../RETENTION.md),
[IDENTITY](../IDENTITY.md), [MIGRATIONS](../MIGRATIONS.md), and
[THREAT-MODEL](../THREAT-MODEL.md).

Windows x64 validation passed on Node 22.12, Rust 1.93 and Edge 154:
218 server tests, 74 browser-unit tests and 118 Rust tests; Rust formatting,
warnings-denied Clippy, release WASM, version consistency, the browser,
security-storage, security-UI and passkey runners, and isolated PowerShell and
POSIX (`run.sh` under Git Bash) launcher smokes all passed. The WSL-built WASM
artifact also passed browser-unit and core browser regressions. The WSL HTTP
launcher was not run because that distribution has no Node executable. Other
operating systems/browsers, physical authenticators, independent security
review and production certification remain unverified.
