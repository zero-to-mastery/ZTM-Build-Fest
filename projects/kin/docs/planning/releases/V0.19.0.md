# v0.19.0 — Shared Shopping Lists

**Target date:** 2026-10-10

**Status:** Implementation and validation complete on
`kin-fast-track-v0.16.3-v0.20.x`; this is an unpublished candidate, not
production certification. No tag is created on the batch branch.

## Goal

Make common shopping capture and completion fast, shared, and offline-friendly.

## Capability contract

- Add Shopping as Item classification code 2 and expose it as a dedicated
  list on the existing Lists page. Today and Needs remain unchanged.
- Reuse schema-v2 `ITEM_ADDED` and existing completion, reopening, and archive
  events. Do not create a second shopping entity, quantity/price model, or
  duplicate event stream.
- Add replay protocol 13. Protocols 1–12 reject Shopping-bearing history or
  projections rather than omit or remap the classification; their prior
  Today/Needs layouts and behavior remain unchanged.
- Persist through the existing encrypted local event store. Offline capture
  works locally and the existing encrypted household sync carries the same
  canonical events when connectivity is available. Existing KARC export/import
  also carries the canonical events.
- No IndexedDB, server database, event-kind, KARC, or sync-envelope migration
  is required. Histories with no Shopping Items replay unchanged.
- Retain the 4096 UTF-8-byte Item text limit, 10,000-event limit, and 64 MiB
  protocol bound. Use native labelled selection, semantic list headings,
  keyboard operation, and list focus restoration.
- No notifications, auto-purchasing, quantity tracking, prices, prioritization,
  assignments, or inventory inference are introduced.

## Product rule

Deliver one understandable household capability without making Kin feel like enterprise project management.

## Architecture constraints

- Preserve canonical event history and deterministic Rust/WASM behavior where the capability enters household state.
- Preserve local-first and encrypted-sync boundaries.
- Keep plaintext household semantics client-side.
- Define persistent-format migration before changing storage.
- Prefer native Web APIs and existing Kin abstractions.
- Do not add AI, scoring, surveillance, or hidden inference.

## Required implementation questions

- What new domain state or event is actually necessary?
- Can existing events/state represent the feature more simply?
- What happens offline?
- What happens across two devices?
- What happens after retry/restart?
- What does export/import do with it?
- Does member/device revocation affect it?
- What are the size/count limits?
- What is the migration from the prior supported version?
- What must be accessible by keyboard/screen reader?

## Validation evidence

Windows x64 validation passed with the pinned Rust toolchain, Node 22, and
Microsoft Edge: Rust tests, Node/real-WASM tests, formatting, warnings-denied
Clippy, release WASM build, Kin version consistency, and full browser
regressions. Browser coverage includes Shopping capture and list isolation,
completion/reopening/archive, local persistence, keyboard focus restoration,
and the existing layout/accessibility checks. No independent security review
or assistive-technology certification is claimed.
