## Goal

Add lightweight ordered substeps to actionable items while keeping capture fast.

## Capability contract

- Each Item supports at most 16 Step additions over its lifetime, including
  archived Steps. Step labels are trimmed plain text, 1–80 Unicode scalar
  values, no more than 256 UTF-8 bytes, and contain no control characters.
- Step IDs are stable 128-bit identities unique across the household. Steps
  remain in creation/replay order; there is no reordering, nesting, assignment,
  deadline, or separate schedule.
- Completing all Steps never completes the parent Item. Step changes require
  an active parent; completed Items must be reopened first. Parent archive
  preserves Step history. Step archive is terminal and does not free capacity.
- Protocol 11 adds event kinds 25–28 and appends a bounded Step result section.
  Protocols 1–10 preserve their exact layouts and fail closed when asked to
  interpret Step-bearing history. Existing histories need no synthetic events.
- Steps are ordinary canonical encrypted household events. They work offline
  through the existing append/retry and sync path; authority, device revocation,
  and key rotation remain unchanged. Server routing sees no Step plaintext.
- No IndexedDB, server, sync-envelope, portable archive (KARC v1), or canonical
  event framing migration is introduced. Existing export/import replay carries
  the new canonical events through the current adapters.
- The UI uses native checkboxes and a labeled short-text form. The disclosure
  exposes expanded state and an accessible progress summary; Step controls
  follow the parent Item lifecycle.

## Prerequisite

`v0.16.x` and all earlier platform prerequisites are genuinely complete.

## Product rule

Deliver one understandable household capability without making Kin feel like enterprise project management.

## Architecture constraints

- Preserve canonical event history and deterministic Rust/WASM behavior where the capability enters household state.
- Preserve local-first and encrypted-sync boundaries.
- Keep plaintext household semantics client-side.
- Define persistent-format migration before changing storage.
- Prefer native Web APIs and existing Kin abstractions.
- Do not add AI, scoring, surveillance, or hidden inference.

## Required implementation questions

- What new domain state or event is actually necessary?
- Can existing events/state represent the feature more simply?
- What happens offline?
- What happens across two devices?
- What happens after retry/restart?
- What does export/import do with it?
- Does member/device revocation affect it?
- What are the size/count limits?
- What is the migration from the prior supported version?
- What must be accessible by keyboard/screen reader?
