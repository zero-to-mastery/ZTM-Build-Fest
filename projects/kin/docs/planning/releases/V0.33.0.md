# v0.33.0 — Attachment UX & Lifecycle

**Status:** Implementation candidate in PR #30.

Attachments use the existing AES-GCM household key epochs and opaque authenticated relay. Capture validates JPEG, PNG, WebP, and PDF locally (up to 4 MiB), persists encrypted content before appending the canonical parent binding, and remains available offline. When sync is ready, trusted clients upload, retry, restore, and remove ciphertext. The server does not receive the plaintext parent identity.

IndexedDB schema 4 adds protected local attachment records. Household archives use format 2 and include protected local attachment rows. Export rejects an active binding whose bytes are not available locally, rejects damaged ciphertext by digest, and rejects local-sealed data that does not match the canonical parent. The existing 64 MiB archive limit still applies. Older format 1 archives remain importable when their event histories have no attachment payloads.

Parent archive retains attachment history and availability. Attachment removal commits the canonical removal first, then retries remote cleanup. Household deletion uses the existing deletion flow to purge relay data and protected local household storage. Parent relationships remain limited to Notes, Reference Records, Maintenance Records, and Items. Client reconciliation removes unbound local or remote objects and preserves removed bindings in household history.

The release candidate has native lifecycle tests, Rust replay coverage, WASM protocol coverage, and existing server/crypto regression suites. Full browser accessibility and end-to-end interaction checks are not available in the current environment and remain unverified.
