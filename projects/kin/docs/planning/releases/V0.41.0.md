# v0.41.0 — Mobile Experience & Passkey-First UX

**Candidate:** `kin-v0.41.0` candidate name on `feat/kin-v0.41.0-mobile-experience`, based on `origin/kin-development` at `3840741f36c6432ebe9ae6773a719916b7da897a`. Implementation candidate only: no tag, no release, no production certification, no physical-device evidence. The former "Backup Safety & Disaster Drills" v0.41.0 proposal is deferred as [BACKUP-SAFETY-DRILLS-PROPOSAL](BACKUP-SAFETY-DRILLS-PROPOSAL.md).

## Goal

Make Kin intuitive for a household member on a phone while keeping every
security, encryption, offline, and synchronization guarantee unchanged. The
audit that motivated each change is in
[V0.41.0-MOBILE-EXPERIENCE-PLAN](../V0.41.0-MOBILE-EXPERIENCE-PLAN.md).

## What changed

### Authentication and onboarding (`kin-security`, `passkey-unlock.js`)

- First visit: "Welcome to Kin" explains on-device encryption and the three
  steps (save a recovery key, create or join a household, turn on passkey
  unlock). `Set up protection` leads to "Save your recovery key" with a
  `Copy key` action and a confirmation field before encryption. Passkey-first
  describes everyday unlock; first-time cryptographic setup still begins with
  the recovery key required by the local-vault security model.
- Returning visit: "Welcome back" with `Unlock with passkey` as the single
  primary action whenever a PRF wrapper exists and the browser supports
  WebAuthn. `Use recovery key` reveals the recovery form; after a failed or
  cancelled passkey attempt the form is revealed automatically. Without a
  passkey wrapper the recovery form is shown directly with a hint that passkey
  unlock can be turned on after unlocking.
- Offline: the lock screen states that passkey unlock needs a connection and
  shows the recovery form; a network failure during a passkey attempt is
  reported as a connection problem, and a device without a household
  credential is told to create or join a household first. Error codes
  (`connection_unavailable`, `credential_unavailable`) are preserved.
- Settings (More → Privacy & continuity): passkey unlock status (On/Off/
  unavailable), `Turn on passkey unlock` or `Add another passkey`, per-passkey
  removal (the recovery wrapper can never be removed, as before), an
  automatic-lock preference (lock on close only, or additionally after 5/15/60
  minutes of inactivity; elapsed time while the page is suspended is checked
  before continuing; stored as a plain number in `localStorage`), recovery
  guidance, `Replace recovery key`, and the existing export/restore/persistent
  storage actions.
- Today shows an "Unlock faster next time" prompt once the device holds a
  household credential but no passkey wrapper; it runs the existing
  server-verified PRF enrollment.

### Household joining (`kin-household`, `kin-app`)

- A protected device without a household sees "How would you like to get
  started?" with `Create a household`, `Join an existing household`, and
  `Add this device to my existing membership`, each with a one-line
  explanation, plus `Log in with passkey` for a logged-out member. The panel
  explains that device protection (recovery key, passkey) and household
  membership (approval by an existing member) are separate.
- Create names the device and warns that someone who already uses Kin should
  join instead. Join and add-device show the same code form with path-specific
  instructions and state that entering a code never creates a second
  household. All three use the existing bootstrap, claim, fingerprint
  comparison, approval, and activation endpoints unchanged.
- Today shows a "Get started" card with the same three choices and a
  "Waiting for approval" card while a claim is pending.

### Classification and capture (`kin-compose`, `kin-today`, `kin-app`)

- The Today capture form defaults to Today and keeps the destination the
  person last chose instead of resetting to Needs after every add.
- Needs, Shopping, and Staples each carry one single-field capture fixed to
  that list ("Add to Shopping"); no dropdown. Each list has a one-line hint.
- Confirmations name the destination ("Added to Shopping.") and, only when
  this device actually syncs, add "It will sync when you're connected" while
  offline.
- Rust classification values, `kin:add-item`, event bytes, and search filters
  are unchanged. "Needs" keeps its product name; a rename to "To-do" is
  recorded as a follow-up decision rather than changed here.

### Attachment presentation (`kin-attachments`, `attachment-preview.js`, `kin-app`)

- Images render as bounded thumbnails (longest edge 192px, decoded once via
  `createImageBitmap`, falling back to the original blob where unavailable),
  requested only when the tile intersects the viewport. Tapping opens an
  in-app `<dialog>` viewer with the file name, `Close` (also Esc and backdrop
  tap), and `Save file`; focus returns to the thumbnail on close.
- PDFs and unrecognised files render as document tiles with kind, size, state,
  `Open`, `Save file`, `Retry` where applicable, and `Remove`.
- Previews are session-scoped object URLs held in memory by `kin-app`; they are
  revoked when an attachment is removed, when the viewer closes, and on lock.
  Rows now carry the validated MIME type. CSP `img-src` adds `blob:`; HTML
  and SVG uploads remain rejected by the existing MIME allow-list.

### Mobile interaction and messages (`kin-item`, `app.css`, `index.html`)

- Item rows show the text, a context line (area, planned date, responsibility,
  last changed), visible photos, one primary action, `Checklist` with its step
  count, and a `Details` disclosure holding the file control, responsibility,
  area, planned date, reminder, pin, and archive controls. Expanded state is
  remembered across re-renders.
- `viewport-fit=cover` and `interactive-widget=resizes-content`, header top
  safe-area padding, a fixed error card above the bottom navigation on narrow
  screens, full-width security and household actions on phones, and 48px
  minimum touch targets throughout.
- Sync pauses, offline, and attachment failures use plain language and never
  claim data was synced or deleted.

## Unchanged contracts

Rust/WASM remains authoritative; replay protocol, event schema, IndexedDB
schema, local envelope, security manifest, KARC, sync envelope, and server
schema are unchanged. PRF unlock still requires a server-verified assertion
with user verification and real 32-byte PRF output; recovery remains the only
offline unlock. No plaintext key or recovery material is written to web
storage (asserted by tests). Household authorization, member removal, device
revocation, Temporary expiry, B-002 committed-rotation recovery, and archive
restore boundaries are untouched; the household authority drill passes
unchanged.

The served-shell fingerprint is a deterministic hash of sorted relative paths
and file bytes (test files excluded); modification times are ignored. The
database-wide clear command is not part of v0.41.0; see the separate
[maintenance handoff](../../maintenance/DATABASE-CLEAR-HANDOFF.md).

## Known limitations and follow-ups

- Offline passkey unlock is not available; it would be a documented contract
  change (local challenge instead of server verification) and is deferred.
- P-005 (approval button visual state before fingerprint confirmation) is
  unchanged.
- The PDF viewer opens files in a new tab rather than inline; inline PDF
  rendering would require a `frame-src`/`object-src` CSP change.
- Renaming "Needs" to "To-do" was not done; the product vocabulary keeps
  "Needs" with a clearer hint.
