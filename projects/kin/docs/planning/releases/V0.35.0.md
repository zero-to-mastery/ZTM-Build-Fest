# v0.35.0 — More Adult Members

**Target date:** 2026-10-26

**Status:** Implementation candidate; review required.

## Goal

Generalize the proven two-adult household model to a small bounded adult household.

## Implemented membership contract

- At most **4 active adults** and 16 trusted devices per household. Inactive
  historical membership records do not consume adult capacity.
- Admission reuses the existing short-lived, single-use pairing code. The
  active adult who created the invitation reviews the claim and approves it
  with their trusted device/passkey ceremony. Any active adult may create and
  approve an invitation; there is no quorum. Only one live adult admission
  invitation is retained per household; creating another revokes the earlier
  pending or claimed invitation. Removing its author also revokes it.
- New adults receive current and future key epochs only. Earlier history is
  not provisioned to them. This preserves the v0.9 entitlement policy.
- Removal requires fresh passkey authentication by an active adult, revokes
  every target device and session, and excludes those devices from subsequent
  epoch provisioning. Existing access-change epoch rotation remains in force.
- One adult may remain after another leaves or is removed. The last active
  adult cannot leave; household deletion retains its existing one-adult
  fresh-passkey authority and 30-day cancellation window.
- Recovery remains member-targeted: any other active adult may authorize a
  particular active member's recovery. One eligible approver is sufficient;
  a single remaining adult cannot recover another member.
- Existing two-adult households retain member IDs and event history and need
  no re-pairing or key regeneration. Their existing two-member state is valid
  under the new bound.
- Durable server schema v4 updates the admission-limit trigger transactionally;
  browser event, IndexedDB, and household archive formats do not change.
- Responsibility events continue to reference stable member IDs. The client
  offers every active member as an assignee and clears a removed member's
  current assignment while retaining the historical event.

The current identity model has no adult display-name field. Household access
therefore presents adults descriptively; IDs remain authoritative and are not
sent as names to the relay.

## Prerequisite

The previous release line has passed its gate.

## Product rule

Deliver one understandable household capability without making Kin feel like enterprise project management.

## Architecture constraints

- Preserve canonical event history and deterministic Rust/WASM behavior where the capability enters household state.
- Preserve local-first and encrypted-sync boundaries.
- Keep plaintext household semantics client-side.
- Define persistent-format migration before changing storage.
- Prefer native Web APIs and existing Kin abstractions.
- Do not add AI, scoring, surveillance, or hidden inference.

## Required implementation questions

- What new domain state or event is actually necessary?
- Can existing events/state represent the feature more simply?
- What happens offline?
- What happens across two devices?
- What happens after retry/restart?
- What does export/import do with it?
- Does member/device revocation affect it?
- What are the size/count limits?
- What is the migration from the prior supported version?
- What must be accessible by keyboard/screen reader?

## Release gate

- End-to-end capability works.
- Relevant Rust/native/WASM/browser tests pass.
- Existing history remains compatible.
- Offline/sync behavior is defined.
- Migration behavior is tested where needed.
- Accessibility is verified.
- Resource limits are explicit.
- Privacy/security claims are honest.
- Docs match implementation.

Then stop this line and move to the next minor.
