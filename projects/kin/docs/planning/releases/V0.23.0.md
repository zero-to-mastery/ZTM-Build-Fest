# v0.23.0 — Calendar Interoperability

**Target date:** 2026-10-14

**Status:** Implemented candidate on `kin-fast-track-v0.21-v0.25`; no tag or merge.

## Goal

Let a household intentionally carry explicitly dated Kin Items into calendar
software using the open iCalendar format.

## Delivered capability

- Lists provides a download action for active Items with planning dates.
- Each Item becomes an iCalendar `VEVENT` with `DTSTART;VALUE=DATE` and a
  one-day duration. Output is date-sorted and ties use stable Item identity.
- Text uses iCalendar escaping and UTF-8-aware 75-octet line folding. Stable
  UIDs derive from the Item ID; `DTSTAMP` is export time, not an Item time.
- Completed, archived, and undated Items, Routines, household identity,
  actor/device context, reminders, and times are omitted.
- Export is a local, explicit download; there is no calendar account access,
  network request, import, background sync, or storage mutation.
- The UI discloses that the downloaded `.ics` file is unencrypted and contains
  Item text. Users control the browser's download destination and handling.

## Product rule

Deliver useful portability without making Kin a generic calendar or a
project-management tool. Export is only available when an active dated Item
exists.

## Architecture constraints

- Reuse the protocol-16 Item projection; no new domain event or protocol.
- Keep iCalendar serialization in a small browser-side module with no new
  dependency. iCalendar format versioning is independent of Kin versioning.
- Use the existing encrypted local state in memory and create no persistent
  plaintext export cache. No storage, server, sync-envelope, or KARC migration.
- Bound output to 10,000 events and 16 MiB; reject malformed dates and
  timestamps rather than returning partial or success-shaped output.

## Validation

- Unit tests cover sorting, inclusion/exclusion, escaping, Unicode line
  folding, leap dates, invalid civil dates, timestamps, and count/byte bounds.
- The full Edge regression exercises accessible action state, filename,
  MIME type, local all-day content, and disabled state after clearing the last
  date. Existing Rust/WASM and protocol-16 compatibility suites remain required.
- Export is a point-in-time local snapshot. Across-device state arrives only
  through existing encrypted sync; a later export reflects the current local
  projection. Retrying a download does not alter or duplicate household data.
- No migration is required. Older protocol writers and archived backups retain
  their existing compatibility behavior.
