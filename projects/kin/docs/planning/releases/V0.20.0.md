# v0.20.0 — Staples & Replenishment

**Target date:** 2026-10-11

**Status:** Implementation and validation complete on
`kin-fast-track-v0.16.3-v0.20.x`; this is an unpublished candidate, not
production certification. No tag is created on the batch branch.

## Goal

Support recurring household supplies without becoming inventory management.

## Capability contract

- Add Staples as Item classification code 3 and expose a reusable Staples list
  on the existing Lists page. Today, Needs, and Shopping retain their behavior.
- Use the existing schema-v2 `ITEM_ADDED` event and Item archive lifecycle.
  A staple stays active when replenished; “Add to Shopping” appends a separate
  ordinary Shopping Item with the staple's text. The two Items are independent.
- Add replay protocol 14. Protocols 1–13 reject Staple-bearing events,
  summaries, and projections rather than omit or remap them; protocol 13
  continues to support Shopping and earlier Today/Needs behavior is unchanged.
- Keep Staples in canonical encrypted events. Local offline capture works, and
  existing encrypted household sync and KARC export/import carry the events.
  No IndexedDB, server database, event-kind, KARC, or sync-envelope migration
  is required.
- Retain the 4096 UTF-8-byte Item text limit, 10,000-event limit, and 64 MiB
  protocol bound. Use a labeled native classification selector, semantic list
  heading, keyboard-operable replenishment action, and focus restoration.
- Replenishment is always a member-triggered action. Do not add stock levels,
  quantities, purchase tracking, automatic schedules, notifications,
  prioritization, assignments, or inventory inference.

## Prerequisite

The previous release line has passed its gate.

## Product rule

Deliver one understandable household capability without making Kin feel like enterprise project management.

## Architecture constraints

- Preserve canonical event history and deterministic Rust/WASM behavior where the capability enters household state.
- Preserve local-first and encrypted-sync boundaries.
- Keep plaintext household semantics client-side.
- Define persistent-format migration before changing storage.
- Prefer native Web APIs and existing Kin abstractions.
- Do not add AI, scoring, surveillance, or hidden inference.

## Required implementation questions

- What new domain state or event is actually necessary?
- Can existing events/state represent the feature more simply?
- What happens offline?
- What happens across two devices?
- What happens after retry/restart?
- What does export/import do with it?
- Does member/device revocation affect it?
- What are the size/count limits?
- What is the migration from the prior supported version?
- What must be accessible by keyboard/screen reader?

## Release gate

- End-to-end capability works.
- Relevant Rust/native/WASM/browser tests pass.
- Existing history remains compatible.
- Offline/sync behavior is defined.
- Migration behavior is tested where needed.
- Accessibility is verified.
- Resource limits are explicit.
- Privacy/security claims are honest.
- Docs match implementation.

Then stop this line and move to the next minor.

## Validation evidence

Windows x64 validation passed with Node 22 and Microsoft Edge: 148 Rust tests,
311 Node tests (including 230 server tests), formatting, warnings-denied
Clippy, release `wasm32-unknown-unknown` build, and the Kin version check. The
full Edge browser regression passed with Staples capture/list isolation,
manual Shopping replenishment, archive behavior, and failed-append retry that
preserves Shopping item identity and returns focus to the source Staple.
Security UI, encrypted-storage, virtual-passkey, and root-rotation browser
regressions also passed. No independent security review or
assistive-technology certification is claimed.
