# v0.18.0 — Richer Routine Scheduling

**Target date:** 2026-10-09

**Status:** Implementation and validation are complete on `kin-fast-track-v0.16.3-v0.20.x`; this candidate is not published and is not production certification. No tag is created on the batch branch.

## Goal

Make recurring household work flexible enough for real life without building a calendar engine.

## Capability contract

- Retain Daily (wire code 0) and Monday-start Weekly (1); add every-two-weeks
  (2) anchored to the routine's creation civil date and Monthly (3) keyed to
  the first day of each calendar month.
- A routine created partway through a period has that period available on its
  creation date, but not earlier. Completion and reopening remain human
  actions for the current period; old completions do not carry forward.
- Keep the schema-1 `ROUTINE_CREATED` payload shape and canonical event bytes.
  Add replay protocol 12 as the explicit compatibility gate for cadence codes
  2 and 3. Protocols 1–11 reject richer-cadence events and cannot encode a
  richer-cadence projection; protocol 12 reads prior event history unchanged.
- Continue deriving current periods from an explicit browser civil-date
  sample and Rust replay. The creation date anchors biweekly schedules across
  devices; no browser-side recurrence reducer, reminders, notifications,
  calendar integration, assignments, or streaks are introduced.
- Keep schedules in canonical encrypted events. IndexedDB, server, sync
  envelope, KARC archive, and event schema versions do not change, so old
  histories require no migration and export/import uses the existing adapters.
- Keep routine text bounded to the existing 4096 UTF-8-byte limit and the
  event stream bounded to 10,000 events/64 MiB. Use a native select and
  announce cadence plus the active period in the existing routine status.

The previous release line has passed its gate.

## Product rule

Deliver one understandable household capability without making Kin feel like enterprise project management.

## Architecture constraints

- Preserve canonical event history and deterministic Rust/WASM behavior where the capability enters household state.
- Preserve local-first and encrypted-sync boundaries.
- Keep plaintext household semantics client-side.
- Define persistent-format migration before changing storage.
- Prefer native Web APIs and existing Kin abstractions.
- Do not add AI, scoring, surveillance, or hidden inference.

## Required implementation questions

- What new domain state or event is actually necessary?
- Can existing events/state represent the feature more simply?
- What happens offline?
- What happens across two devices?
- What happens after retry/restart?
- What does export/import do with it?
- Does member/device revocation affect it?
- What are the size/count limits?
- What is the migration from the prior supported version?
- What must be accessible by keyboard/screen reader?
