# v0.22.0 — Lightweight Planning Dates

**Target date:** 2026-10-13

**Status:** Implemented fast-track candidate; not published or production-certified.

## Goal

Let a household attach one optional date to an Item without turning Kin into a
calendar, reminder, or deadline manager.

## Product behavior

- Existing non-archived Items can receive, change, or clear a planning date.
- The native date input accepts valid Gregorian dates in years 0001–9999.
- Today and Tomorrow shortcuts resolve to the browser's local civil date once,
  when selected. The resulting value is fixed and never rolls forward.
- No time, time zone, reminder, notification, urgency inference, or automatic
  date is stored. Adding an Item and setting its date are separate user
  actions and separate canonical events.
- Completed Items can be planned or cleared. Archived Items are read-only in
  the UI. A stale date event authored offline before learning of an archive
  remains replayable after it, preserving convergence and importability; the
  command validator will not author a new date event for an archived Item.

## Canonical and compatibility contract

- Add schema-1 `ITEM_PLANNING_DATE_CHANGED`, event kind 30, with an Item ID and
  a four-byte `YYYYMMDD` civil-date key. Zero means clear.
- Add replay protocol 16. The result header retains its 72-byte shape and
  appends one `u32` planning-date value per Item after all existing Step
  records. Zero means unset.
- Protocols 1–15 retain their existing result layouts and fail closed on a
  date-bearing event or projection; they never silently discard a date.
- Event replay is deterministic and clock-independent. Concurrent updates
  use the existing `(logical_time, device_id, event_id)` order.
- Local event append remains one IndexedDB transaction. The existing
  encrypted sync, outbox, revocation, and KARC v1 archive paths carry the
  canonical bytes unchanged. No database, envelope, archive, or server
  migration is required.

## Accessibility and validation

The editor uses a native date input with an Item-specific accessible name.
Today, Tomorrow, and Clear are keyboard-operable buttons with explicit
accessible labels. Focus returns to the edited date input after persistence.
Rust validates command state, date encoding, protocol compatibility, and
replay; browser code does not make the replay depend on current time.

Validation includes Rust replay/command compatibility tests, real-WASM
protocol roundtrips and bounds tests, JavaScript syntax checks, local
persistence/replay and accessibility regressions, server tests, formatting,
warnings-denied Clippy, the release WASM build, version consistency, and the
full Edge browser regression. Detailed command results are recorded with the
milestone commit.
