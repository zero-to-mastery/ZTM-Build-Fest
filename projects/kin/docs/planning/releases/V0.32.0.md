# v0.32.0 — Encrypted Attachments Foundation

## Scope

Provide a cryptographic and durable relay foundation for bounded household attachments. This milestone adds browser-side AES-256-GCM encryption and authenticated server transfer. It does not yet add user-facing capture, offline queueing, attachment lifecycle controls, or portable archive support; those remain v0.33 work.

## Security and storage

- The browser encrypts file bytes and metadata (filename, MIME type, plaintext size, and parent routing) using the current household epoch key. A fresh 96-bit nonce is generated per encryption. AES-GCM additional authenticated data binds the format version, household ID, opaque attachment ID, and key epoch.
- The relay receives ciphertext, opaque attachment ID, epoch, byte count, and SHA-256 digest. It cannot read file contents or encrypted metadata. HTTPS remains required outside loopback.
- Every transfer requires an active authorized session, completed sync provisioning, and the relevant provisioned epoch. Uploads accept exact retries and reject conflicting content for a reused ID. Download verifies stored size and digest.
- Limits are 4 MiB plaintext per file, 64 attachments, and 50 MiB total per household. SQLite schema v3 stores ciphertext durably; household deletion finalization purges it.
- Images (JPEG, PNG, WebP) and PDF are accepted. The MIME type is encrypted and is client-declared; this is not a server-side content scanner.

## Validation

Focused crypto, sync-service, HTTP attachment, durable-store, and existing lock tests were run on Node 22.21.1. Crypto (3), sync service (15), HTTP sync (4), durable-store (6), and durable lock without the child-process case (13) passed. The lock test requiring a spawned Node process is blocked by this Windows sandbox's `spawn EPERM`; full browser integration and accessibility review remain outstanding.
