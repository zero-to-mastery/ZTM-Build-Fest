# v0.24.0 — Useful Household History

**Target date:** 2026-10-15

**Status:** Implemented candidate on `kin-fast-track-v0.21-v0.25`; no tag or merge.

## Goal

Answer 'when did we last do/change this?' without creating surveillance.

The v0.24.0 capability is a date-only “Last changed” label on each Item. Its
value is derived from the event timestamp of the latest effective Item or
checklist-Step transition in deterministic replay order. This is not a member
read receipt, actor/device history, exact-time display, or browsable timeline.
The displayed date comes from the source event clock, which may differ across
devices; logical event order, not wall-clock timestamp, determines replay.

## Architecture constraints

- Preserve canonical event history and deterministic Rust/WASM behavior where the capability enters household state.
- Keep the history date derived from existing events; add no event kind or
  actor/member attribution.
- Preserve local-first and encrypted-sync boundaries.
- Keep plaintext household semantics client-side.
- Define persistent-format migration before changing storage.
- Prefer native Web APIs and existing Kin abstractions.
- Do not add AI, scoring, surveillance, or hidden inference.

## Validation

- Windows x64, Node 22.12.0, and Microsoft Edge 154.0.4258.62.
- `cargo fmt --check`, warnings-denied Clippy, and 156 Rust tests passed.
- Release `wasm32-unknown-unknown` build passed; all 321 Node tests passed,
  including real-WASM protocol 16 compatibility and malformed protocol 17
  timestamp boundaries. Version consistency and `git diff --check` passed.
- Full Edge browser regression passed, including date-only rendering,
  effective-change refresh, focus restoration, persistence, and replay.
- Event timestamps use source-device clocks; clock skew can make the displayed
  date appear earlier or later. Logical ordering remains authoritative.
- The browser formats dates in the viewing device's local time zone, so
  devices in different zones can display adjacent dates for the same event.
- The timestamp extension is bounded at eight bytes per Item (80,000 bytes at
  the existing 10,000-entity limit) within the 64 MiB protocol result bound.
- No new event kind, persistent storage migration, server interpretation,
  actor/device attribution, read receipt, exact-time display, or timeline.
