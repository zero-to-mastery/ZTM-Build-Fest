# v0.41.1 — Mobile Attachment Upload Fix

**Candidate:** `kin-v0.41.1` candidate name on `fix/kin-v0.41.1-mobile-attachments`, based on `origin/kin-development` at `b173141` (the merge of PR #40, v0.41.0). Correctness patch to the v0.41.0 Mobile Experience & Passkey-First UX candidate: no tag, no release, no production certification, and no physical-device evidence (see the manual checklist below). It does not begin v0.42.

## Problem

Real-world phone testing: the attachment control was hard to find (behind an item's `Details`), tapping it did not reliably open a picker, choosing an image gave no confirmation, and chosen images never appeared as tiles.

## Root cause

- Each item row rendered its own `<input type="file">` (with a `<label for>`) inside `Details`. `<kin-today>` and `<kin-item>` rebuild their DOM on every state refresh, and `<kin-app>` refreshes on every sync pass, which runs every 5 seconds once a household exists. A phone picker (camera, gallery, confirm) takes longer than that, so by the time a file was chosen the input that received it was detached. Its `change` listener still ran, but the `kin:add-attachment` event it dispatched bubbled from a detached subtree and never reached `<kin-app>`. On a desktop the picker closes within the window, which is why the defect looked intermittent and automated tests (which dispatched the event straight at the app) passed.
- The status element was passed inside that same event and detached by the same refresh, so success or failure text was written into a node nobody could see.
- `handleAddAttachment` returned silently when the app was busy, and `captureAttachment` rejected any device without a server household identity with "Unlock Kin before attaching a file" even though the device was unlocked and the vault-sealed local path already existed.
- Attachment rows produced by a sync pass replaced the app's rows wholesale, so a pass that started before a save dropped the new tile until the next pass; the orphan sweep in the same pass could delete ciphertext saved by a capture whose binding had not yet committed.

## Corrections

### `web/components/kin-app.js`

- Owns one hidden file input (`attachmentInput`, `accept` photos and PDF) appended once and never re-rendered.
- `kin:pick-attachment` → `handlePickAttachment` records the target record and calls `input.click()` synchronously inside the tap, so the native picker opens from the user activation. `change` → `handleAttachmentChosen` → `saveChosenAttachment`; `cancel` clears the pending target.
- `saveChosenAttachment` reports progress per record: `Preparing photo…` (or `file`), waits up to 10 s for another save to finish instead of dropping the file, `Saving securely…`, then `<name> is saved on this device` (with `and waiting to sync to your household` when sync is configured). Failures are specific: file problem (type with detected MIME, empty, over 4 MB), locked session, still busy, storage failure, or "protected but couldn't be linked to this record". Errors also go to the app alert. Success text clears after 8 s; errors stay until the next attempt. `kin:add-attachment` remains as a programmatic entry to the same path.
- `mergeAttachmentRows` reconciles sync-produced rows against the current canonical bindings: rows for bindings removed locally are dropped, and local rows for bindings missing from the incoming list are kept.
- Locking clears the pending target, progress timers and progress text in addition to previews and the viewer.

### `web/components/kin-item.js`

- Every non-archived row shows an `Add photo` button (`aria-label` "Add a photo or file to <text>", `data-item-action="attach"`, 44 px) on the secondary line next to `Details`. The file control is no longer rendered under `Details`; the other controls there are unchanged.

### `web/components/kin-attachments.js`

- Modes are `full` (an "Add a photo or file" button plus tiles; notes, references, maintenance) and `tiles` (item rows). Both dispatch `kin:pick-attachment`; neither owns an input. The status line is read from the progress store on every render and the element re-renders when its own record's progress changes. Error status uses `role="alert"`. State labels: Saved on this device / Saved here, waiting to sync / Syncing / Synced / Not downloaded yet / Couldn't sync or open.

### `web/attachments/attachment-progress.js` (new)

Session-only per-record progress store with subscribe/notify. Nothing is persisted.

### `web/attachments/attachment-lifecycle.js`

- `attachmentFileProblem(file)` returns the specific human reason or `null`.
- `captureAttachment` tags failures with `error.stage` (`validation`, `storage`, `binding`), no longer requires a server identity (the vault-sealed `localSealed` path is used and reconciliation re-encrypts with the household key later), and otherwise persists exactly as before.
- `reconcileAttachments` accepts `suspectedOrphans`; an unbound `local` row is deleted only when still unbound on the next pass. `web/sync/sync-coordinator.js` passes a per-coordinator set. Callers without the set keep the previous immediate sweep.

### Service worker

- `web/service-worker.js` precaches `/attachments/attachment-progress.js` with the rest of the shell so offline loads keep working. The cache name still derives from the release and build fingerprint, so this version is a fresh cache.

### Styles and tests

- `app.css`: button and status styling; the label/file-input rules are removed.
- `scripts/attachment-upload-regression.mjs` (new, run by `browser-regression.mjs`), `scripts/passkey-regression.mjs`, `scripts/mobile-ux-regression.mjs`, harness event hooks and `blob:` same-origin allowance in `browser-regression.mjs`, plus Node tests listed in `docs/TESTING.md`.

## Unchanged contracts

Rust/WASM domain protocol and `bind-attachment` / `remove-attachment` commands; attachment ciphertext format (`kin/attachment/v1`), AES-GCM keys and epochs; the vault-sealed local fallback; IndexedDB stores and `attachment_records` row shape; server schema 6 and sync endpoints; CSP (no new sources; previews remain in-memory `blob:` URLs revoked on removal, viewer close and lock); recovery-key and passkey handling; household authorization (read-only/archived records expose no attach control). No plaintext is persisted and no household data is cleared.

## Manual mobile acceptance (not yet performed)

On a phone with the household already joined and unlocked:

1. Lists → Shopping: every item row shows `Add photo` without opening `Details`.
2. Tap `Add photo`: the system picker (camera / photos / files) opens on the first tap.
3. Take or choose a photo and wait longer than 10 seconds before confirming: the row shows "Preparing photo…", "Saving securely…", then "<name> is saved on this device and waiting to sync to your household".
4. The tile appears under that item with the file name, "Photo", its size and "Saved here, waiting to sync"; after sync it reads "Synced".
5. Tap the thumbnail: the viewer opens full-screen; `Close` returns you to the row.
6. Open and close `Details`, switch to Today and back, lock and unlock: the tile and thumbnail remain.
7. Choose a non-photo file (for example a `.txt`) or a very large photo: the row and the alert explain why it was refused and no tile appears.
8. Cancel the picker: nothing changes.
9. Repeat steps 2–4 from the installed PWA (home-screen icon) and confirm the picker opens and the photo saves.
10. Turn on airplane mode and attach a photo: it saves with "waiting to sync"; after reconnecting it reads "Synced" on this phone and appears on another household device.
