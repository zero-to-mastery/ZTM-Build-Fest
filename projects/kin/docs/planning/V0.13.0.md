# v0.13.0 — Recovery & Household Continuity

**Status:** v0.13.0 implemented. The first recovery milestone defines the
capability matrix and separate authority boundaries, and adds an explicit
same-member replacement-device ceremony. See [RECOVERY](../RECOVERY.md).

An active adult must use a remaining trusted device to select a lost device.
The replacement establishes a fresh passkey, device ID/token, and device keys;
approval atomically revokes the selected device and its sessions. Existing
recipient-bound provisioning supplies entitled epochs without exposing
plaintext household keys to the service. Claims retain the existing short
expiry, one-time activation, version binding, fingerprint review, and bounded
pairing limits.

This milestone does not yet let one adult authorize the other adult's recovery;
that is the v0.13.1 correctness gate. It adds no escrow, email/SMS recovery, or
promise that content survives loss of every key-bearing device and archive.

## v0.13.1 correctness

One active adult may now authorize a short-lived recovery ceremony for the
other active adult. The recovering adult creates and activates a fresh passkey
and device; the approver never receives the target's session or impersonates
them. Completion retains the stable member identity while revoking the target's
old credentials, trusted devices, tokens, and sessions. The fresh device is
eligible for retained epoch provisioning through the existing encrypted,
recipient-bound path. Removed/unrelated members, revoked devices, stale
approvals, and replayed activation fail closed.

## v0.13.2 hostile recovery

Restore now snapshots current active authority before accepting an older
backup, then reapplies exact current members, credentials, device/token and
revocation records, epoch/rotation metadata, and provisioning grants. Existing
deletion tombstones retain precedence and pending deletion still blocks
restore. The temporary restored database is fully validated and checkpointed
before publication. If no newer database/ledger survives, an old backup still
cannot reveal later changes; this is an explicit disaster-recovery limit.

Missing epochs pause sync. They are recoverable only from an entitled trusted
device or, for local-only history, a valid encrypted archive. Kin never skips
undecryptable events or obtains plaintext keys from the server.

## v0.13.3 UX and release gate

Recovery is exposed through the existing household and trusted-device views
with plain-language actions and explicit consequences. Keyboard-native controls,
focusable confirmation inputs, live status/error announcements, wrapping
layouts, and the existing visible expiry countdown cover the recovery path.
The final documentation records authority separation, key continuity, stale
restore behavior, disaster limits, threat assumptions, and irrecoverable states.

The final Windows x64 gate passed on Node 22.12, Rust 1.93, and Edge
154.0.4258.53: 304 Node/real-WASM tests, including 230 server/recovery tests;
118 Rust tests and doc-tests; formatting; warnings-denied Clippy; release WASM;
version/whitespace checks; the complete product browser suite; 313 encrypted
storage/security assertions; 97 security UI assertions; and 18 virtual
WebAuthn assertions with PRF exercised. This is not an independent security
audit, physical-authenticator certification, mobile-platform certification, or
global rollback proof. Other browsers and operating systems remain unverified.

## v0.13.4 review correction

Recovery capacity is calculated from the post-operation trusted-device set:
ordinary addition still requires a free slot, replacement exchanges one active
device for one fresh device, and member recovery revokes the target's active
devices before adding the fresh device. Restore now fails closed if the current
validated target has an active household absent from the backup. These rules
prevent a full household from blocking legitimate recovery and prevent a
predating backup from silently deleting newer active authority.

## v0.13.5 cancelled-deletion restore correction

When the live target has returned to active after cancelling deletion, its
current authority overrides an older backup's `deletion_pending` lifecycle.
Current pending deletion still blocks restore, finalized tombstones still win,
and a backup missing the active household is still rejected. The v0.13.x line
is implemented and release-gated; the remaining material below records the
original design contract and acceptance criteria.

## Prerequisites

- v0.11 durable identity/relay service semantics and restore behavior.
- v0.12 household deletion, backup retention, tombstone and offline-device
  semantics.
- Preserve v0.10's local-only archive restore boundary until a reviewed recovery
  design explicitly changes it.

## Problem being solved

Household history, local unlock, passkey identity, device trust, membership and
relay access are distinct capabilities. Losing different combinations of those
capabilities has different outcomes; Kin must not imply universal recovery.

## Scope

Produce a recovery matrix that classifies each case as automatically recoverable,
recoverable with explicit proof/action, local-history-only recovery or not
recoverable:

- one browser profile lost; one device lost; device wiped/reinstalled;
- passkey lost with another trusted device available; passkey lost with recovery
  secret retained; recovery secret lost with passkey PRF available;
- recovery secret compromised; all trusted devices lost; all passkeys lost;
- encrypted archive retained;
- identity-service database restored from backup; relay data lost while local
  devices survive;
- one adult loses all access while the second adult remains; both adults lose all
  devices; stale local backup restored.

Make one explicit, reviewed archive-authority decision during this line:

**A. Local-only restore.** An archive provides encrypted history portability, not
membership authority, device trust or server-account recovery. Synchronized
re-entry uses a separately authorized enrollment flow.

**B. Authenticated reattachment.** Only if justified by a security design, require
current member authentication, active household membership, authorization of a
new installation, proof of household history provenance, relay reconciliation,
current epoch entitlement, no restoration of cookies/session tokens, no revoked
device resurrection, conflict detection and fresh destination security setup.

Define replacement-device continuity for an existing member separately from
adding a second adult and recovering a removed member. A replacement preserves
member identity but creates a new device identity; it never silently reuses the
lost device ID or private keys.

Evaluate whether a second active adult may assist with recovery and specify
exactly what may be authorized. Keep member authentication, device authorization
and household key provisioning distinct; do not allow unrestricted impersonation.

State the all-device-loss boundary. Do not introduce server-side plaintext or
content-key escrow to make every case recoverable. Without surviving authorized
key material or a separately retained encrypted recovery artifact containing it,
synchronized content may be unrecoverable.

Test rollback/stale-state cases: old device after replacement, stale archive,
older server backup, old recovery manifest/key epoch, revoked device, removed
member, conflicting identity, duplicate replacement enrollment and a lost
response during recovery.

## Non-goals

- A promise that every household is always recoverable.
- Silent trust restoration from archive files or possession of old cookies.
- Reusing a lost device's private key/device ID.
- Server-side plaintext/content-key escrow absent a separate, reviewed design.
- One adult's unrestricted authority to impersonate the other.

## Architecture boundaries

Member authentication, device authorization, household-key provisioning,
encrypted household history and relay availability are separate state. Archive
restore cannot silently restore server authority. Recovery must reconcile with
current membership, revocation, deletion tombstones, key epochs and durable
server state; stale backups and devices do not override newer authority.

## Primary invariants

Recovery only succeeds through explicitly documented surviving capabilities.
Unrecoverable states are surfaced honestly. Recovery is never an authorization
bypass and never silently resurrects deleted households, removed members or
revoked devices. A replacement device has a new device identity.

## Expected failure scenarios

Exercise expired credentials/grants, unavailable service, lost response after
commit, duplicate enrollment, partial key provisioning, conflict between archive
and relay, old key epoch, restored stale server backup, stale local/remote
tombstone, revoked/removed identities and loss of every usable content key.

## Acceptance/readiness criteria

- Every listed recovery case has a documented capability inventory, classification,
  user-visible consequence and authorized action (or explicit unrecoverable
  result).
- Archive restore authority is chosen with rationale and tests; the chosen
  behavior matches portability, identity, sync, deletion and threat-model docs.
- Replacement-device enrollment is distinct from second-adult pairing and
  removed-member replacement, with new device identity and current authorization.
- Any second-adult assistance is constrained and tested against impersonation.
- All-device-loss behavior is honest and does not add unreviewed key escrow.
- Rollback, stale-state, replay, duplicate and lost-response cases fail closed
  without bypassing current membership/revocation/deletion state.
- No promise of recovery exceeds the capabilities and verified implementation.

## Deferred decisions

Choose archive reattachment (A or B), exact recovery proof, assisted-recovery
authority and any recovery material only during v0.13 design/review. No escrow
mechanism or reattachment protocol is selected in this planning contract.

## Relationship to next release

v0.13 stabilizes the authority and failure semantics that v0.14 must present in
onboarding, trusted-device, sync, archive, recovery and deletion experiences.
