# v0.41.0 — Mobile Experience & Passkey-First UX: implementation plan

**Status:** implementation candidate plan. Written before the code changes on
`feat/kin-v0.41.0-mobile-experience`; the release record in
[releases/V0.41.0.md](releases/V0.41.0.md) states what was actually done.

## Audit of the current mobile journey

The journey was traced through the real components (`kin-app`, `kin-security`,
`kin-household`, `kin-compose`, `kin-today`, `kin-item`, `kin-attachments`),
`web/security/*`, `web/attachments/*`, the server login route and the browser
regression suites.

| Step | Finding | Kind |
|---|---|---|
| First visit | The locked shell opens on "Protect this household" and a `Create recovery key` button. Nothing says what Kin is, that data stays on the phone, or that a passkey comes later. | Misleading default |
| Passkey enrollment | A PRF wrapper can only be added after the device holds a household credential (`/api/login/options` requires the trusted-device cookie). Enrollment is a secondary `Add passkey unlock` button in More and is never suggested. | Missing presentation |
| Returning unlock | Every PRF wrapper renders an identical `Unlock with passkey` button next to a permanently expanded recovery-key form; the heading is "Household locked". | Misleading default |
| Offline unlock | PRF unlock requires the identity service by documented contract (CRYPTOGRAPHY.md); offline the passkey button fails with a raw `fetch` error. | Security constraint needing explanation |
| Create vs join | Setup copy reads "Set up this adult and device with a passkey before pairing another adult" with `Set up household` as the only primary action; joining lives on `/pair`, which a new phone never reaches unless it opened an invitation link. Same-member device adds are indistinguishable from joins. | Misleading default |
| Classification | The only capture form is on Today, defaults to `need`, and resets to `need` after each add; Lists has no capture at all. Nothing explains Today / Needs / Shopping / Staples. | Confusing default, missing presentation |
| Attachments | Every attachment is a filename plus Open / Save file / Remove; images are never shown. Rows do not carry the MIME type. CSP `img-src 'self'` would block blob previews. | Missing presentation |
| Item rows | Each item renders ~12 controls (file input, responsibility, reminder, area, planned date, pin, checklist, archive) at once. On a 360px phone one item is taller than the viewport. | Mobile layout |
| Feedback | Status/alert text is at the bottom of the page below all content, so on a phone errors and retry are invisible when the user is near the top. | Mobile layout |
| Viewport | No `viewport-fit=cover`; header ignores the top safe area; fixed bottom nav does not account for the software keyboard. | Mobile layout |
| Error wording | Sync pauses show raw server messages; attachment failures say "unavailable on this device" without stating that nothing was deleted. | Misleading labels |
| Approve button visual state (P-005) | Already recorded; unchanged here. | Known |

No functional storage, replay, or authorization defect was found in this audit.

## Constraints that shape the implementation

- PRF unlock keeps its documented contract: a server-verified assertion with
  required user verification. Offline unlock stays recovery-key only; the UI
  now explains that instead of failing with a network error. An offline local
  challenge would be cryptographically equivalent for vault decryption but is a
  documented contract change and is deferred (see follow-ups).
- No plaintext secret is ever written to `localStorage`/`sessionStorage`.
  Thumbnails live only in memory as revocable object URLs and are revoked on
  lock.
- Rust classification values (`today`, `need`, `shopping`, `staple`) and the
  `kin:add-item` contract are unchanged. Labels and defaults are presentation.
- Household joining uses the existing pairing/claim/approval endpoints only.

## Workstreams

1. **Authentication & onboarding** — `kin-security`, `passkey-unlock.js`:
   welcome flow, recovery-key save step, passkey-first lock screen with
   recovery as a secondary action, offline explanation, settings view that
   shows passkey state and auto-lock preference, post-registration prompt to
   turn on passkey unlock.
2. **Household joining** — `kin-household`, `kin-app`: "How would you like to
   get started?" with create / join / add-device choices, plain-language
   explanation of device protection vs. membership, Today "Get started" card.
3. **Classification & capture** — `kin-compose`, `kin-today`, `kin-app`:
   context-sensitive defaults (Today page → Today; each list has its own
   capture), sticky chosen destination, descriptive list hints, destination in
   the confirmation message.
4. **Attachment presentation** — `kin-attachments`, new
   `attachments/attachment-preview.js`, `kin-app`, CSP: inline image
   thumbnails with lazy decode, tap-to-view dialog, document tiles, revocation.
5. **Mobile interaction & errors** — `kin-item`, `app.css`, `index.html`,
   `kin-app`, `kin-household`: primary action + Details disclosure per item,
   safe areas, keyboard-aware viewport, mobile feedback placement,
   human-readable sync/attachment messages.

Each workstream is verified with the existing Node and browser gates plus
focused additions before the next begins.
