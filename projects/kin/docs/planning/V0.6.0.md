# v0.6.0 — Since You Last Looked

**Status:** Current through v0.7.4 Routine Stale-Action Correctness; Frozen capability contract. This release adds a bounded, event-derived household catch-up summary. It does not record who viewed it. Stabilization milestones are v0.6.1 correctness, v0.6.2 resilience/accessibility, and v0.6.3 hardening/polish; stop after v0.6.3 for user evaluation.

## Product and privacy boundary

Answer “What changed that I should know about?” with a compact summary of meaningful household coordination events since this browser installation was explicitly marked caught up. This is a bounded snapshot, not an activity feed, audit-log UI, read receipt, member tracker, contribution history, or person-by-person timeline.

No domain event is written for opening, reading, or acknowledging the summary. Add no summary-view, last-looked, member-caught-up, or read-receipt event kinds. No actor/device IDs, names, attribution, individual event timestamps, analytics, external service, or AI appear in the summary. Pulse is excluded. There is no history browser, search, filter, export, pagination, or “view all activity.”

The catch-up cursor means only that this browser installation explicitly advanced through a local event boundary. It does not identify a person or claim that anyone read or agreed with the changes. Canonical household events remain in the `events` store; local catch-up metadata remains in the existing `local_context` singleton. IndexedDB stays schema version 1.

## Summary semantics

Rust owns summary event selection, semantic kinds, ordering, counts, truncation, and the frozen event-stream boundary. JavaScript owns neutral presentation wording and safe DOM rendering. Include exactly these meaningful event kinds:

| Summary kind code | Semantic kind        | Entity code | Text source             | Classification |
| ----------------- | -------------------- | ----------- | ----------------------- | -------------- |
| 1                 | item-added           | 1 (Item)    | Added Item text         | Today or Needs |
| 2                 | item-completed       | 1 (Item)    | Referenced Item text    | absent         |
| 3                 | item-reopened        | 1 (Item)    | Referenced Item text    | absent         |
| 4                 | item-archived        | 1 (Item)    | Referenced Item text    | absent         |
| 5                 | handoff-added        | 2 (Handoff) | Added Handoff text      | absent         |
| 6                 | handoff-acknowledged | 2 (Handoff) | Referenced Handoff text | absent         |
| 7                 | handoff-archived     | 2 (Handoff) | Referenced Handoff text | absent         |
| 8                 | talk-added           | 3 (Talk)    | Added Talk text         | absent         |
| 9                 | talk-resolved        | 3 (Talk)    | Referenced Talk text    | absent         |
| 10                | talk-reopened        | 3 (Talk)    | Referenced Talk text    | absent         |
| 11                | talk-archived        | 3 (Talk)    | Referenced Talk text    | absent         |

Do not summarize `PULSE_SET` or `PULSE_CLEARED`; they still participate in normal state replay and can lie within the through-boundary. Rust emits the most recent eight meaningful entries, in original event order. `summary_total_count` counts every meaningful event strictly after the input cursor, including omitted earlier entries. The omitted count is `summary_total_count - summary_count`. Never attribute an entry to an actor or show its event timestamp. Archive wording says “archived,” not deleted.

Presentation wording is browser-owned, for example: “Buy milk added to Needs,” “Trash tonight added to Today,” “Electric bill handled,” “Electric bill reopened,” “Diaper bag added to Handoff,” “Diaper bag acknowledged,” “Weekend plans added to Talk,” and “Weekend plans resolved.” Omission copy is a compact count of earlier changes. Empty state is “You’re caught up.” The explicit control is “Caught up.” Render household text as text, never markup.

## Local cursor and initialization

Extend the `local_context` singleton with equivalent fields:

```text
last_looked_event_id: 16 bytes or null
last_looked_local_sequence: safe integer (0 when no event boundary exists)
last_looked_at: safe integer UTC epoch milliseconds
```

Treat a legacy context with all three fields absent as uninitialized. Validate its existing identity and counter fields first. Initialize the cursor and read the event tail in one IndexedDB read/write transaction spanning `events` and `local_context`, the same stores used by event append. If history exists, store the last committed event ID and local sequence, with initialization time; if history is empty, store null/0 and initialization time. A concurrent append serializes before or after this transaction: an append before it is included in the initial boundary, and an append after it remains unseen. Do not write an event, advance `next_logical_time`, rewrite event bytes, or create artificial summary data. Partial or malformed cursor metadata fails closed without overwriting it. No schema version bump or new store/index is allowed.

Provide a narrow `getCatchUpState()` and `markCaughtUpThrough(snapshotBoundary)` storage API. KinApp orchestrates their use; components do not access `local_context`. A read-only catch-up snapshot must read ordered event rows and cursor metadata in one IndexedDB transaction so the Rust request and rendered upper boundary describe the same snapshot.

Use local sequence only inside browser storage for lookup and monotonic comparison. Protocol v6 uses stable `event_id`; the browser maps the Rust result boundary back to the exact row/local sequence in that captured snapshot. Never ask Rust to interpret IndexedDB sequence numbers.

`markCaughtUpThrough` is one read/write transaction over `events` and `local_context`. It validates context, verifies both the requested sequence and event ID still identify the same stored row, validates the current cursor boundary, and compares local order before writing. Advance only when the requested sequence is newer; the resulting cursor is `max(current, requested)`. A stale/equal request is a no-op and never changes `next_logical_time`. Preserve all unrelated context fields. The requested boundary comes from the rendered snapshot, never from a new “latest event” read at click time. A successful cursor update sets `last_looked_at`, then KinApp broadcasts a content-free view-state invalidation and refreshes the projection.

## Snapshot and race contract

Every v6 result reports the exact last event in the supplied ordered stream as `summary_through_event_id`, whether or not that event is meaningful (including a trailing Pulse event). This is the only boundary the UI may mark caught up for that projection. If the stream is empty, the boundary is absent. The boundary is not the last meaningful summary entry.

An event appended after the snapshot is rendered is not acknowledged by clicking “Caught up.” For example, if the view is rendered through event 100 and event 101 arrives before the click, the cursor advances only through 100 and a refreshed summary includes 101. If Tab B marks through 105 and a stale Tab A later requests 100, the cursor remains at 105. Truncation acknowledges the bounded snapshot as a whole: marking through the exact snapshot boundary also covers omitted earlier meaningful changes represented by the total/omitted count.

After the first-run boundary is initialized to existing history, normal browser requests include that stable cursor, so historical events are not presented as unseen. A protocol request with no cursor summarizes all meaningful events in its supplied stream. A present cursor must match an event in that stream; if missing, fail deterministically with invalid-event/domain status (4). Never guess its position or silently summarize from the beginning. Exact duplicate event delivery must not duplicate a summary entry; conflicting event-ID reuse remains an integrity error.

## Protocol v6 request

All integers are little-endian. Protocols v1–v5 retain their exact request/result bytes, behavior, event support, and explicit v5 `as_of`. Protocol v6 adds a summary cursor without repurposing old reserved bytes. Its request header is exactly 40 bytes:

| Offset | Size | Field                                               |
| ------ | ---- | --------------------------------------------------- |
| 0      | 4    | `KINE`                                              |
| 4      | 2    | protocol version = 6                                |
| 6      | 2    | reserved = 0                                        |
| 8      | 4    | event_count, at most 10,000                         |
| 12     | 8    | explicit `as_of:i64`, valid browser timestamp range |
| 20     | 1    | `cursor_present` = 0 or 1                           |
| 21     | 3    | reserved = 0                                        |
| 24     | 16   | stable cursor event ID                              |

When `cursor_present = 0`, all 16 cursor bytes must be zero. When present, the bytes are the exact stable ID of an event in the supplied ordered stream. v6 accepts existing event kinds 1–13 and supported event schemas exactly as v5 does. Its current-state projection is the v5 projection evaluated at the supplied `as_of`.

## Protocol v6 result

The v6 `KINS` header is exactly 52 bytes:

| Offset | Size | Field                                               |
| ------ | ---- | --------------------------------------------------- |
| 0      | 4    | `KINS`                                              |
| 4      | 2    | protocol version = 6                                |
| 6      | 2    | reserved = 0                                        |
| 8      | 4    | item_count                                          |
| 12     | 4    | handoff_count                                       |
| 16     | 4    | talk_count                                          |
| 20     | 4    | pulse_count                                         |
| 24     | 4    | summary_count (0–8)                                 |
| 28     | 4    | summary_total_count (at most event_count)           |
| 32     | 1    | `summary_through_present` = 0 or 1                  |
| 33     | 3    | reserved = 0                                        |
| 36     | 16   | exact last stream event ID, or all zero when absent |

Preserve the v2 Item, v3 Handoff, v4 Talk, and v5 Pulse record layouts and ordering. Follow them with `summary_count` records. A summary record has a 24-byte fixed header followed by exact UTF-8 text:

| Offset | Size | Field                                                         |
| ------ | ---- | ------------------------------------------------------------- |
| 0      | 16   | summary source `event_id`                                     |
| 16     | 1    | summary kind code 1–11 from the table above                   |
| 17     | 1    | entity code (1 Item, 2 Handoff, 3 Talk), consistent with kind |
| 18     | 1    | classification (0 Today, 1 Needs, 255 absent)                 |
| 19     | 1    | reserved = 0                                                  |
| 20     | 4    | text length in bytes, 1–4096                                  |
| 24     | N    | strict UTF-8 text                                             |

Only kind 1 may carry classification 0 or 1; every other kind must use 255. Validate kind/entity/classification combinations, reserved bytes, UTF-8, exact lengths, counts, trailing bytes, and the existing 10,000-event/entity and 64 MiB bounds. `summary_count <= min(8, summary_total_count)`. The result may contain up to 10,000 existing entity records plus eight summary records, subject to the 64 MiB limit. KERR remains protocol 1 with stable error categories. Protocols v1–v5 do not expose summary projection and must not be made to understand a cursor.

The current browser writer becomes protocol v6. The bridge accepts and strictly decodes v1–v6. Protocol v6 retains explicit `as_of`; no event schema or domain event code changes.

## Browser and component responsibilities

Add a focused `<kin-catch-up>` presentation component near the top of main content. It receives Rust-derived structured entries, total/omitted counts, the local `last_looked_at`, and the immutable mapped snapshot boundary. It renders a semantic section/heading/list, concise entries without per-entry timestamps, omitted-count copy, textual empty state, and explicit “Caught up” button. It dispatches user intent only; KinApp owns cursor reads/writes, busy/focus/feedback, refresh and BroadcastChannel.

Keep a rendered boundary frozen until that projection is replaced. The button must submit only that boundary. On success, reload a consistent event/cursor snapshot and recompute through Rust; on write failure, keep the cursor and rendered summary unchanged, surface an assertive error, and offer a recoverable retry. If the write commits but the reload fails, broadcast the committed view-state invalidation, preserve the rendered summary, and offer a canonical refresh retry without another cursor write. Opening/reloading Kin never advances an initialized cursor.

Keep the existing `{ type: "events-changed" }` message. Add `{ type: "view-state-changed" }` for committed local cursor updates. Neither message may include an event ID, cursor, text, count, actor, or device. Receivers reload local metadata and canonical events and recompute. BroadcastChannel is advisory; reload/focus recovery must converge from IndexedDB.

Use a semantic section and heading, semantic summary list, clearly named native button, keyboard operation, logical focus order, focus retained/restored after update, polite summary/caught-up feedback, assertive errors, textual state (not color-only), visible focus, 48px target, 320px reflow, forced-colors, increased-text-spacing, reduced-motion, and 200% zoom where actually tested. Do not claim screen-reader certification without testing.
