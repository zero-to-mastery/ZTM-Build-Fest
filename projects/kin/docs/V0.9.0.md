# Kin v0.9.0 — Encrypted Event Synchronization Contract

**Status:** Binding implementation contract and living v0.9.3 release record. v0.8.8 had no content-key management or sync; v0.9.x implements the design below. This is not an independent security review or production certification.

## Goal and trust boundary

Trusted devices encrypt the exact canonical `encoded_event` bytes locally and exchange versioned opaque envelopes through an authenticated relay. Rust remains the domain validator/reducer. JavaScript owns Web Crypto, key persistence, and transport. The service authorizes members/devices and coordinates opaque delivery; it never receives household keys, plaintext event payloads, or decrypted state. Passkeys authenticate members and are not encryption keys.

This design targets a curious-but-honest service and database disclosure. It is not a zero-knowledge claim. The service still controls authorization and availability. Active malicious code in an authorized browser/runtime defeats client encryption.

## Assets, adversaries, and threat assessment

Assets: household plaintext/history, epoch keys, device private keys, identity/authorization state, encrypted envelopes, cursors, credentials, and users' recovery expectations. Boundaries: browser/runtime, browser storage, browser/service, service/database/logs, and device provisioning.

| Threat                                             | Protected                                                                                         | Partially protected                                                            | Not protected                                                    |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| Curious-but-honest operator                        | Event content and keys are client-only                                                            | Household/device IDs, event timing/count/size, epochs, cursors, and membership | Content already opened on a client                               |
| Service database compromise                        | No plaintext content key or event semantics in relay records                                      | Ciphertext, IDs, public keys, cursors, and operational metadata may leak       | Availability and traffic correlation                             |
| Passive network observer                           | TLS plus payload AEAD                                                                             | IP, endpoint, packet size/timing patterns                                      | Anonymity                                                        |
| Active network attacker                            | TLS origin validation, AEAD, signatures, and one-use grant binding reject modifications           | Blocking/delay                                                                 | Availability or compromised endpoints                            |
| Malicious/replaying server response                | Signed envelopes and AEAD AAD bind author, household, event, and epoch; ID conflicts are detected | Reordering/withholding and some locally observed rollback                      | Completeness for a first-time client; global anti-equivocation   |
| Revoked device                                     | Server rejects later operations; new epochs exclude it                                            | Old ciphertext/keys remain usable if already copied                            | Erasing prior plaintext or keys                                  |
| Stolen locked device                               | Non-extractable private keys and OS lock reduce casual access                                     | Browser-profile/forensic protection varies                                     | Compromised platform or unlocked profile                         |
| Stolen unlocked trusted device                     | Another device can revoke sessions/access                                                         | Local content and keys remain accessible until revocation takes effect         | Confidentiality while attacker controls runtime                  |
| Malicious household member                         | Device signatures identify which enrolled device authored an envelope                             | A member can use their own authorized device to create/copy content            | Preventing an authorized member from acting as themselves        |
| Compromised browser/runtime, XSS, build, or origin | No cryptographic protection once authorized code executes                                         | CSP, text-only rendering, dependency minimization reduce likelihood            | Plaintext/key confidentiality or integrity while compromised     |
| Lost trusted device                                | Revoke it from a remaining active device                                                          | A disconnected device learns later                                             | Remote erasure or recovery of secrets held only there            |
| All trusted devices lost                           | No hidden server escrow                                                                           | Future user-held recovery requires a separately reviewed design                | Decryption without a surviving key/recovery secret               |
| Offline conflicting edits                          | Stable IDs, validation, and deterministic replay                                                  | A total ordering is reproducible but not semantic authority                    | Inferring who is right                                           |
| Old-event rollback/replay                          | Stable IDs, exact-envelope comparison, persisted observed cursor/high-water checks                | Fresh clients and consistent withholding weaken detection                      | Global anti-rollback without an independent transparency witness |

Non-goals: anonymity, protection from an unlocked compromised client, recall/erasure of data already learned, guaranteed service availability/completeness, server-side content recovery, relationship scoring, or generic CRDT behavior.

## Key hierarchy and lifecycle

Use one random 256-bit AES-GCM household content key per monotonically increasing epoch. Each device has separate P-256 ECDH and ECDSA key pairs; passkey keys are never reused. No extra household master/derived-key layer is introduced.

- Generate keys using Web Crypto/CSPRNG. Persist device private keys as non-extractable `CryptoKey` objects. Keep household AES keys non-extractable at runtime and persist only locally sealed key bytes in IndexedDB: derive a local AES-GCM wrapping key with HKDF-SHA-256 from the device's non-extractable ECDH private key and its public key, using a fresh random salt and domain-separated info. Bind household/epoch/purpose as AAD. During an explicitly approved provision only, decrypt the sealed bytes into a transient buffer, import the key as extractable solely for Web Crypto key wrapping, and zero the temporary buffer. Do not put raw keys in localStorage, URLs, cookies, or service sessions; do not claim protection from executing compromised JavaScript or a device that can invoke its own key.
- New devices create their key pairs locally. The claimant and inviter compare both device fingerprints. After fresh passkey approval, the inviter signs a device-authorization certificate binding household, member, device ID, public keys and fingerprint. The service verifies the signer is the authenticated approver; clients verify certificate chains from a locally pinned or manually compared root. A public key merely returned by the service is never sufficient identity proof.
- Provision an epoch with ephemeral ECDH P-256, HKDF-SHA-256, and AES-256-GCM wrapping. Fresh salt/nonce; AAD binds protocol, household, sender, recipient device and key fingerprint, epoch, grant ID, and expiry. The sender signs the canonical grant/envelope with its ECDSA device key. Grant is one-use, short-lived, recipient-bound; same-package retry is idempotent and changed-package reuse is conflict. The service sees wrapped bytes/public keys only.
- Events use only the current epoch. Active devices retain historical keys; rotation does not re-encrypt history. Revocation is committed and sessions invalidated before advancing the epoch. Remaining active devices provision the new key. If none can, sync pauses; no service escrow/fallback.
- A newly trusted device for an existing active member receives all retained epochs/history only after explicit trust. A newly joined or replacement adult receives only the membership-time/current epoch and later epochs; pre-join epochs are not provisioned in v0.9.x and may remain unavailable. A revoked/removed device never receives later epochs but cannot be made to forget what it already received.
- One lost/wiped device can be replaced from another active device. A device offline during rotation must receive the missing authorized epoch before reading it or creating current-epoch events. Missing historical/current keys block corresponding history/sync. Stale backups cannot lower epoch/cursor high-water state and must reauthorize. All-device loss without separately reviewed recovery material may make encrypted history unrecoverable. No recovery/escrow is implemented by implication.

## Event envelope and primitive choices

JSON envelope v1 (binary values canonical base64url):

```json
{
  "protocolVersion": 1,
  "envelopeVersion": 1,
  "eventId": "128-bit-random-id",
  "householdId": "opaque-id",
  "deviceId": "trusted-origin-device-id",
  "deviceSequence": 17,
  "logicalTime": "42",
  "keyEpoch": 1,
  "nonce": "96-bit-csprng-value",
  "ciphertext": "ciphertext-and-authentication-tag",
  "signature": "device-signature"
}
```

Plaintext is exactly the existing canonical event record, with no wrapper or semantic reserialization. AEAD AAD is a canonical length-delimited encoding of protocol/envelope versions, authenticated household ID, event ID, signing/upload device ID, device sequence, logical time, and epoch. ECDSA P-256/SHA-256 signs the AAD, nonce, and ciphertext. For newly authored synchronized events, embedded canonical `household_id`, `actor_id`, and `device_id` must equal the authenticated household, member, and signing device. Pre-sync events retain their placeholder IDs; an encrypted, signed identity-binding control record maps the exact legacy `(household, actor, device)` tuple to authenticated household/member/device. This means the signer adopts responsibility for importing that local history; it is not proof the historical action was made by that human. Receivers require exact identity equality or a previously verified binding before Rust accepts the event. Missing or conflicting bindings fail closed. Signatures identify the cryptographic envelope author, not semantic truth.

Use Web Crypto AES-256-GCM, 128-bit tag, and a fresh CSPRNG 96-bit random nonce per event. No counter/timestamp nonce. Limit to 2^20 envelopes per epoch key (random-nonce birthday collision probability below about 2^-57); rotate before the limit and never reuse a nonce. Keys/signatures/wrapping use platform primitives only: AES-GCM, ECDSA P-256/SHA-256, ECDH P-256, and HKDF-SHA-256. No custom crypto, ECB, unauthenticated AES, XOR, homemade MAC, password-derived key, or deterministic encryption.

Event IDs are stable CSPRNG 128-bit identifiers. Exact duplicate ID and envelope is idempotent; same ID with different bytes is corruption. Device sequence is per-device gap/ordering metadata, not event identity. Lamport logical time advances above every observed event. Replay order is `(logical_time, device_id bytewise, event_id bytewise)`; wall clock is display/audit metadata only. Unknown versions and malformed/noncanonical encodings fail closed and preserve source bytes.

## Metadata visible to the service

The service may see household/member/device/session identifiers; event ID; device sequence; key epoch; protocol version; opaque cursor; ciphertext size; count/timing; public device keys; provisioning grant participants/expiry; revocation/rotation timing; IP and connection patterns. It can infer devices in one household and sync cadence. Encryption does not conceal traffic patterns.

Retain only fields needed for authorization, routing, sequencing, deduplication, limits, and retention. Never send plaintext kind, title, description, category, item/routine ID, member text, or projection as relay metadata. Logs/errors/metrics use bounded outcome codes/coarse counts only; never log plaintext, keys, wrapped-key plaintext, nonce with plaintext, or full envelope contents.

## Relay, authorization, and bounds

Every push, pull, acknowledgement, key-directory operation, provisioning operation, and epoch operation rechecks active membership, matching household, trusted non-revoked device, and valid session. IDs, ciphertext, grants, and cursors are not authority. Store immutable records by `(household,eventId)`; exact retry returns prior acceptance, conflicting reuse fails. Pull uses bounded batches and household-bound opaque cursors. A stale cursor never bypasses current authorization.

Implementation enforces 16 active trusted devices/household, 128 key epochs, 128 live provisioning grants, 256 sync requests/device/minute, 20 events or binding controls/request, 200 KiB/request, 8 KiB/envelope, 10,000 local/outbox events, and 100,000 relay events/household. Every operation rechecks authorization. The v0.8.x identity service and v0.9 relay are volatile: restart loses identity and relay data. Local canonical events and exact cached envelopes survive and are retried if the relay cursor regresses, but ciphertext originating only from another device may be unavailable until that source returns. Acknowledgement is process-local, not durable; no backup or durable sync is claimed.

## Pairing, migration, and reconciliation

Pairing/passkeys establish member/device trust, not content keys. A joining device's public-key fingerprint is bound to its exact approved identity and compared through the user-verifiable pairing step. The joiner redeems only its own live grant. The service never gets a plaintext epoch key.

Pre-sync browser installations have independent placeholder household/actor/device IDs. Initial sync preserves those IDs and exact event bytes. A signed, encrypted identity-binding sidecar maps legacy identity tuples to the authenticated importer; v8 replay resolves them only in memory. Keep original rows authoritative and usable until the required key, outbox, relay, decrypt, and replay checks pass. Legacy actions are attributed to the importer only for household projection, not retroactive historical authorship.

Local persistence succeeds before upload; retry is at-least-once and idempotent. Pull/decrypt/validate/store is bounded and atomic per batch. Applied IDs prevent duplicate state application; conflicting IDs stop sync. Transport cursor order is separate from causality and conflict semantics. Deterministic state replay for the same accepted set is `(logical_time, effective device_id, event_id)`. The local catch-up summary retains local arrival order and its separate UI cursor. Concurrent completion/reopen is resolved by that deterministic tuple and both events remain in history. A terminal archive wins against an equal-Lamport mutation from another device; the concurrent mutation remains stored as a no-op and the local catch-up summary can surface both facts. A mutation with greater Lamport time after observing an archive remains invalid and pauses replay rather than silently dropping data. Text replacement is not currently an event; no generic CRDT or timestamp LWW is claimed.

Persist locally observed cursor/high-water state and accepted IDs. Lower-than-observed cursors and conflicting known envelopes stop with integrity errors. This cannot prove completeness for a fresh client or detect a server consistently withholding history; transparency witnesses are deferred.

## Frozen implementation amendments

This section is authoritative and supersedes any earlier wording in this document that suggests rewriting event headers, replacing event bytes, or applying the old strictly-increasing-time reducer unchanged to distributed sync.

- **Canonical representation:** exact `encoded_event` bytes are the household-history authority. Sync encrypts these bytes directly; after download, exact decrypted bytes are validated, ID-deduplicated, persisted, and passed to Rust. No semantic JSON event copy, projection-derived history rewrite, or destructive replacement is allowed. A checkpoint, if ever added, is derived/disposable under a separate reviewed contract.
- **Identity:** new synchronized canonical events embed the authenticated household/member/device IDs; the signature proves control of that device key and server authorization independently proves trust. Historical canonical records keep local placeholder IDs. Their envelope identifies the authenticated importing/signing device, not retroactive historical authorship. A signed, encrypted identity-binding record maps the exact legacy `(household, actor, device)` tuple to the importing authenticated identity. Rust v8 receives only verified mappings as interpretation context, decodes original bytes, and retains exact `canonical_bytes`; it fails on missing, ambiguous, or conflicting mappings. A mismatch is never accepted merely because the outer envelope says so.
- **Distributed ordering:** add v8 without changing v1-v7 fixtures or legacy single-device behavior. v8 resolves effective identity and sorts a copy for household-state replay by Lamport `logical_time`, then effective device ID bytes, then event ID bytes. Equal logical times are concurrent and valid. The original local-arrival-ordered rows remain the input to the local catch-up summary and UI cursor, so a later-arriving event that sorts earlier cannot be skipped by an acknowledged cursor. The local clock advances beyond the greatest observed remote value. The catch-up/UI cursor is never used as the sync cursor.
- **Outbox and cursor atomicity:** canonical local writes enqueue persistent bounded sync work. Persist the exact encrypted envelope and reuse those exact bytes on retry. Same event ID plus different ciphertext is a conflict. Remote cursor advancement occurs only in the same IndexedDB transaction as storing exact canonical bytes after decryption, identity checks, deduplication, and successful Rust replay. A pre-commit crash permits safe redelivery; cursor state is separate from catch-up state.
- **Epoch arbitration:** a rotation is compare-and-advance `(expected=N, new=N+1)` with recipient-bound wrapped keys. Exactly one concurrent proposal may commit; retry returns that same transition, stale proposals fail, clients reject epoch rollback, and the service never creates/learns content keys. Device revocation and member removal first invalidate all target sessions/devices, then trigger rotation excluding every target device. No remaining provision-capable device means sync pauses.
- **Historical entitlement:** a new device for an existing active member receives all retained epochs. A newly joined or replacement adult receives only the membership-time/current and later epochs; v0.9.x has no retroactive pre-join key grant. Revoked devices and removed members receive no later keys. Kin has no event-snapshot bootstrap, so missing older history is reported unavailable rather than faked with an incomplete state. This is an intentional privacy/product limit.
- **Migration gate:** do not mark initialized until keys exist, original rows remain intact, exact outbox envelopes are durably persisted locally, relay acceptance is observed, and downloaded/decrypted bytes pass identity validation and Rust replay. Any failure leaves the pre-sync household fully usable. Relay acceptance is not claimed durable unless restart-safe persistence is implemented and tested.
- **Migration epoch:** pre-sync local history is imported by the authenticated device at the current enrollment epoch. This does not retroactively give a newly joined/replacement adult earlier shared-household epochs; their own imported local bytes and the household's earlier shared events remain distinct entitlements. Historical canonical bytes are unchanged.
- **Transport/restart:** the built-in server binds loopback only. External use requires a trusted TLS-terminating proxy and HTTPS `KIN_ORIGIN` for sessions, WebAuthn, provisioning, and sync. No key derives from auth tokens. Relay acceptance is current-process receipt only; full service restart loses identity/session and relay state. Local canonical events and exact cached envelopes remain, but they do not recreate authenticated household identity; same-household sync cannot resume without service identity recovery, which v0.9.x does not implement. Do not claim durable/robust sync across restart.
- **Conflict and audit gates:** transport order, event causality, and domain conflict policy remain separate. Same accepted event set must replay identically; event ID duplicate applies once; conflicting reuse fails. Test equal-time events, local clock advancement, exact canonical encrypt/decrypt roundtrip, authenticated uploader/device mismatch, outer/inner identity mismatch, cursor crash ordering, exact-envelope retry, concurrent/stale rotations, membership removal, history entitlements, HTTPS configuration, and server restart. Malformed ciphertext/signatures/nonces/epochs/devices fail closed. The limits and privacy/logging audit are release gates.

## Implementation and validation record

The completed client uses exact `encoded_event` bytes as the only household-history authority. Browser Web Crypto encrypts and signs envelopes; the same-origin service authenticates and relays opaque bytes. Pairing binds locally generated device public keys by a human-comparable fingerprint. Same-member additional devices are supported. New/replacement adults receive only current and later epochs; no pre-join epoch grant or encrypted snapshot is implemented.

Validated on Windows x64 with Node 22.12.0, Rust/Cargo 1.93.0, and Edge 154.0.4258.53: all 108 Rust tests pass, including unchanged v1-v7 fixtures and v8 binding/order/conflict cases; all 104 crypto, pairing, relay, provisioning, HTTP, two-device, and real-WASM Node tests pass; and the complete isolated Chromium browser runner passes, including IndexedDB schema migration, exact-envelope relay-reset retry, reversed equal-time delivery, peer fingerprint persistence, cursor atomicity, catch-up independence, CSP, accessibility modes, and legacy product regressions. `cargo fmt --check` and Clippy with warnings denied pass.

Performance spot checks: 10,000 equal-Lamport v8 events replayed in about 80 ms in the native debug Rust test and about 198 ms through real release WASM under Node 22.12.0. A Node 22.12 Web Crypto sample of 100 signed/encrypted 512-byte payloads measured about 0.219 ms/event to encrypt and 0.313 ms/event to verify/decrypt. These are local single-run observations, not cross-browser benchmarks or production throughput guarantees.

No live cloud service, external AI, physical second device, Firefox/Safari, assistive-technology certification, durable relay restart, or independent cryptographic review is claimed. Relay acknowledgements are process-local. All-trusted-device/key loss can make encrypted household history unrecoverable.
