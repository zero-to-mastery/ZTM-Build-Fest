# GitHub sign-in deployment

Public exploration requires no authentication: the browser directly fetches account identity and one page of up to 100 owned public repositories, using primary language, topics and basic metadata. GitHub sign-in lets the Studio read pinned projects, every language in each project, and recent activity; the CLI and core loaders also use it for contribution discovery, contributor information and commit-backed features. Neither mode sends tokens into configuration, rendering or exports.

Anonymous API calls must stay client-side/direct; do not route them through a shared unauthenticated proxy. The local preview proxy is used by the browser only when the server advertises local token authentication, without exposing the token. The OAuth exchange service remains limited to authorization exchange and is not a general GitHub API proxy.

The static Studio uses GitHub App user authorization with authorization code + S256 PKCE. GitHub currently requires a client secret during exchange even with PKCE: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app

The isolated `auth/github-exchange.mjs` service is a portable Fetch API handler with no graph or npm runtime dependencies. GitHub Pages continues serving the application; the exchange runs separately, on either host:

- **Netlify (recommended).** `auth/netlify/functions/github-exchange.mjs` wraps the handler as a Netlify Function at `/api/github-exchange`, with a per-visitor rate limit (20 requests a minute, available on every Netlify plan). The repository's `netlify.toml` makes that Netlify site serve only the function and a one-line notice. This deployment's exchange URL is `https://constellation-sign-in.netlify.app/api/github-exchange`. Once the Netlify site is linked, `bash scripts/setup-sign-in.sh` walks the owner through steps 1 to 4. On Windows, run it with Git Bash: `bash` typed in PowerShell starts WSL, which can't run the Windows Netlify CLI, and the script says so and prints the Git Bash command. It opens a pre-filled GitHub App form and stores the three public values from step 3. For step 4, it opens Netlify's environment variables page, where the owner pastes the client secret, so the secret never passes through the script, a file or a command line. It then checks that Netlify stored the secret correctly, redeploys, and confirms the function answers.
- **Cloudflare Workers.** `auth/wrangler.toml` deploys the same handler as a Worker.

1. Register a **new GitHub App** in GitHub developer settings. Set its homepage to your Studio URL and its user authorization callback to the exact Studio URL, including the trailing slash (for this deployment: `https://mnichols08.github.io/constellation/`). Disable webhooks unless needed separately. Do not enable Device Flow. Keep expiring user tokens enabled.
2. Use public account data with no account write permissions and no repository write permissions. Leave optional permissions unset; GitHub's mandatory repository Metadata permission is read-only. Do not request broad OAuth `repo` scope. Test public profile and pinnedItems GraphQL access using a user authorization token before rollout; only add a documented read permission if GitHub requires it for your chosen data.
3. Set `GITHUB_CLIENT_ID`, `GITHUB_REDIRECT_URI`, and `STUDIO_ORIGIN` in the service environment. The origin is only `https://mnichols08.github.io`, without a path. Keep the callback exact and fixed server-side. On Netlify, set them as site environment variables on the site's **Environment variables** page or through the API, as the setup script does. Values in `netlify.toml` are not visible to functions, and changes need a new deploy. On the free plan, `netlify env:set` with `--scope` exits without saving anything and without an error, because scopes on plain variables need a paid plan.
4. Store `GITHUB_CLIENT_SECRET` in the deployment host's secret store. On Netlify, mark it **secret**, limit it to the production context, and leave out the post-processing scope; Netlify rejects a secret without those limits. Then run `netlify deploy --prod` from the repository root. For a Worker, from `auth/`, use your installed Wrangler CLI: `wrangler secret put GITHUB_CLIENT_SECRET`, then `wrangler deploy`. Apply the host's rate limit to the exchange endpoint. Do not log request/response bodies, authorization codes or tokens. No secret goes in the repository, Pages variables or browser JavaScript.
5. Fill the public meta values in `index.html`: `constellation-oauth-client` with the client ID, `constellation-oauth-exchange` with the HTTPS service URL, and `constellation-oauth-redirect` with the app's exact callback URL. The Studio offers GitHub sign-in only when it is served from that callback address, or its `index.html`, and always sends that address to GitHub. Local previews and forks serving the same file therefore keep the token form instead of a GitHub button that can't complete. Leave `constellation-oauth-redirect` empty to offer sign-in on any address. Deploy the static site normally. Empty values hide the **Sign in** button on Home; public exploration works as usual.
6. Verify sign-in against the real app: press **Sign in** on Home, then **Continue with GitHub**; approve and deny consent, test a mismatched/expired callback, verify username/avatar, public repositories and pins, and **Sign out** (from the **Signed in as @you** button on Home). The automated tests simulate GitHub; live consent cannot be verified until the owner registers and deploys the app/service.

A 32-byte random state and 32-byte verifier are stored in sessionStorage for at most ten minutes and consumed once. The callback URL is cleared before exchanging. Only the code and verifier go to the service. Its fixed-origin CORS response contains only the access token; refresh tokens and upstream errors are discarded. Access tokens remain in page memory and are confined to `https://api.github.com` with redirects rejected. Reload requires authorization again; saved local designs remain available. Sign out clears memory and cancels pending authorization, but does not revoke the GitHub App grant. Users can revoke that grant in GitHub settings.

The browser's draft/preset/config/scene/export paths do not receive credentials. Local preview keeps `.env` / `GH_TOKEN`, CLI and Actions keep their existing token support. On localhost only, the sign-in dialog offers a collapsed **Use a personal access token (local only)** form; it is absent from hosted copies. When the local preview server already uses `GH_TOKEN` from `.env`, Home shows **Signed in locally** and no token form is needed. For local OAuth testing, register a separate localhost callback/app and configure matching public meta values and broker environment.

Public GitHub request caching, its freshness window, refresh behavior and authenticated-response storage policy are described in [GitHub request caching](github-data-cache.md).
