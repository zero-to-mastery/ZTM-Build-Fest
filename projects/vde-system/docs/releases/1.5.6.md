## 🛡️ Core Highlights

A point release closing two related host-ownership-corruption defects, both stemming from the same class of problem: a host-side bind-mounted path silently ending up with broken ownership because of container-side assumptions.

### Fixed: Container entrypoint corrupting the host Docker socket ([#457](https://github.com/dderyldowney/vde-system/issues/457))
The Spoke entrypoint ran `chown root:docker /var/run/docker.sock` against a socket bind-mounted from the **host**. That resolved `docker` against the **container's own** `/etc/group` — assigned at image-build time by `docker-ce-cli`'s postinst, with no relation to the host's actual `docker` GID — silently rewriting the host socket's group ownership on every `vde start`/`vde rebuild`, and locking real host users in the `docker` group out of their own daemon.

The entrypoint no longer touches the host-mounted socket at all. Devuser's Docker access is now granted entirely at container **launch time** via Compose's `group_add:`, populated fresh on every ignition by `bin/vde` reading the host socket's numeric GID directly (with a Darwin/Linux `stat` branch, and an inert devuser-GID fallback instead of root/GID 0 if resolution ever fails). Nothing GID-related is baked into the Dockerfile, so images stay portable across hosts with differing GIDs.

### Fixed: Host workspace/data/logs directories auto-created root-owned ([#459](https://github.com/dderyldowney/vde-system/issues/459))
Docker auto-creates a missing bind-mount source directory itself, owned `root:root`, the first time a container starts. Nothing pre-created `projects/<name>` or `logs/<name>` for any VM (only `data/<service>` was pre-created, and only for a fixed list of types at `vde init` time), so `devuser` silently lost write access to their own workspace on every freshly-created VM.

`bin/vde` now pre-creates the correct host-owned directories (as the invoking user) right before every `docker compose up`, generalized by VM category so it also covers VM types added later via `vde add`:
- language VMs: `projects/<name>`, `logs/<name>`
- service VMs: `data/<name>/pgdata`, `logs/<name>` (the nested `pgdata` mount applies to every service template, not just Postgres — a pre-existing templating artifact this fix accounts for)

### Test Coverage
Two new `@host-safety` regression scenarios in `system-spine.feature` assert host bind-mount ownership survives a full stop/start cycle and a fresh ignition, with no manual `chown` ever required.
