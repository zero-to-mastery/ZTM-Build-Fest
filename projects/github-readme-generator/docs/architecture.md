# Architecture

## Application boundaries

`src/components/app-shell.js` coordinates draft selection, dialogs, pane visibility, preview settings, autosave, and import/export. `markdown-editor`, `github-preview`, `builder-form`, and `readme-health` are native Custom Elements. They use light DOM so shared design tokens, focus behavior, and accessibility relationships remain straightforward. The app does not need a framework or component runtime. Shadow DOM is an optional future boundary for independently distributed components.

`builder-form.js` uses a small field schema for badges, projects, links, and images. Repeating entries support edit, remove, reorder, and duplicate. Technology and widget data live outside components in `src/data`. Each widget supplies project attribution, instructions, and generic embed fields; no third-party private API is called.

## Markdown pipeline

1. The editor emits untouched Markdown.
2. The store records a bounded undo checkpoint and updates the draft.
3. Independent debounces schedule preview at 180ms, Health at 600ms, and autosave at 900ms. Raw input updates the source immediately.
4. Marked parses GFM; highlight.js highlights explicitly recognized code languages.
5. DOMPurify sanitizes the HTML against explicit tag and attribute allowlists.
6. Safe links receive a new tab target and `noopener noreferrer`; task inputs are disabled.
7. The preview replaces only its document content. The builder is not rendered on every keystroke after the initial ownership transition.

`<picture>` media sources are adjusted only in the preview DOM when simulating a theme. The source Markdown and exported media queries remain intact. Raw HTML is never used directly as application chrome. Form values, block labels, and metadata are escaped before interpolation.

Sanitization is a security boundary. `markdown/compatibility.js` is a separate advisory analysis layer and is not relied upon for security. Analysis traverses Markdown tokens, excludes fenced code examples, and reports categories instead of a numeric score. Regex checks for HTML patterns are intentionally heuristic.

## Block ownership

A block is `{ id, type, settings, separator? }`. `serializeBlock` emits ordinary Markdown/HTML. `serializeBlocks` inserts a blank line by default. Explicitly split imported sections use an empty separator: every byte of spacing is already included in their exact source slices. No ownership comments are added to exported content.

Builder operations replace only the block list and regenerate its document. Manual editor input goes through `markdown/source-patch.js` (ADR epic63-01): `changedRange` finds the one changed range from the common prefix and suffix, widened so it never splits a CRLF or surrogate pair; `editRanges` splits it around every Block whose text reappears unchanged inside the replacement, and `patchBlocks` applies each range right to left, mapping it onto `documentSegments` (each segment's `start`, `contentStart` after its Seam, and `end`). Blocks outside the Edited scope keep their ID, settings and ownership. Text inserted at a Seam extends an adjacent Custom Markdown block or becomes a new one and never detaches a neighbour. A range that reaches only the next Block's Seam keeps that Block and gives it the whitespace before its text as its Seam. A touched run of Blocks becomes one Custom Markdown block: a single Custom Markdown block keeps its ID; any Owned block (a non-custom type, a custom block with shared/generated/profile ownership, or the `bannerReference` target) is replaced under a new ID, so a builder form left open on the old ID can no longer overwrite it. Generated-section detachment and `bannerReference` removal are scoped to touched Blocks. The result must satisfy `serializeBlocks(blocks) === markdown`; otherwise, or on any exception, the whole draft becomes one Custom Markdown block with one non-Restorable record, so raw editing is never blocked.

Each Detachment adds a Detachment record to `draft.metadata.detachments` (ADR epic63-02): `{ version: 1, id, blockId, previousBlockIds, labels, kinds, at, previous }`, where `labels` and `kinds` run parallel to `previousBlockIds`. `previous` keeps a copy of the single detached builder or component Block (at most 32 KB of JSON), which makes the record Restorable; otherwise it is `null`. The list keeps the 20 newest records. Records follow Undo, autosave, backups and Studio projects (downloads go through `withoutDetachedCopies`, which sets `previous` to `null`, replaces any label that no longer appears in the Markdown with a generic name for its kind and drops records whose Block is gone, so removed text never travels in a file), never appear in exported Markdown, and `validateDraft` remaps `blockId`/`previousBlockIds` with the same map as `bannerReference`, dropping records whose Block is gone. Readers skip malformed entries and never rewrite them on read.

`markdown/ownership-review.js` is the pure Story #78 seam. It recognizes a source change or Detachment against the Block captured when a builder/component form opened, or resolves one Restorable record into current and proposed source. `ownership-review` uses the shared inert source-diff surface. Keep/Escape mutates nothing. Apply requires the whole-draft snapshot still to match, preserves the target position's Seam, replaces only that Block, removes only the used record and calls `Store.blocks` once. A changed snapshot refreshes the comparison without applying; missing targets, malformed/non-Restorable copies and duplicate Block identities fail closed. Generated, shared, profile and banner owners retain their separate reviewed recreation paths.

Seams belong to positions. Moving a Block up or down keeps each position's separator; removing a Block removes its own Seam. A Seam next to the change becomes a blank line only when the preceding Block's text does not end in a line break and the Seam has none, so the last split section never glues onto the next heading. Undo checkpoints include both Markdown and blocks, so every ownership transition can be reversed.

The explicit section splitter recognizes H1/H2 boundaries outside backtick and tilde fences. It creates Custom Markdown blocks rather than guessing structured fields. Import does not call the splitter.

## Local state and recovery

`state/store.js` maintains one active draft and up to 80 history checkpoints, with a shared estimated 8,000,000-byte snapshot budget for undo/redo. Drafts store names, Markdown, blocks, project metadata, IDs, and timestamps. `state/drafts.js` persists a versioned draft collection and workspace settings under `readme-studio:v1`. Draft JSON import validates its basic structure and compares serialization to raw Markdown; incompatible block metadata falls back to preserved source.

`documentation/suites.js` is the pure boundary for version-1 Documentation suite manifests. It owns the bounded project-type catalogs, fixed paths, source-size validation and atomic draft planning. The UI begins with no selection and emits only an exact-reviewed manifest. `app-shell` revalidates that manifest and its workspace snapshot, saves the complete candidate draft array once, and changes active state only after persistence succeeds. Suite drafts remain local and carry intended path metadata; this path is not a GitHub publishing target.

`localization/metadata.js` validates version-1 language-edition metadata at live, backup and Studio-project boundaries; `localization/model.js` builds and compares it. A workspace document declares one supported locale, an optional source-document ID, and a bounded source snapshot of up to 100 rendered sections using SHA-256 content and opaque heading-identity digests. Target-path, source/locale and translation-chain collisions fail before persistence for localized editions; legacy non-localized documents may retain shared targets. Workspace restore remaps source-document IDs alongside draft IDs, rejects chained sources, and preserves missing source links as explicitly unavailable until reconnected. Translation review compares digests conservatively, labels duplicates/truncation Unknown, and persists only the reviewed snapshot after source, translation, metadata and storage checks. Language-dependent prose heuristics remain explicitly unavailable for non-English locales; structural checks do not infer language or translated meaning.

`workspace/document-links.js` builds a case-sensitive path index from suite paths in a local namespace and validated repository-document targets isolated by canonical repository and exact branch. Before tokenization it enforces 256,000 UTF-8 bytes per document and 8,000,000 bytes per check, then walks at most 200 inert Markdown/HTML link tokens per source, resolves relative paths through the shared above-root-safe resolver, and checks target anchors with the shared GitHub-style heading parser. Exact-case explicit HTML IDs remain distinct from generated heading slugs. Results are derived and unpersisted. Export checks only the current source against the full index; unresolved or truncated results open `document-link-check`, whose export-anyway action is guarded from check start by the active document and snapshots of every workspace draft because a target Source/path or active-document change can invalidate the result. The module and review component are lazy-loaded together on check/export; pathless drafts retain direct offline export because they have no resolvable base.

`documentation/example-provenance.js` validates the three explicit statuses, emits one inert comment with a deterministic content fingerprint immediately before a structured code fence and performs the bounded, container-aware fence/marker association scan used by document, form and block Copy/Export. Verification notes remain in block settings; only the status and fingerprint enter Source. Editing an example invalidates older evidence by resetting its working-copy status to Placeholder; raw edits make the fingerprint stale. The small checker and `example-export-check` ship with the editing shell so offline copy/export never depends on loading a deferred review chunk. The review never executes or renders example content and emits only an explicit continuation tied to the checked source snapshot. Legacy/unmarked and imported fences are preserved without classification or automatic execution, but are reported as unclassified at copy/export time (ADR epic66-03).

Malformed saved data is not overwritten automatically: the app opens a temporary working draft, reports the storage problem, and allows exports. Quota/unavailable-storage errors are visible. JSON backups preserve settings for individual blocks; exported README files intentionally have no application metadata. History is session-local.

GitHub import fetches repository metadata and the public README endpoint, with a 20-second timeout and bounded response reads. Base64 content is decoded as UTF-8 without discarding a BOM. Larger READMEs use the raw media type and recheck the SHA to reject a remote change during retrieval. Markdown is capped at 2 MB of UTF-8 bytes, not JavaScript characters. There is no arbitrary HTML fetch/render API, token storage, or authenticated write path.

## Import pipeline

`markdown/resolve-urls.js` is a pure URL resolver. `render(markdown, { sourceContext })` sanitizes first, then resolves safe image/srcset/link attributes in the preview DOM. GitHub context contains owner, repository, ref, README path, SHA, and fetch time. Images use raw GitHub URLs; files use GitHub blob URLs. Anchors stay local and the preview assigns heading IDs. Unsafe schemes and unresolvable local paths cannot become application-relative requests. The sanitizer allowlist is unchanged; image data URLs are rejected by the resolver.

`markdown/sections.js` uses top-level Marked tokens and maps normalized lexer offsets back to the untouched source, including CRLF. It recognizes H1/H2/H3 and supports chosen boundary levels. Fences, comments, raw HTML, inline code, and nested blockquote/list content are not mistaken for structural boundaries. Genuinely parsed Markdown headings inside details can be boundaries. Each result has original start/end offsets, title, level, kind, body, and exact source. Classification is advisory metadata.

`markdown/merge.js` indexes normalized headings, deterministic body hashes, conservative kind aliases, and image URLs. Hash matches are verified against content; normalization is comparison-only. Candidate lists are bounded, and similarity checks inspect a bounded prefix only for matching headings. Ambiguous matches and duplicates never select or delete anything. `assembleMerge` requires every imported decision, rejects conflicting replacements, and retains original slices. Only newly joined boundaries may gain blank lines. This is a section-selection tool, not a Git three-way merge.

`state/import-plan.js` creates pure new/replace/append/merge plans. `import-dialog` loads a source, summarizes it, collects choices, and reviews the result before dispatching an apply event. A snapshot check rejects stale reviews. Current-draft operations call `Store.blocks` once with blocks and metadata, so undo restores both. New draft creation is separate. Requests cancel on input changes, source changes, close, or removal, and generation checks discard obsolete responses.

Draft `metadata.importSource` supports re-import; an additive import history records other fetched sources. Blocks can override context with `sourceContext`, including explicit null for local content. Adjacent blocks with matching context render together, preserving reference definitions and HTML across splits. Cross-source groups render independently. Splits/merges derive context from the actual source ranges, ignoring separator-only whitespace. A raw edit that collapses mixed-source blocks marks the result mixed rather than assigning an incorrect repository. Preview then warns for ambiguous relative images. Context and classification are backup-only metadata, never inserted into exported Markdown.

Plain Markdown imports have no inferred generated ownership. Valid Studio backups retain blocks and metadata for new/replace; append retains their blocks. Section split/merge produces user-owned Custom Markdown and does not invent autofill ownership. Existing detached-autofill section records remain conservative to avoid later duplicate generation. No storage schema migration is required; old v1 drafts with no context still work.

## GitHub profile autofill

`state/github-profile.js` validates usernames/profile URLs, fetches the public user record and paginated owned repository list, and normalizes a curated set of public data. Requests are limited to GitHub API endpoints, a 30-second timeout, and ten 100-item repository pages. Repository failure returns a usable profile with explicit incomplete-result metadata. Counts of received stars/forks exclude forks; language summaries count primary repository languages. No contribution or private-activity data is fabricated.

`state/profile-autofill.js` is a pure draft transformation. It replaces explicit placeholders, safely escapes external text, fills known sample content, and adds chosen generated sections. Internal block metadata records the last generated Markdown and identity placeholder source/value pairs. Refresh replaces only content that still matches its last generated form; manual changes relinquish ownership. Draft metadata retains detached section kinds to prevent duplicate insertion after raw editing. These records never appear in exported Markdown.

`github-profile-form` loads and previews the transformation without mutating the draft. An AbortController cancels requests on username changes, dialog close, or component removal; request generations also discard stale results. The loader clears its 30-second timeout and removes cancellation listeners when a request ends. Completed repository pages survive repository timeouts, but explicit cancellation produces no usable result.

Applying compares the reviewed snapshot (draft ID, Markdown, blocks, and metadata) against the current draft before recording one undo checkpoint. A mismatched snapshot is rejected. Internal `profileIntro` and `profileLinks` records allow untouched hero bios and sample contact URLs to refresh. Contact records check the row index, label, and previous URL before updating; reordered or edited rows are treated conservatively. Missing formerly public fields clear only generated values. Older v0.1.0 drafts keep their content, and absent ownership records are never inferred from ordinary personal text.

Profile metadata is scoped to the draft and included in JSON backups; no account-wide automatic fetching or background refresh occurs. The local storage schema remains version 1; additive ownership metadata requires no destructive migration.

## Performance and future Rust boundary

Editor input is native textarea editing; unrelated component trees do not rerender continuously. Preview and analysis are debounced. Unit coverage includes a Unicode document over 100 KB, with browser workflow coverage separately. Performance depends on markup complexity and device capability; this is not a latency guarantee.

Rust is not included in v0.1. Future measurements could justify moving deterministic analysis or large-document transforms behind the existing `analyze(markdown)` interface, behind the existing Worker boundary. A WASM loader should always preserve the JavaScript implementation as fallback and keep editor/preview startup independent of WASM. DOM rendering, forms, and local state belong in JavaScript.

Future banners can emit ordinary light/dark asset URLs into the existing picture block. A future schema migration should be explicit and preserve raw source on failure. OAuth, remote persistence, and integrations are outside this release’s boundaries.

## Foundation hardening boundaries

`state/workspace-backup.js` validates version 1 workspaces, normalizes known settings, regenerates imported IDs, and resolves name collisions. Reads of malformed/partial/future-schema storage preserve the original string and enter a write-blocked temporary workspace. Valid drafts from a partial version 1 document can be salvaged. The original remains downloadable. Replace/merge restore builds a candidate workspace and writes it successfully before switching in-memory state. Confirmation is required before replacing local drafts or the blocked recovery data. Restore itself is not a document history operation.

`workspace/repository-worksets.js` owns the additive version-1 `repositoryWorksets` workspace field and the separate portable workset format. A workset stores an allowlisted name plus canonical `owner/repository` strings only: document IDs, branches, paths, source, account data and credentials are not part of the contract. The module caps a workspace at 50 sets and each set at 100 repositories, resolves current local documents only when displayed, migrates the legacy version-0 portable shape, and gives colliding imports new IDs and suffixed names. Workspace backup merge keeps both libraries explicitly; old workspaces normalize to an empty library. The UI reviews imports before one local save and performs no network request or document mutation.

`themes/visual-library.js` owns reusable visual-token portability. A brand kit is the normalized combination of a complete theme and banner-visual settings: palette and component defaults plus deterministic dimensions, decoration, seed and light/dark treatment. It may also contain a bounded, inert light/dark logo URL or relative-path pair with required alt text; unsafe schemes, credentials, embedded data and executable content are rejected. It excludes banner identity text, README Source, generated SVG and executable presentation payloads. New brand-kit and visual-pack exports use version 2 so older readers reject logo-bearing data instead of silently stripping it. Version-1 visual packs and legacy `readme-studio-visual-preset` files migrate explicitly without logos. Import, token edits, application and destructive reset remain separately reviewed local actions; reviewing a saved kit exposes copyable logo markup without editing Source.

`workspace/batch-review.js` owns the version-2 interrupted-batch contract. Version-1 queues migrate in memory. A bounded, allowlisted journal records explicit decisions and successful opens; per-item checkpoints keep only a document ID, exact-source fingerprint, target identity and time. Recovery compares those checkpoints with current local documents and never fetches, mutates or publishes. Each successful open is persisted independently, so an interrupted multi-open operation retains completed progress without turning the journal into a remote-write outbox.

The store records source immediately and synchronizes it into the workspace before scheduling side effects. Draft switches save the outgoing workspace; pagehide and hidden-document events attempt a synchronous flush. Quota/access errors keep a persistent notice and download actions. A visual save status may change while typing; the separate live region announces settled saves rather than every keystroke. Local storage remains best-effort browser storage, not a durable database.

History snapshot sizes use twice the serialized JSON character count as a conservative estimate, cached in a WeakMap. Both count and byte caps prune old snapshots. This bounds retained history, not total browser memory or a single active document. Each newly loaded draft has its own store/history. Workspace presentation settings do not enter Markdown undo.

`markdown/url-safety.js` is shared by serializers, sanitizer, and preview URL resolution. It validates safe HTTP(S), mailto links, relative paths, and local anchors while rejecting credentials, control characters, backslashes, and unsafe schemes. Images exclude mailto/anchors/data payloads. DOMPurify remains the HTML boundary; only inert task checkboxes survive input sanitization. Preview CSS classes are limited to code/task-list classes so untrusted HTML cannot borrow application overlay styling. Preview DOM transformations never modify the store, source, or download path.

`markdown/visit-tokens.js` traverses parsed tokens in source order without Marked's accumulating callback-result arrays. This removes quadratic allocation from analysis. `health.worker.js` computes pure Health/duplicate results off the UI thread. The Health component has at most one request running and one latest pending draft; obsolete results are discarded and the Worker terminates when the component leaves the page. Worker failure produces a local explanation rather than rerunning expensive analysis synchronously. Whole-Markdown and identical source-segment analysis are reused within a request.

The preview catches rendering failures locally and keeps source/editor/export intact. Builder initialization failures show a local fallback. Unexpected window errors and unhandled rejections show a persistent recovery notice with reload/download actions, without exposing stacks in normal UI. Console diagnostics remain available for development. Clipboard errors open a readonly, selected-text dialog. Downloads use sanitized filenames, attached temporary anchors, and delayed object-URL revocation.

Dialogs retain their original trigger through nested content changes, focus meaningful fields on open, and restore a connected visible target on close. Import/split completion can explicitly target the editor; draft deletion/restore targets the draft selector. Background rendering/saves do not steal focus. Native dialog modality keeps hidden workspace controls outside tab flow.

Static builds include a separate Health Worker asset and relative Vite asset references. `scripts/static-smoke.mjs` verifies root and `/readme-studio/` deployments with a plain HTTP file server and no route fallback. A browser `file://` launch is not supported for ES modules/Workers; serve `dist/` over HTTP(S).

## Badge Studio (v0.2.x)

Provider adapters generate GitHub, npm, crates, Netlify and other documented Shields URLs locally. Dynamic preview is requested only on Generate; static preview follows composer edits. There is no proxy or API fetch while typing. Metadata contributes explicit target suggestions, never silently selected repositories.

`collections.js` validates portable schema-1 collection files and the workspace's schema-1 `badgeCollections` field. Collections are independent of draft blocks. Insertions clone settings or serialize source; stack integration does not establish live references. Collection saves write validated data before replacing in-memory persisted state. Quota/unavailable-storage failures leave the editable collection open for export. Duplicate output is bounded to 100 distinct guidance messages. Collection previews cap remote images at twenty and allow three widths; export is never truncated. No new runtime dependency was added.

Badge components use native controls and the app's dialog focus management. Composer clipboard fallback selects its output in place, retaining edits. Collection close prompts protect unsaved changes. Malformed builder settings fail locally; source editing and downloads remain available. Cross-browser tests cover these workflows in Chromium, Firefox and WebKit with mocked image providers.

## Structural analysis

`analysis/source.js` maps normalized parser offsets back to original UTF-16 source and caches one token tree per worker. `analysis/analyze.js` emits bounded, explainable findings and section inventories. Health rejects stale source jumps. Preview sanitization and exported source remain independent.

### Optional analysis core

The Health worker lazily initializes `analysis/wasm-loader.js`. Runtime statistics cross the WASM boundary; Marked parsing, section boundaries and rule diagnostics stay in JavaScript to avoid large JSON transfers. The standalone Rust structural API shares fixture parity tests. Initialization is bounded, failures use JavaScript, and consumers need no Rust toolchain. See [the Rust core guide](rust-core.md).

## Optional publishing boundary (0.8.0)

`server/publishing.js` owns ephemeral credentials and a fixed GitHub API operation allowlist. The optional Node server serves built static files and the same-origin boundary. `src/github/publishing-client.js` carries an in-memory CSRF nonce only; `publish-dialog` holds an immutable prepared source and independent remote baseline. Pure, DOM-free `publishing/change-set.js` is the seam between review and writing, shared by the dialog and the server (ADR epic69-02). `gitBlobSha` computes Git blob SHAs with Web Crypto. `buildChangeSet` turns the prepared files into a frozen, content-free manifest of File changes (create, update or unchanged, each with Base and Result SHA) whose id is the SHA-256 of its canonical JSON; the dialog binds Publish approval to that id and rebuilds the set on any change. `verifyChangeSet` re-reads every file before the first write and reports per-file SHA drift, and `executeChangeSet` writes the non-unchanged entries in order, stopping at the first failure. The server's `commit` recomputes the Result SHA and refuses a mismatch, a stale Base SHA or a create over an existing file. Change sets live only in dialog memory.

`publishing/journal.js` owns the separate version-1 Publish journal (ADR epic69-03). Before the first write, the dialog saves the content-free target, change set identity and per-file Base/Result SHAs; it marks each request pending before sending it and records its outcome after the response. A pending entry recovered after reload is unknown. Reconciliation explicitly reads every changed remote file and classifies it as written, not written or diverged. Only same-session content for the same change set can retry, only not-written paths are submitted, and a new checkbox approval is required. The server refuses a duplicate when the current blob already has the Result SHA. Malformed journal bytes are never overwritten: publishing stays blocked until the author downloads and explicitly clears them. The key is machine-local and is excluded from drafts, projects and backups.

Generated asset publishing reads baselines with `publishing/assets.js` and writes through the same Change set executor. The browser reviews each file and the optional owned banner rewrite; the server independently regenerates requested SVGs from normalized settings. Each remote write has a SHA precondition. Files are sequential, README last, with explicit partial-result reporting. Banner ownership is exact-source metadata and detaches on raw edits.

Workflow generation is a pure structured model and central quoted YAML serializer (`workflows/`). Generated sources carry no Studio runtime. The server re-generates YAML before accepting workflow writes and separately gates Workflows permission; scripts/commands execute only after users commit/run them on GitHub. Local settings do not hold secret values.

Rate limits stop further reads. Content is parsed with `JSON.parse` and line scans, never evaluated, and is discarded after evaluation; results are not persisted (ADR 0002). The evidence dialog renders escaped, status-grouped results; app-shell imports GitHub modules only when a plan needs them, rejects results if the document, Source or target changed during the read, and never calls `Store`.

### Reviewed drift remediation (1.6.2)

`evaluateDrift` attaches an optional `fix` ({ find, replace, once }) to observed mismatches and uncertain findings only when evidence supplies a correction: the existing spelling of a case-only path (shortest differing tail with any written `./` or `../`, or the whole link URL), a punctuation-only near anchor, exactly one punctuation-or-case near script name, or the whole `engines.node` minimum (`minimumVersion`, e.g. `20.11`) for a prose version (each non-overlapping statement on a line is its own claim). A link claim's line is where its URL is written as a link (`](url`, an `href`/`src` attribute or a full URL's autolink, searched with code spans, fenced code and HTML comments masked out; for a reference link, the lexed `def` token its label uses); when it cannot be found verbatim or unambiguously the claim is `unlocated`, keeps a best-guess line and gets no `fix`. A Node claim keeps its whole written version and is compared only as far as it is written; a statement read through an inline link or across a soft line break carries `written`/`versionAt` so its fix replaces the version on the line that holds it (`once`). Unknown results and matches never carry one. `workspace/drift-remediation.js` is pure: `driftProposals` groups remediable findings by Source line (numbered as the check numbers them, with `\r\n`, `\r` and `\n` endings kept out of the line text), places each fix only on whole-token occurrences, never after or before a character that continues a word, path or URL (a `find` ending in a separator such as `docs/` is not matched when the path goes on; an `=` or `,` inside another URL's query also joins), so a fix never lands inside a longer link, path or cross-file anchor on the same line (refusing ambiguous `once` fixes; a finding whose identical fix an earlier one on the line placed counts as placed) and keeps each finding's evidence. `previewDriftChanges` applies `{ line, before, after }` changes from the end backwards, rejecting stale, duplicate and out-of-range lines and writing typed line breaks with the line's own ending. `applyDriftProposals` additionally requires the current Source to equal the checked Source (ADR 0003).

The evidence dialog holds the checked Source and proposals in memory only (ADR 0002). Each line is a fieldset with read-only current text, an editable proposed line, a textual per-line diff and an approval checkbox; editing withdraws approval and the shared `source-diff` pane shows the combined result as text. Apply emits only approved changes. App-shell compares them with the draft ID, target identity and exact Source it recorded when the check finished, applies them with one `Store.raw` call (one Undo checkpoint; like other reviewed source edits it detaches only the Owned blocks whose lines change, which the dialog states before Apply and the status names after Apply), saves through the normal path and clears the result. A conflict clears the proposals without changing the Store. No GitHub module, publishing client or network request is involved.

### Guided start (1.7.0)

`workspace/guide.js` is pure. It holds the three Goals (label, description, `needsNetwork`; only the audit needs the network), `validateGuide`/`recoverGuide` for the optional version-1 `guide` workspace field, `chooseGoal` (the only way an unknown-version guide is replaced) and `goalOptions`, which lists step 2's options as existing AppShell action ids plus two blank starts, with offline alternatives for the audit. `validateWorkspace` and `recoverWorkspace` include the field, so backups carry it through `createBackup`; replace restore takes the incoming value and merge keeps the current one. It is not part of `workspaceSettings`, so Studio projects, single-draft JSON and README export never contain it (ADR 0004). `workspace/ui.js` renders both steps inside the shared `app.modal()` dialog, saves the Goal through `app.save()` and opens each option through `app.action()`, so review, stale-state and Undo guards stay with the tool. It makes no request.

### Next steps (1.7.1)

An Arrival (ADR 0005) is `app.arrival = { draftId, kind, detail }`, held in memory only. `kind` is `import`, `audit`, `template` or `blank`; `detail` keeps only known values of `mode` (`new`/`replace`/`append`/`merge`), `origin` (`github`/`file`/`project`), `existing` and `template` (`profile`/`repository`), through `createArrival` in `workspace/guide.js`. App-shell calls `app.arrive()` after `import-apply` (all modes, including Re-import; `import-dialog` adds `origin` to the event), `audit-improve` (existing document, new draft, or `repositoryReadme(context, "audit")` when the builder is opened from the audit), a profile template click, the repository builder's create (template) or open-original (GitHub import) outside the audit, and `openProjectDialog` (import from a project); Guided start's blank options arrive as `blank`. `addDraft` now returns the new draft, so nothing arrives when the 500-document limit refuses one. `load()` of another id, workspace restore and **Hide** call `app.clearArrival()`; nothing writes the Arrival to storage, backups or projects, so a reload drops it.

`nextSteps(arrival, facts)` is pure and deterministic. `facts` come from `documentFacts(draft)` (block count, a single Custom Markdown block, empty Markdown, `documentTarget`, `documentGroup`, an import source) plus the Goal, `navigator.onLine` and `storageBlocked`, all read without analysis or I/O. It returns at most three `{ command, label, reason }` entries drawn only from `NEXT_STEP_COMMANDS`: existing command or `data-action` ids plus the `sections` and `library` builder tabs, which `workspaceAction` opens (expanding a collapsed builder) with focus on the tab heading. Offline it drops `NETWORK_COMMANDS` and `offlineHidden` reports that it did; with blocked storage the last step is `download`. `arrivalContext` gives the one-sentence context. Unit tests pin the whole table and sweep every combination of Arrival and facts for write, publish or offline network commands.

`workspace/ui.js` installs `<section class="next-steps" aria-labelledby>` after `.batch-bar`. `renderNextSteps` shows it only for the active document's Arrival when `nextStepsEnabled(guide)`, and re-renders on Arrival changes, dialog close and `online`/`offline`. Step buttons are keyed by command and reused, so focus and `dialogTrigger` survive a re-render, and the shared `data-action` dispatch opens each tool, records Local activity for listed commands and returns focus to the step when its dialog closes. The panel is not a live region and never moves focus; native modality makes it inert behind dialogs. **Hide** focuses the editor when visible, else `#draft-select`. The Settings checkbox writes `guide.nextSteps` through `setNextSteps`, which like `chooseGoal` is an explicit choice that replaces an unknown-version guide.

### Audience-aware README review (1.9.25)

`audience/review.js` is a pure, local analyzer. It maps populated recognized headings to bounded topic roles for four reader perspectives and four first-visit project types. Evidence statuses are `observed`, `not-detected` or `unknown`; the model has no score and says heading presence is not proof of accuracy or completeness. Section ordering accepts only distinct H2 headings with at least two distinct recognized roles and at most one H1. It sorts exact source slices, leaves the preamble untouched and refuses missing, repeated or ambiguous hierarchies.

`audience/dialog.js` is loaded only when **Audience review** opens and is included in the production service-worker cache. Persona and project-type changes recalculate in memory and clear approval. A safe changed plan renders the shared read-only before/after/diff surface; apply requires explicit approval and sends the original draft snapshot, source and proposed source to AppShell. AppShell rejects stale state and otherwise performs one `Store.raw` update, preserving normal detachment and Undo behavior. Analysis makes no request, persists no findings or choice and performs no GitHub write.

### Usability validation (1.7.2)

Usability evidence comes from Scripted runs and facilitated Participant sessions, never in-app analytics (ADR 0006). The app gains no telemetry, session recorder or storage key, and Local activity keeps its fixed scope. [usability-scripts.md](usability-scripts.md) holds the facilitator protocol and the Usability scenario table (ID, audience, start state, success criterion, step budget); [usability-findings.md](usability-findings.md) is the Friction tracker. `scripts/usability-docs.mjs` is pure: `parseScenarios` reads the scenario table and `validateFindings` checks the tracker, so each kind of run stays in its own section, no finding is mislabelled as a Participant session, every Fixed row links a test and no severity 1–2 item from a Scripted run or heuristic walkthrough stays open. `tests/browser/usability-scenarios.spec.js` takes its budgets from the scripts doc, counts author actions through a wrapper around click, key press and field entry, and attaches `{ scenario, audience, completed, steps, budget, keyboardOnly }` as JSON. A budget therefore changes only with the doc.

Two fixes came from the baseline. `workspace/unsaved-section.js` is pure: `unsavedSection(opened, current)` compares a section's serialized Markdown with what it was when the form opened, and `unsavedSectionPrompt` words the question. `builder-form` exposes `isDirty()` and `save()` (the same commit as its submit button); AppShell's `download`, `copy`, `save-project`, `backup-all` and draft `backup` actions call `unsavedSectionGuard(action, run)`, which asks before running instead of leaving unsaved edits out, and saves only on the author's choice. It runs the tool after a save only when the form is still the builder's current form and the `commit` handler confirmed the save (`sectionCommits`), so a form replaced behind the dialog is never reported as saved; with invalid fields (`canSave()` false) it offers no save. `restoreNotice` words the restore notification and always names the draft a merge opened. `restoreWorkspace` merge now sets `active` to the backup's own active draft (its re-validated id) while keeping every local draft. Guided start lists **Restore a backup**, a `data-action="restore"` Start path into the existing validated restore dialog.
