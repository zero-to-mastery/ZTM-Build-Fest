# v1.6.1 — Drift Checks

Implements story #190 (Stale commands and links) with tasks #206 (bounded drift evidence detectors) and #207 (false positives, missing files and link failures) under epic #184 (Documentation Drift Detection). Story #191 (reviewed drift remediation) is not included: drift checks never propose or apply edits.

Documents with a GitHub target can run an explicit, read-only **drift check** from the Evidence snapshots dialog or **GitHub → Drift check**. Claims are extracted from the local Markdown: package scripts and installs, files named in shell commands, inline paths, relative and same-repository GitHub links, heading anchors, Node version statements and `.env` keys. They are compared with the branch's tree and, at most, the root `package.json`, one `.env` example and ten anchored Markdown files, each read by blob revision and bounded to 256 KB of UTF-8 text.

Each claim is an **observed mismatch** only when repository evidence directly contradicts it at an unambiguous working directory. Heuristics (inline mentions, commands that can fall back to binaries or defaults, generated or ignored paths, ambiguous directories, prose, near anchors, `.env` keys) are **uncertain**; failed, truncated or uncovered evidence is **unknown** and never drift. With a same-target Baseline, results say whether their evidence file changed since it.

Nothing is executed, saved or written: file content is parsed as data and discarded, results are not persisted (ADR 0002) and only GET requests are made. Documents whose only claims are in-page anchors are checked without GitHub, including offline. Snapshot capture now shares the tree reader, relative path resolution and URL walk; its behaviour and the snapshot schema are unchanged.

See [Drift checks](../drift-checks.md).

## Review fixes

- Interpreter options and their values (`node -r dotenv/config`, `node --import tsx`, `python -X dev`, `php -S localhost:8000`, `tsx watch`, `deno run npm:vite`) are no longer read as missing files. An unrecognised option before the script makes a missing file uncertain, since it may have taken the word as its value.
- `node server` and `node scripts/seed` match `server.js`, `scripts/seed.mjs`, TypeScript files or a folder, as Node.js resolves them.
- Version and help commands (`cargo --version`, `make -v`, `docker compose version`, `yarn --version`) no longer need a Makefile, Cargo.toml, compose file or lockfile.
- A missing file that an earlier command in the same block mentions (`python -m venv env`, `go build -o bin/server`, `gcc -o hello`, `curl -LO …/install.sh`) is uncertain instead of an observed mismatch, unless the mentioned folder is already in the tree.
- `cd` into a clone of another repository makes the directory unknown instead of checking its commands against this repository. Paths inside a Git submodule are unknown.
- In `console` sessions, npm's echoed `> pkg@1.0.0 build` / `> node …` output lines are no longer commands. A trailing backtick only continues a line in PowerShell fences and `^` only in cmd fences.
- Absolute `github.com` links to the document itself are checked against the local headings, not the README on GitHub. A link that may name a longer branch (`blob/release/1.0/…` on branch `release`) is uncertain when that first folder is not in the tree.
- Linked Markdown that starts with a UTF-8 BOM keeps its first heading; `&amp;` and other common entities are decoded before slugging; anchors inside HTML comments do not count.
- Fenced commands in list items get their own line numbers even when the item's prose repeats the command. `npm install` with no lockfile now reports a result instead of disappearing.
- Each linked Markdown file is parsed once for anchors, so 200 anchors into one large file no longer freeze the page for seconds.
- A browser test now covers the result being discarded when the Markdown changes while GitHub is read.

## Second review fixes

- Raw HTML headings (`<h1 align="center">My Project</h1>`, multi-line ones included) produce anchors from their text, as on GitHub, in the document and in linked Markdown files, sharing duplicate numbering with Markdown headings.
- A missing `./program` after a build, unpack, download or package-manager step, or after another `./script` (`./autogen.sh` then `./configure`, `make` then `./widget`, `unzip` then `./widget`), is uncertain. Files that earlier blocks mention or create are carried to later blocks, so `python3 -m venv env` and a later block's `source env/bin/activate` are uncertain too.
- `dist`, `build` and similar output folders themselves (`cp -r dist …`, `node build`) are generated, not only paths below them.
- `cd <repo-name>` without a `git clone` in the block may be the clone or a folder of that name; when the tree has the folder both are checked, and a file missing from both is uncertain. After an explicit clone, a second `cd <repo-name>` enters the folder.
- `pushd`/`popd` change and restore the directory, `( cd … )` scopes its `cd` to the subshell, and heredoc and PowerShell here-string bodies are not read as commands.
- Settings such as `python = "^3.9"` are not commands; paths need a letter or digit and no `=`; in untagged fences and for `source`/`.` an interpreter's file must contain `.` or `/`, so prose like `source code lives in src/` is skipped.
- A missing committed template (`.env.example`, `.env.sample`, `.env.template`) is an observed mismatch, like a link to it; only local files such as `.env` or `.env.local` are treated as usually ignored.
