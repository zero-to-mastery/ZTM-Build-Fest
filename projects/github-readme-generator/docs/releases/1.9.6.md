# 1.9.6 — Publishing failure recovery

Implements story #99 and tasks #158/#159 under Epic 08. A lost GitHub write response is no longer presented as a normal failure: the content-free Publish journal records it as unknown, stops the attempt and requires an explicit remote read before any retry.

Reconciliation compares GitHub's current blob SHA with the reviewed Result and Base SHAs. Already-applied content is recorded as written without another PUT; its observed branch head is stored explicitly as reconciliation evidence, never mislabelled as the commit that performed the write. Content still at its Base is eligible for a same-session retry only after a new approval; any third state is diverged and returns to fresh review. The publishing server also refuses an already-applied Result SHA before issuing a PUT.

The journal uses its own browser key and contains target/change-set metadata only—never README, asset or workflow content, credentials or authorization. It is not part of drafts, projects or backups. Invalid journal data remains byte-for-byte in storage, blocks publishing and must be downloaded before the author can explicitly clear it. Local source and editing metadata remain unchanged on every path.
