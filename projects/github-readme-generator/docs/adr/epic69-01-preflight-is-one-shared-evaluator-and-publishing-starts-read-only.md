# Preflight is one shared evaluator and publishing starts read-only

Every publishing review starts in Read-only mode. Writes become approvable only after a Preflight for the exact Publish target returns every blocking check as `pass`. The Preflight is a set of facts gathered by a new read-only server operation and then judged by one pure evaluator, `src/publishing/preflight.js`. The server's own write authorization (`authorizeTarget`) calls the same evaluator, so the reason a write is refused always matches what the dialog showed. Blocking checks cover the service, session, installation, Contents permission, the author's push access, archive state, branch existence, path support and, for workflows, server opt-in plus Workflows: write. An `unknown` result blocks too.

Branch rules (classic protection or rulesets) and committing to the default branch are only advisory warnings. A token without admin rights cannot fully read protection settings, and rulesets can allow bypass. Treating them as blocking would wrongly lock out authors whom GitHub would accept. GitHub's own rejection at write time (403/422) is definite, writes nothing, and leads to the existing "publish on a new branch" route. We rejected trusting the picker's `writable` flag alone: it hides why a target is read-only and ignores the branch. We also rejected a client-only check that the server never enforces. The Preflight result is held only in memory and dropped when the target changes, on disconnect or on reload. It is never saved, because permissions change on GitHub without Studio knowing.
