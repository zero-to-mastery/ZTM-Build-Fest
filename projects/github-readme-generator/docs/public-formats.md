# Public formats and compatibility

Application versions and file schema versions are independent. The 1.x compatibility commitment is to read supported version-1 envelopes and preserve canonical Markdown, using source-only recovery when structured metadata is no longer safe. Future versions are rejected rather than silently interpreted. Keep original files when importing.

| Format                | Required envelope                                                                                          | Optional/defaulted data                                              | Failure behavior                                                                              |
| --------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Studio project        | `schemaVersion: 1`, `type: readme-studio-project`, name, dates, document.markdown, document.blocks, assets | appVersion, metadata, settings, libraries                            | Source-only new draft for readable unsupported/damaged metadata; no original overwrite        |
| Workspace backup      | `version: 1`, drafts (1–500)                                                                               | active, settings, createdAt, activity, guide, reusable libraries     | Validation before merge/replace; damaged storage retained for recovery download               |
| Snippet pack          | `version: 2`, `type: readme-studio-snippet-pack`, name, snippets                                           | description, author, homepage, license, extensions, badgeCollections | Migrate v1 without source changes; reject invalid/future envelopes; reviewed collision policy |
| Extension manifest    | `version: 1`, `type: readme-studio-extension-manifest`, name, publisher, capabilities, entries             | description                                                          | Reject executable shapes, unsafe markup/URLs and undeclared/unsupported capabilities          |
| Theme                 | `version: 1`, `type: readme-studio-theme`, name, theme                                                     | normalized theme defaults                                            | Reject invalid colors/unsafe visual fields/future versions                                    |
| Theme pack            | `version: 1`, `type: readme-studio-theme-pack`, themes                                                     | each entry has name/theme and optional ID                            | Validate entries, repair collisions                                                           |
| Brand kit             | `version: 2`, `type: readme-studio-brand-kit`, name, theme, banner                                         | bounded safe light/dark logo references and alt text                 | Reject v1/future envelopes, unsafe URLs, executable fields and invalid tokens                 |
| Visual pack           | `version: 2`, `type: readme-studio-visual-pack`, version-2 library                                         | versioned themes/banners/bundles and optional brand-kit logos        | Migrate v1 packs; validate all categories before applying                                     |
| Badge collection      | `version: 1`, `type: badge-collection`, name, badges                                                       | id, style (plain default)                                            | Validate badge models; fresh IDs on import as appropriate                                     |
| Project showcase pack | `version: 1`, `type: project-showcase`, projects                                                           | supported project fields and public GitHub provenance                | Reject invalid/future file; reviewed copies are appended                                      |

The workspace backup's optional `guide` (`{ version: 1, goal, nextSteps }`, see [Guided start](guided-start.md)) is a workspace field, not a setting: Studio projects, single-draft JSON and README exports never contain it. Any other `guide` value that is not version 1 (another version, or a malformed value such as `null`, a string, a list or an object without `version`) is kept unchanged and read as no goal when it is up to 1 KB, within the backup's nesting limit and without credential-named keys; a larger or uncarriable value is replaced by the default.

See [project schema](project-schema.md), [snippets](snippet-packs.md), [themes](themes.md), [badges](badges.md) and [projects](projects.md) for field behavior and limits. Single-theme, banner-preset and brand-kit exports are configurations, not README content. All untrusted source previews remain sanitized; exported Markdown remains user source.

Public files are supported interchange boundaries. Internal block settings, DOM custom-element interfaces, localStorage keys, Worker messages, Rust bindings and publishing HTTP routes are implementation details, not a public programming SDK. Known structured models retain editability where exact serialization can be verified; unknown models must not be reverse-engineered or silently rewritten.

A schema change must introduce an explicit version and source-preserving migration or reject safely. Brand-kit logo references therefore live only in version-2 brand-kit, visual-pack and nested visual-library data. Version-1 visual packs and legacy `readme-studio-visual-preset` files migrate without a logo field; older applications reject the version-2 envelope instead of accepting and silently dropping logo data. Do not repurpose a field's meaning within the same public schema. Breaking application behavior belongs in a major release; deprecations should appear in the changelog and migration guide before removal. Security validation can become stricter without promising continued execution/rendering of unsafe markup.

From 1.0, patch releases fix bugs/security/compatibility, minor releases add backward-compatible features, and major releases introduce breaking schema/API behavior. Deprecation notices cover old component/theme/provider fields before removal; preserved source is the fallback when structured editing cannot safely continue.
